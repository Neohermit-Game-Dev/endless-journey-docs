Shredder

Players hold a ProximityPrompt on a placed Workbench to convert non-Energy junk Tools into crafting material Tools via a two-step server handshake; ejected materials land in the world with a bezier arc and hover until picked up or auto-collected.

At a glance​

LayerFileRole
Clientsrc/StarterPlayer/StarterPlayerScripts/ShredderClient.client.luauPrompt registration, nonce-guarded two-step handshake, junk-count-reactive HoldDuration updates
Serversrc/ServerScriptService/ShredderServer.server.luauSession management, anti-exploit validation, junk consumption, material ejection arc, auto-collect loop

Configsrc/ReplicatedStorage/SharedModules/Configs/ShredderConfig.luauAll tunable constants for interaction, hold duration, anti-exploit, arc animation, auto-collect, and asset names

Packets: ReqShredderStart, ReqShredderComplete — see Networking Map Signals: none — the shredder is a self-contained two-step RemoteFunction handshake

How it works​

Client: prompt and handshake​

ShredderClient watches CollectionService for Workbench-tagged models. On each workbench it finds a ProximityPrompts/ShredPromptPart/ProximityPrompt, sets ActionText, HoldDuration, and MaxActivationDistance from config, and wires three connections: PromptButtonHoldBegan (fires ReqShredderStart), PromptButtonHoldEnded (bumps the nonce to cancel), and Triggered (fires ReqShredderComplete only when the nonce matches the armed value). A Backpack and Character Janitor pair keeps HoldDuration in sync whenever junk is added or removed. If the player holds the prompt with zero non-Energy junk, an "info" notification fires and the prompt is briefly disabled.

Server: two-step session​

ReqShredderStart validates the workbench tag, proximity (INTERACT_DISTANCE + INTERACT_DISTANCE_TOLERANCE), workbench lock state, per-player cooldown, and junk availability. It stores a session record (workbench, start time, computed duration, junk snapshot). ReqShredderComplete re-checks all constraints plus timing (elapsed >= duration - HOLD_COMPLETION_TOLERANCE), re-validates junk still belongs to the player from the snapshot, builds a shuffled material sequence, destroys all junk Tools, locks the workbench, then spawns ejectMaterials.

Ejection​

ejectMaterials animates each handle along a Catmull-Rom spline (MotionMaster.SplineMove) with uniform-disk scatter around LandingPoint, then calls ProximityPickupServer.RegisterItem. Overflow beyond MAX_ANIMATED_EJECT_ITEMS is granted directly in scheduler batches. A 0.5 s auto-collect loop sweeps droppedMaterials; after AUTO_COLLECT_DELAY the item is force-claimed to the owner. See Proximity Pickup for the registration/claim contract.

Shared math and result codes​

ShredderMath.ComputeHoldDuration linearly interpolates hold time between MIN_HOLD_DURATION (1 item) and MAX_HOLD_DURATION (MAX_JUNK_COUNT items). Both client and server call it so the prompt ring and the server timing check always agree. ShredderResultCodes is a frozen enum used by both sides for unambiguous rejection reasons.

Gotchas​

Anti-exploit thresholds are sensitive

INTERACT_DISTANCE_TOLERANCE, HOLD_COMPLETION_TOLERANCE, and PER_PLAYER_COOLDOWN are the primary barriers against timing exploits and teleport-shredding. Increasing tolerances too far removes protection; tightening them too far breaks legit high-latency players.

Studio asset requirements — all three must be present or the server will warn and abort ejection:

  1. Each workbench Model must be tagged "Workbench" with a PrimaryPart set.
  2. Each workbench must contain a child Model named "TrajectoryPoints" (tag it PlacementIgnore) with two invisible, anchored, non-collidable BasePart children: "SpawnPoint" (at the shredder output mouth) and "LandingPoint" (floor landing target).
  3. In ReplicatedStorage, a Folder named "CraftingMaterials" must contain Tool templates named "Wood" and "Metal", each with a BasePart child named "Handle". Set CanBeDropped = false on each template.

Nonce guard. The client uses a per-workbench nonce pair (holdNonce, armedNonce) to drop stale ReqShredderComplete calls when the player releases early or changes workbenches mid-hold. Modifying the hold flow must preserve this guard or the server's NO_SESSION rejection will fire spuriously.

Junk snapshot. The server snapshots junk at ReqShredderStart time. ReqShredderComplete re-filters that snapshot to tools still in the player's possession — it does not re-scan the Backpack. This prevents inflation from picking up new junk during the hold.

Energy junk exclusion. Only Metal and Wood junk types are consumed and yield output. Energy junk is excluded from both the client count and the server's junk collection helpers.

Data flow​

sequenceDiagram
    participant C as ShredderClient
    participant S as ShredderServer

    C->>C: PromptButtonHoldBegan - countNonEnergyJunks() > 0
    C->>S: ReqShredderStart(bench)
    S->>S: validate tag, proximity, not locked, cooldown, junk count
    S->>S: ShredderMath.ComputeHoldDuration()
    S->>S: record session + StartTime
    S->>C: (isValid, duration, code)
    C->>C: prompt.HoldDuration = duration

    C->>C: PromptButtonHoldEnded -> nonce bump (cancels armed session)

    C->>C: Prompt.Triggered (hold complete), armedNonce check passes
    C->>S: ReqShredderComplete(bench)
    S->>S: re-validate session, workbench match, elapsed >= duration - TOLERANCE
    S->>S: re-verify junk still owned, buildMaterialSequence(junks)
    S->>S: destroy junk Tools, lock workbench
    S->>C: (success, woodCount, metalCount, code)
    S->>S: task.spawn(ejectMaterials)
    Note over S: SplineMove handle P0->arcPeak->landing<br/>ProximityPickupServer.RegisterItem()<br/>tag CraftMaterial, auto-collect loop (0.5s poll)<br/>unlock workbench after ARC_DURATION
