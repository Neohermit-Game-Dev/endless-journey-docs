Sound

A layered client audio system built around a single facade module, SoundManager. All game audio — one-shot SFX, positional SFX, looped sounds, background music, and ambience beds — flows through it; no other script creates Sound instances directly. Playback is entirely client-local except for positional SFX replication and BGM context, which are server-relayed/server-driven through Packets.

How it works​

Facade and playback​

SoundController.client.luau calls SoundManager.Init() once at startup. Init creates the SoundGroup bus hierarchy (Groups.Ensure), warms the positional sound pool (Pool.Ensure plus per-asset pre-warm), connects the replication receiver (SFX.ConnectReplication), preloads every configured asset ID via ContentProvider:PreloadAsync, and autostarts any ambience beds listed in SoundConfig.Ambience.Autostart.

After Init, any client script or tool may require(SharedModules.SoundManager) and call the facade (PlaySFX, PlaySFXAt, PlayLooped, PlayMusic, SetAmbience, SetVolume). The submodules (Groups, Pool, SFX, Music, Ambience) are internal and should not be required directly. The bus hierarchy is fixed:

SoundService
  └─ Master SoundGroup
        ├─ SFX SoundGroup
        ├─ BGM SoundGroup
        └─ Ambience SoundGroup

Positional replication​

The server does not play audio itself — ReplicatedSoundService.server.luau acts only as a validated relay for Packets.ReplicateSoundAtLocation:

  1. Per-player rate limit (MIN_INTERVAL = 0.05s) rejects bursts.
  2. Payload shape is validated (data.SoundConfig.Id must be a string).
  3. The sound ID must be in ALLOWED_SOUND_IDS, built at startup from SoundConfig.GetReplicatedIds() — any SFX entry with Replicate = true is included automatically.
  4. The original payload is passed to every other connected player via FireClient.

The receiving client's SFX.ConnectReplication handler acquires a pooled part at the given position and plays it, the same path PlaySFXAt uses locally.

BGM contexts​

SoundConfig.Music.Playlists defines exactly three named playlists — one per BGM context. There is no generic/default playlist; Music.Play falls back to "Normal" only when called with no argument.

ContextTriggerGap behavior
NormalDefault; nothing else activeGapped — random silence between tracks
CombatServer calls MusicService.SetContext(player, "Combat")Continuous — overlapping crossfade, no silence
LowFuelAutomatic, client-derived from fuel levelContinuous — overlapping crossfade, no silence

Priority when more than one condition is true: Combat > LowFuel > Normal. MusicDirector.client.luau holds two local inputs — combatContext (set by the server) and lowFuelActive (derived locally from Signals.OnTrainStateChanged) — and recomputes the resolved context on every change to either, calling SoundManager.PlayMusic(context) only when the resolved context actually changes. A low-fuel state during combat is suppressed without losing track position when combat ends.

Driving combat from server gameplay code (an event or outpost zone):

local MusicService = require(game.ServerStorage.SharedModules.MusicService)
MusicService.SetContext(player, "Combat") -- on event/outpost enter
MusicService.SetContext(player, "Normal") -- on event/outpost leave

MusicService.SetContext is stateless — it only fires Packets.SetMusicContext to the targeted player. Passing "Normal" clears the combat override; the client then falls back to LowFuel or Normal based on its own fuel state. Low fuel itself needs no gameplay code: MusicDirector watches Signals.OnTrainStateChanged and activates LowFuel whenever fuel / TrainConfig.MAX_FUEL drops below SoundConfig.Music.LowFuelPct (default 0.25).

Volume persistence​

The four buses (Master, SFX, BGM, Ambience) persist across sessions as part of the generic Settings system, not inside SoundManager itself. SoundManager.SetVolume(group, volume) / GetVolume(group) remain the immediate-apply primitives — they read/write the Groups bus hierarchy directly and do nothing else.

UI code that needs the change saved calls SettingsClient.Set("MasterVolume" | "MusicVolume" | "SFXVolume" | "AmbienceVolume", value) instead. SettingsClient.Set validates via SettingsSchema, applies it (SettingsAppliers maps the key to a bus via SettingsConfig.VolumeBusByKey and calls Groups.SetVolume), fires Signals.OnSettingChanged(key, value), and schedules a debounced save (Packets.SaveSetting) that coalesces rapid changes (e.g. a slider drag) into one trailing send. On join, SettingsManager delivers the saved settings map via Packets.SyncSettings; SettingsClient applies each entry the same way but never re-saves a synced value, so no feedback loop results. See Settings for the full validate/apply/persist flow.

Gotchas​

Never create ad-hoc Sound instances

All Sound creation must go through SoundManager. Creating Sound instances by hand bypasses the bus groups (volume controls have no effect), skips the positional pool (memory churn), and may leak sounds that persist across character reloads.

  • SoundManager.Init() must be called before any Play* call. It is called once by SoundController.client.luau; do not call it again elsewhere.
  • PlaySFXAt parents a pooled BasePart at the given Vector3 in the workspace; the pool releases it after sound.TimeLength + 0.05 seconds. Do not hold references to the part or sound after the call.
  • PlayLooped returns a LoopHandle. The caller must call handle:Stop() or handle:Destroy() when done — an abandoned handle leaks a live Sound under SoundService.
  • A sound entry with Replicate = true and an empty Id ("") is excluded from the allowlist automatically by GetReplicatedIds(); the pool warm step also skips empty IDs.
  • The BGM and Ambience buses default below 1.0. An SFX entry authored at Volume = 0.5 will be audibly louder than music at the same numeric volume because the bus multipliers differ.

Data flow​

sequenceDiagram
    participant ClientA as Playing client
    participant Relay as ReplicatedSoundService (server)
    participant ClientB as Other clients
    participant MusicSvc as MusicService (server)
    participant Director as MusicDirector (owning client)

    Note over ClientA,ClientB: POSITIONAL SFX REPLICATION
    ClientA->>ClientA: SoundManager.PlaySFXAt(name, position) — local pooled playback
    ClientA->>Relay: ReplicateSoundAtLocation(location, soundConfig)
    Relay->>Relay: rate-limit (MIN_INTERVAL) + payload + ALLOWED_SOUND_IDS check
    Relay->>ClientB: FireClient to all other players
    ClientB->>ClientB: SFX.ConnectReplication — Pool.Acquire(position) positional playback

    Note over MusicSvc,Director: BGM CONTEXT SWITCH
    MusicSvc->>Director: SetMusicContext(context) (e.g. "Combat")
    Director->>Director: resolve priority Combat > LowFuel > Normal
    alt resolved context changed
        Director->>Director: SoundManager.PlayMusic(context) — crossfade or gap per playlist
    end
    Note over Director: Signals.OnTrainStateChanged (fuel) toggles LowFuel locally — no server round-trip

Tuning​

  • Config module: SoundConfig — src/ReplicatedStorage/SharedModules/Configs/SoundConfig.luau
  • Playbook: Add a Sound

Bus volumes (SoundConfig.GroupVolumes):

BusDefault
Master1.0
SFX1.0
BGM0.6
Ambience0.5

Per-SFX definition fields (SoundConfig.Sfx):

FieldDescription
IdRoblox asset ID string; empty string disables the entry
VolumeDefault playback volume (0–1)
PitchFixed pitch multiplier
PitchRangeTwo-element array {min, max}; randomizes pitch per play
GroupBus name ("SFX", "BGM", "Ambience"); defaults to "SFX"
Replicatetrue to include the entry in the server relay allowlist
DebounceMinimum seconds between plays of this entry (anti-spam)
PoolInitialPre-allocated pool slots warmed at Init (positional only)
PoolMaxHard cap on the per-asset pool size (positional only)

Adding a new replicable SFX needs only Replicate = true on the SoundConfig.Sfx entry — GetReplicatedIds() and ReplicatedSoundService pick it up automatically on next server start.

Music playlist fields (SoundConfig.Music.Playlists):

FieldDescription
TracksArray of asset IDs; played in Shuffle order if set, else array order
ShuffleRandomize track order each time the playlist (re)starts
FadeInSeconds to fade a new track up from 0 at start
FadeOutSeconds to fade a track down to 0 at its end; also the crossfade overlap window when continuous
GapMin / GapMaxRandom silence range (seconds) between tracks; GapMax <= 0 means continuous (overlapping crossfade, no silence)
VolumeTarget playback volume for tracks in this playlist

SoundConfig.Music.LowFuelPct (default 0.25) is the fuel-fraction threshold below which MusicDirector activates the LowFuel context.
