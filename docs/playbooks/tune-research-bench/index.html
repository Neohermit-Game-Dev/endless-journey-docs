Tune Research Bench

Goal: Adjust Research Bench node costs/durations, fuel/queue/refund constants, or add a new node.

Steps​

  1. Change a node's cost or duration. Open src/ReplicatedStorage/SharedModules/Configs/ResearchConfig.luau and edit the Levels table on the node:

    Shield_Alpha = {
        DisplayName = "Shield α", Description = "+50 maximum shield energy.",
        GuiPath = "TrainShield.TrainShield1", Prereqs = nil, MaxLevel = 1,
        Effects = { { Type = "StatBuff", Key = "MaxHP", PerLevel = 50 } },
        Levels = { [1] = { Cost = { Metal = 25 }, Duration = 30 } },  -- ← cost / time
    },

    Cost is a { [material]: number } map spent from the server-wide Material Pool — only Wood and Metal are valid (any other key makes MaterialPool.Spend refuse the enqueue), matching the authored WoodCostContainer/MetalCostContainer. Duration is in seconds and is the wall-clock time the node takes to complete while fuel is available — see step 2 below. Both values take effect immediately for any job enqueued after the change; jobs already queued or active keep the cost/duration they were enqueued with (no live re-pricing). Every node ships at MaxLevel = 1 today, so in practice only Levels[1] exists.

    Changing an Effects entry's PerLevel (for StatBuff) or DrainPerLevel (for FuelEfficiency) changes the buff granted — see step 5 for the effect shapes. No code change is needed; ResearchEffectsDispatcher recomputes buffs from every node's Effects list on every level-up.

  2. Review the fuel and pause behavior before retuning it.

    • FUEL_CAP (default 100) — the fuel reserve ceiling.
    • FUEL_BURN_RATE (default 1.0/sec) — how fast fuel burns while a job is active. Raising this makes fuel run out faster relative to node Duration, so jobs pause more often; consider raising FUEL_PER_POINT in tandem if you raise this.
    • FUEL_PER_POINT (default 2) — bench fuel per pool Energy point; a refuel fills to FUEL_CAP and spends only the points needed. Tune this against FUEL_BURN_RATE * <typical node Duration> so a single refuel roughly covers the jobs you want it to.

    A job's elapsed only advances while fuel is available (ResearchState.advance clamps effectiveDt = min(dt, fuel / burnRate)), so at FUEL_BURN_RATE = 1.0 and FUEL_CAP = 100, a fully-fueled bench can sustain 100 seconds of active research before needing a refuel.

  3. Change the queue depth. QUEUE_MAX (default 3) caps how many jobs can wait behind the active one (ResearchState.validateEnqueue rejects with QUEUE_FULL beyond this). It matches the three authored QueueButton1..3 slots in StarterGui.TechTreeGui — raising it beyond 3 needs matching Studio work (more queue slot Frames) or the extra queued jobs will have nowhere to render; lowering it forces more frequent bench visits.

  4. Change the cancel refund fraction. ACTIVE_REFUND_FRACTION (default 0.5) is the fraction of the active job's cost refunded when it is cancelled — queued jobs always refund at 1.0 (full), since they haven't started consuming fuel/time yet. Set this to 1.0 to make cancelling an in-progress job free, or 0 to make active progress non-refundable. This does not affect the cascade behavior itself (see Research Bench — Cascade-cancel) — only the fraction applied to the active job's refund.

  5. Add a new node. Unlike the old code-generated GUI, a new node needs both a config entry and a Studio card — TechTreeGuiController only binds cards that already exist under StarterGui.TechTreeGui...TechScrollingFrame; it does not create them.

    • Author the card in Studio first: duplicate an existing card Frame (keeps TechText/StatusContainer/UIStroke/UICorner/UIPadding) under the right branch frame, rename it, and wire its ConnectionLines attribute (outgoing — the comma-separated Line* frames running out of it, if any) plus the new/incoming line(s) on whichever card(s) should point into it.

    • Declare it in ResearchConfig.Nodes. Pick a unique key (the nodeId, <Branch>_<Name> by convention), DisplayName and Description (both shown — DisplayName/timer on the card, both plus Description in the detail panel), GuiPath ("<BranchFrame>.<CardFrame>", matching the card you just authored), an optional Prereqs list (other nodes' ids — all must reach level ≥ 1 before this node accepts enqueues; nil means available from the start), MaxLevel (1 for every shipped node — leave it at 1 unless you deliberately want a multi-level node, which also needs a QueueButton/queue-slot rethink since the GUI assumes one job per node), an optional Gamepass id (0/nil = no gate), and Levels (one {Cost, Duration} entry per level from 1 to MaxLevel).

      Example — a new single-level "Reinforced Hull" node gated behind both Shield_Gamma and Shield_EfficiencyPlus:

      TrainShield_ReinforcedHull = {
          DisplayName = "Reinforced Hull", Description = "+75 maximum shield energy.",
          GuiPath = "TrainShield.TrainShield5", Prereqs = { "Shield_Gamma", "Shield_EfficiencyPlus" }, MaxLevel = 1,
          Effects = { { Type = "StatBuff", Key = "MaxHP", PerLevel = 75 } },
          Levels = { [1] = { Cost = { Metal = 260, Wood = 40 }, Duration = 90 } },
      },

    • Choose an Effects list shape (omit entirely — Effects = nil — for an unlock-flag node with no buff; a node can list more than one effect, see Shield_Efficiency/Shield_Delta in ResearchConfig for two-entry examples):

      • { Type = "StatBuff", Key = <attributeName>, PerLevel = <number> } — the effect handler in ResearchEffectsDispatcher sums PerLevel * level across every node sharing the same Key into that attribute on ReplicatedStorage/ResearchBuffs. Reuse an existing Key (e.g. "MaxHP") to stack with existing nodes, or introduce a new Key — publishing a key with no consumer is safe (it just sits in the folder, as ShieldStrength/ShieldEfficiency/ShieldAutoRegen do today) but be deliberate about it, not accidental; wire a real consumer if you want the buff to do something.
      • { Type = "FuelEfficiency", DrainPerLevel = <number, 0 < n < 1> } — multiplies into ResearchBuffs.FuelEfficiency as DrainPerLevel ^ level (values below 1 reduce drain; e.g. 0.85 per level means 3 levels compound to 0.85^3 ≈ 0.614). TrainFuelManager already reads this attribute — no new consumer needed if you're adding a fuel-efficiency node.
      • Any other Type string logs a warn and no-ops in ResearchEffectsDispatcher — safe to author a node ahead of its gameplay wiring, but the buff will not apply until a handler exists.
      • nil — an unlock-flag node. Once it reaches level 1, ResearchUnlocked/<nodeId> is written; wire a Workbench recipe's RequiresNode to that same id (see Workbench Crafting), or read the folder from any other gate you want to add.

    • Reload in Studio: ResearchConfig.validate() warns on any unknown Prereqs id, a Prereqs cycle, a missing GuiPath, or an Effects entry with no dispatcher handler. TechTreeGuiController's bind pass separately warns if GuiPath doesn't resolve to a card, or if the card you authored isn't claimed by any node — fix both classes of warning before testing.

    • Test in Studio: join at the bench, open the tree, confirm the new card is locked/greyed until its Prereqs are met, select it and enqueue, and confirm materials are deducted immediately. Let it complete (or refuel to speed through fuel pauses) and confirm the effect applies — check the ReplicatedStorage/ResearchBuffs attribute in Explorer for a StatBuff/FuelEfficiency node, or ReplicatedStorage/ResearchUnlocked/<nodeId> for an unlock-flag node.

Verify​

  1. Join in Studio with API Services enabled, walk to the placed bench under workspace.PlacedObjects.
  2. Open the tree (TechPromptPart prompt) and select/enqueue a cheap node.
  3. Confirm materials are deducted immediately (before the job completes) and the in-progress panel shows the job advancing, with the card's stroke pulsing (InProgress state).
  4. Let fuel run to 0 (or start with an empty bench) and confirm the progress bar stops advancing; click Refuel in the queue panel with Energy in the pool and confirm progress resumes.
  5. Cancel the active job from the in-progress panel — confirm it refunds at ACTIVE_REFUND_FRACTION and the card returns to Available. Queue a job, then cancel it from its QueueButton slot — confirm a full refund and that ReplicatedStorage/ResearchUnlocked/ResearchBuffs do not update for a job that never completed.
  6. Let a StatBuff node complete and confirm the target attribute in ReplicatedStorage/ResearchBuffs updates and the card turns Unlocked (cyan), or let an unlock-flag node complete and confirm ReplicatedStorage/ResearchUnlocked/<nodeId> appears and the corresponding Workbench recipe ungreys.
  7. If testing a Gamepass-gated node, confirm enqueue is rejected with GAMEPASS_REQUIRED while ungated, and succeeds after granting the pass in Studio (or setting BIOME_SELECTOR_GAMEPASS_ID to a pass you own).
