Train Shield

A single global shield pool governs the train's structural integrity for all players. Unlike fuel, the shield has no continuous drain — it is event-driven: damage events deplete it, and players restore it by spending pool Energy at a ShieldConsole. Depleting the shield to 0 is no longer a game over; once the shield is down, further attacks bleed through to fuel instead. TrainShieldManager is the sole authority — clients receive snapshots and update the diegetic shield monitor.

How it works​

Recharge​

Triggering a ShieldConsole-tagged prompt sends ReqRechargeShield(console). The server validates the tag and proximity, and spends pool Energy via MaterialPool.SpendUpTo("Energy", maxShield − currentShield, SHIELD_PER_POINT) (only the points needed, never over-filled). An isRecharging boolean mutex serializes concurrent requests — like the fuel system's isRefueling, it is not a queue: a second request in flight returns SHIELD_FULL or NO_ENERGY rather than a queued success. On success the client plays SoundManager.PlaySFX("ShieldRecharge").

Damage / fuel bleed-through​

TrainShieldManager.ApplyDamage(amount, source?) is the single damage entry point for the train — all incoming attack/hazard damage, whether it lands on the shield or bleeds through to fuel, routes through this call. No system calls it yet; it is designed for a future combat/hazard system. Guards (all must pass or the call is a no-op): hasStarted must be true, TrainGameOver.HasFired() must be false, amount must be > 0 and not NaN.

Shield > 0 (absorbs):  currentShield = max(0, currentShield - amount); broadcast()
                       -- a hit that drives it exactly to 0 discards its excess; this does NOT end the round
Shield == 0 (bleeds):  TrainFuelManager.ApplyFuelDamage(amount * TrainConfig.FUEL_DAMAGE_FACTOR, source)
                       -- see Train Fuel: Combat fuel-kill for what happens if this zeroes fuel

This replaced the old behavior where the shield reaching 0 called TrainGameOver.Trigger directly — shield depletion by itself no longer ends the round, it just removes the train's damage buffer. TrainConfig.CORE_TAG ("TrainCore") is reserved for the train's structural model for a future combat system to tag; ApplyDamage does not read it directly.

Max formula (buffs)​

maxShield = (BASE_SHIELD + ResearchBuffs.MaxHP) * (1 + PartyPerkBuffs.TrainShieldBonus)
  • Research Bench additive: each completed Train Shield node accumulates onto ResearchBuffs.MaxHP — Shield_Alpha +50, Shield_Beta +100, Shield_Gamma +150, Shield_Delta +200 (each MaxLevel = 1, up to +500 total) — added before the perk multiplier. See Research Bench.
  • Party perk multiplicative: TrainShieldBonus = 0.05 * maxLevel across all players (server-max resolution), applied on top of the base + Research sum.
  • Ratio-preserving recompute: when either buff changes, recomputeMax preserves the current fill ratio (currentShield / oldMax) and rounds to the nearest integer — a player at 60% shield stays at ~60% after an upgrade.

subscribeBuffs attaches GetAttributeChangedSignal listeners to both buff folders via WaitForChild, then calls recomputeMax once after attach to catch any missed signals during the wait. See Research Bench and Perks for the upstream buff systems.

Shield monitor​

The shield HUD is diegetic first: TrainShieldGuiController clones the ReplicatedStorage.GuiAssets.TrainShieldGui SurfaceGui template onto every BasePart tagged TrainConfig.SHIELD_MONITOR_TAG ("TrainShieldMonitor"), discovered via CollectionService:GetTagged plus live add/remove signals. The clone is created client-side, so each player drives their own independent copy on the same shared surface — no server/replication involvement in the GUI itself. Each registered monitor owns a Janitor that destroys the clone when the tag is removed.

A second ProximityPrompt on the console opens PlayerGui.TrainShieldGui, a full-screen copy of the same layout, for players who want to read the console without standing at the right angle to the glass. Both assets share one element tree under MainContainer.SafeContainer, so one resolveView and one render path serve both — see The zoom view below.

Readouts​

All five readouts are wired to real sources today. SHIELD HEALTH and SHIELD CAPACITY also drive real gameplay math (current/max shield). STRENGTH RATING, SHIELD EFFICIENCY, and AUTO-REGENERATION read the Shield_Efficiency/Shield_EfficiencyPlus/Shield_Delta buff keys and display them accurately — but nothing in the codebase changes damage or refuel math based on those three yet, so researching them changes the readout, not the shield's actual behavior. See Research Bench — Honest status of Effects.

ReadoutSourceBehaviour
Shield % / ONLINE-CRITICAL / SHIELD HEALTHTrainStateCache.ShieldFraction()Eased per frame, then banded (below)
SHIELD CAPACITYTrainStateCache.ShieldMax() ÷ BASE_SHIELD100% at stock; rises as ResearchBuffs.MaxHP and the party perk raise max
STRENGTH RATINGResearchBuffs[SHIELD_STRENGTH_BUFF_KEY]B → A → S per ShieldStrengthRatings; B when unset
SHIELD EFFICIENCYResearchBuffs[SHIELD_EFFICIENCY_BUFF_KEY]Percentage added to an Energy insert; 0 % when unset
AUTO-REGENERATIONResearchBuffs[SHIELD_AUTOREGEN_BUFF_KEY]FUNCTIONAL (green) once > 0, else BROKEN (red)

The shield fraction is bucketed into one of TrainConfig.ShieldBands, healthiest first:

BandShieldColour
HEALTHYabove 60%#33ffad
WARNING30–60%#ffcc33
DANGER30% or below#e6372e

The SHIELD HEALTH line always takes the band colour. The shield icon's big number, ONLINE/CRITICAL status and TRAIN SHIELD title hold their authored CRT cyan (SHIELD_ICON_HEALTHY_COLOR, #33ccff) through HEALTHY and adopt the band colour from WARNING down — so a full shield reads cyan on the icon and green on the stat line, which is deliberate, while anything worth warning about colours both in step. DANGER is also where the Shield ImageLabel swaps to its cracked asset and the status flips to CRITICAL. Moving up a band costs an extra SHIELD_BAND_HYSTERESIS (0.03), so a value resting on a boundary can't strobe between two colours every frame.

The percentage is always out of the current max, so a capacity upgrade raises what 100% is worth without the number ever reading above 100 — SHIELD CAPACITY is where a 2000-point shield shows up as 200%, not the shield readout.

What updates when​

Only the eased shield number needs RenderStepped; one global loop drives every view. The other four stats change rarely, so they run event-driven off Signals.OnTrainShieldChanged (capacity moves only when the server recomputes max, which is the same event that carries a snapshot) and ResearchBuffs.AttributeChanged. ResearchBuffs is a plain attribute folder in ReplicatedStorage, so the Tech Tree's totals replicate to the client for free — no packet, no server change. The controller waits up to 30s for the folder, since a server script creates it, then reconciles once after attaching.

TrainStateCache.ShieldFraction() returns nil until the server has actually sent a snapshot. The monitor does not invent a starting value — it used to seed displayedShieldPct = 1, asserting "Online 100%" before the server had spoken at all; see Join-Sync Snapshot Handshake. While nil it renders a placeholder ("—", neutral grey) and snaps directly to the first real value with no eased sweep.

TrainShieldController writes TrainStateCache before firing Signals.OnTrainShieldChanged, so the monitor sees the same snapshot whether it reads the cache at init or the signal fires while it's already running.

The zoom view​

StarterGui.TrainShieldGui is a ScreenGui with ResetOnSpawn = false, so the PlayerGui copy survives respawns and is resolved exactly once at startup. The controller forces Enabled = false at init regardless of how the asset was saved.

The TrainConfig.SHIELD_ZOOM_PROMPT_PART_NAME prompt on each ShieldConsole opens it; its MainContainer.CloseButton closes it. While the panel is up every zoom prompt is disabled, so the Close button is the only exit and a held key can't retrigger the prompt sitting underneath the panel. The render loop skips the zoom view entirely while it is hidden, and stats are re-applied on open so a panel opened after a buff change is never stale.

Opening fires Signals.RequestMouseIcon(true) on PC (UserInputService.MouseEnabled and KeyboardEnabled), which is what makes the Close button clickable — the third-person camera otherwise holds MouseBehavior = LockCenter with the icon hidden. CameraController is the sole owner of those properties; this controller never writes them directly, so shift-lock and aim mode stay the single arbiter and aim mode still outranks the request. See Camera — Modes and the Signals Map.

The panel is modal, so setHudHidden clears the rest of the HUD under it. That takes three switches, because no single one covers everything:

SwitchHides
StarterGui:SetCore("TopbarEnabled", false)Roblox's topbar and every CoreGui it owns — chat, leaderboard, menu button
Satchel:SetBackpackEnabled(false)The hotbar and inventory
TopbarPlus.setTopbarEnabled(false)Satchel's inventory icon

The middle one is the easy mistake: SetCoreGuiEnabled(Enum.CoreGuiType.Backpack, false) does nothing here, because Satchel already called it at boot and draws its own hotbar. Satchel re-applies its own flag every Heartbeat, so the hotbar cannot flip back on while the panel is up. Disabling it also unbinds the number-key hotbar actions, so tools can't be swapped through the panel. The third is needed because TopbarPlus icons live in developer ScreenGuis that TopbarEnabled never reaches.

Satchel and TopbarPlus are required inside the zoom setup task after the Close button is wired, not at the top of the file — requiring Satchel boots the entire backpack UI and can yield, and neither the diegetic monitor nor the panel's exit should wait on that. SetCore is pcall'd because it errors if the CoreGui has not registered the callback yet.

One caveat from the engine: with TopbarEnabled false, the strip the topbar occupied still captures mouse events, so a button placed in the top 36 px of the panel will not respond to clicks. Keep interactive elements clear of it.

Studio setup​

Each ShieldConsole-tagged root (Model or BasePart) carries two prompt parts, each a BasePart with a child ProximityPrompt, resolved recursively via PromptResolver:

Config fieldPart namePrompt does
SHIELD_PROMPT_PART_NAMEInsertFuelPromptPartSpend pool Energy to recharge (TrainShieldController → ReqRechargeShield)
SHIELD_ZOOM_PROMPT_PART_NAMEOpenMonitorGuiPartOpen the full-screen readout (TrainShieldGuiController)

Give the two prompts distinct ActionText — both shipped as Interact / Shield Generator, which is indistinguishable in game. Multiple consoles are supported, each registered independently.

Tag every BasePart that should display a monitor with TrainConfig.SHIELD_MONITOR_TAG. Element names in both assets — ReplicatedStorage.GuiAssets.TrainShieldGui (the SurfaceGui template) and StarterGui.TrainShieldGui (the zoom ScreenGui) — are load-bearing and must match each other: TrainShieldGuiController resolves one shared path set with WaitForChild and will hang on startup if either asset renames or re-nests anything under MainContainer.SafeContainer. Tag the train's structural model with TrainConfig.CORE_TAG ("TrainCore") — currently unused by TrainShieldManager but reserved for future combat systems.

Never tag a MeshPart as the monitor. A SurfaceGui adorns its part's bounding box face, not the mesh geometry, and its orientation is the part's CFrame — so a screen that is inset, curved, or tilted inside its bounding box will have the GUI floating in front of it at the wrong angle, with no way to correct it short of rotating the visible mesh. Instead add an invisible flat Part (Transparency = 1, CanCollide/CanQuery/CanTouch off, ~0.05 thick) aligned to the real glass plane and nudged ~0.02 studs out to avoid z-fighting, then tag that. Workspace.Monitor is the reference case: Monitor_Screen's glass is a flat slab leaning back ~31.6°, so the tag lives on a sibling ScreenSurface part instead — 7.5877 × 4.8854 studs, aspect ~1.553 (canvas 3885 × 2501 at PixelsPerStud 512), sat exactly 0.02 studs proud of the glass along its own normal to avoid z-fighting.

That height is not the glass's bounding-box height. The glass leans back ~31.6°, so its extent along its own plane is 4.1067 / cos(31.6°) ≈ 4.82 studs — a surface matched to the bounding box would cover only 85% of the visible glass. The current size covers the full slab. Note it deliberately covers more than the unoccluded aperture: raycasting a grid at the glass with every opaque part of the model as a target shows the bezel opening is rounded, not rectangular, so the extreme corners of this rectangle sit over the CRT bulge. Keep GUI content inside the middle ~90% rather than shrinking the surface — a strictly inscribed rectangle covers only 44% of the glass and reads as far too small.

Because every element is Scale-sized, changing the surface ratio silently stretches all of them rather than letterboxing. Re-check the layout after any resize, and keep the zoom ScreenGui's UIAspectRatioConstraint in step with it so the two copies don't drift apart.

Gotchas​

Font width drives text sharpness, not just PixelsPerStud

Every label on the monitor is TextScaled inside a Scale-sized box, so the font's width per character sets the rendered type size — a wider face is scaled further down to fit the same box. Michroma measures ~31.6px/char against ~21 for a normal sans (measured via TextService:GetTextBoundsAsync at size 48), so it rasterised the small readouts at roughly 20px, where its uniform hairline stems alias into the "no anti-aliasing" look.

The fix was two levers that multiply: PixelsPerStud raised 256 → 512 (canvas 3885×2501 at the current surface size; safe because the layout is entirely Scale-based, so nothing reflows), and the small readouts — ShieldStatus and the ShieldStatsContainer labels — moved to Sarpanch Bold. Michroma is kept for the large display text (ShieldValue, Title), which is big enough to carry it. Apply the same rule to any label added later: if it renders small, it is not a Michroma label.

Michroma is a single-face family — GetTextBoundsAsync returns identical metrics for Regular, Medium, Bold and Heavy — so a FontWeight.Bold on a Michroma label does nothing. Those were reset to Regular. Sarpanch does ship a real Bold, which is why the small labels use it. And do not reach for AlwaysOnTop to sharpen text (the API docs suggest it helps on high-DPI displays): it renders over 3D geometry, so the GUI would draw straight through the monitor bezel.

LightInfluence must stay at 0

The monitor has to stay readable across every biome, including night and interior ones. SurfaceGui.LightInfluence is 0 on the template, meaning environmental lighting has no effect and the CRT renders its authored colours everywhere. Any value above 0 tints the screen toward ambient and makes it dim exactly where visibility matters most. Brightness (emissive scaling, only active while LightInfluence is 0) is left at 1; raising it blows out the thin strokes on the display text. This applies only to the SurfaceGui — the zoom ScreenGui is drawn in screen space and is unaffected by world lighting either way.

The template's Adornee is cleared on every clone

A SurfaceGui with a non-nil Adornee renders on that instance and ignores its parent, so an Adornee saved into GuiAssets.TrainShieldGui propagates to every clone and the monitor renders nowhere — silently, with no error. This bit the project once already, when the template kept a reference to the deleted placeholder generator. TrainShieldGuiController now sets gui.Adornee = nil after cloning, so the asset can be re-authored on any part without breaking the monitor.

Three upgrade stats are displayed but not yet enforced

STRENGTH RATING, SHIELD EFFICIENCY and AUTO-REGENERATION render from ResearchBuffs attributes that nothing writes yet — the Tech Tree has no node for any of them — so they always read B, 0 % and BROKEN. Crucially, the server doesn't read them either: ApplyDamage applies full damage, handleRecharge adds a flat SHIELD_PER_POINT per point, and SHIELD_REGEN_ENABLED is still false.

Wiring one up is therefore two edits, and both are required or the monitor will advertise a buff the server never applies:

  1. A ResearchConfig node with Effect = { Type = "StatBuff", Key = <the matching TrainConfig key>, PerLevel = … } — ResearchEffectsDispatcher accumulates any StatBuff key, so no dispatcher change is needed. This alone moves the readout.
  2. The corresponding read in TrainShieldManager — scale the hit in ApplyDamage, scale value in handleRecharge, or implement the regen loop.

The controller and TrainConfig need no change either way; that is the point of routing the display through named buff keys instead of hardcoding the stock strings.

Recharge mutex is not a queue

isRecharging is a boolean, not a queue. A second recharge request while one is in-flight returns SHIELD_FULL or NO_ENERGY — not a queued success. The player can try again immediately after.

Pre-game freeze

hasStarted is false until Signals.SetTrainStarted fires (the first brake release on the fuel side). ApplyDamage is a no-op until then.

Passive regen is off by default

SHIELD_REGEN_ENABLED = false and SHIELD_REGEN_PER_SEC = 0. No regen loop exists yet. To add passive regen, implement a RunService.Heartbeat-based loop in TrainShieldManager gated on SHIELD_REGEN_ENABLED, and update this page and the config map.

Shield depletion is no longer a game over

The shield can sit at 0 indefinitely; only fuel reaching 0 (natural stall-out or combat bleed-through) ends the round. See Train Fuel — game-over reasons.

typeof guard on OnServerInvoke

ReqRechargeShield.OnServerInvoke receives (player, console) where console is client-supplied. A typeof(console) == "Instance" guard runs before acquiring the isRecharging lock, so a malformed invocation (nil or non-Instance) is rejected cleanly without erroring.

Data flow​

sequenceDiagram
    participant Sv as TrainShieldManager
    participant Cl as TrainShieldController
    participant Cache as TrainStateCache
    participant Gui as TrainShieldGuiController

    Note over Sv,Cl: JOIN - via JoinSync on ClientReady, not PlayerAdded
    Sv->>Cl: TrainShieldSync(currentShield, maxShield)
    Cl->>Cache: SetShield(current, max)
    Cl->>Cl: Signals.OnTrainShieldChanged(current, max)
    Gui->>Cache: ShieldFraction() every RenderStepped; ShieldMax() on the signal

    Note over Cl,Sv: RECHARGE
    Cl->>Sv: ReqRechargeShield(console)
    Sv->>Sv: isRecharging mutex, validate tag + proximity
    Sv->>Sv: MaterialPool.SpendUpTo("Energy", missing, SHIELD_PER_POINT)
    Sv-->>Cl: (success, shieldAdded, code)
    Sv->>Cl: TrainShieldSync(...)

    Note over Sv: DAMAGE (future combat/hazard caller)
    Sv->>Sv: ApplyDamage(amount, source) - guard hasStarted, not HasFired, amount>0
    alt currentShield > 0
        Sv->>Sv: currentShield = max(0, currentShield - amount); broadcast()
    else currentShield == 0
        Sv->>Sv: TrainFuelManager.ApplyFuelDamage(amount * FUEL_DAMAGE_FACTOR, source)
    end

    Note over Sv: BUFF CHANGE
    Sv->>Sv: ResearchBuffs.MaxHP or PartyPerkBuffs.TrainShieldBonus changes
    Sv->>Sv: recomputeMax() - ratio-preserving rescale, broadcast()

    Note over Gui: SHIELD READOUT (RenderStepped, every view)
    Gui->>Cache: ShieldFraction() - nil until first snapshot -> placeholder
    Gui->>Gui: displayedShieldPct eased; pickBand() -> colour, HEALTHY/WARNING/DANGER, image swap

    Note over Gui: UPGRADE STATS (event driven, not per frame)
    Gui->>Cache: ShieldMax() / BASE_SHIELD -> SHIELD CAPACITY
    Gui->>Gui: ResearchBuffs.AttributeChanged -> strength / efficiency / auto-regen
