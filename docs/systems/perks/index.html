Perks

A level-driven permanent progression system, backed by ProfileStore, that lets players spend points on persistent buffs. Two independent point pools — Personal (buffs the owner only) and Party (buffs resolved as the server-max across all players) — each grow by exactly 1 point per XP level; points are derived, never stored. Every perk must be unlocked — a level gate plus a one-time coin + point cost — before points can be spent on it — see Unlock gate. Respec is free to initiate and, unlike leveling, also re-locks and refunds unlocked perks. Structured shared/server/client exactly like Quests and Battle Pass.

How it works​

Point economy​

  • Each level-up grants 1 Personal point AND 1 Party point.
  • Available points = playerLevel - spent, computed by PerkState.available — points are never stored directly. spent = the pool's perk levels plus the UnlockPointCost of every unlocked perk in that pool.
  • Points cannot go negative; the pool is floored at 0.
  • Respec costs nothing and returns all points in the chosen pool — level points and unlock points alike — and also re-locks each unlocked perk in that pool and refunds its UnlockCost in coins (see Unlock gate).
  • Points carry across places because PerkManager uses the same DataStore key (PlayerPerks) everywhere in the universe.

PerkConfig.Perks is the single tuning surface: 12 perk declarations with Category, BuffKey, PerLevel, MaxLevel, DisplayName, Description, display Order, an optional ValueKind, and per-perk UnlockCost/UnlockLevel/UnlockPointCost.

ValueKind controls GUI effect-string formatting in PerkClient.effectFor: nil/"percent" (the default, every perk except Net Cast) renders Description's %d as the whole-percent bonus (floor(PerLevel * level * 100 + 0.5)); "count" (Net Cast only) renders %d as a raw total, baseline 1 plus the bonus (1 + floor(PerLevel * level + 0.5)) — so "Grab up to %d junk at once" reads "Grab up to 3 junk at once" at level 2 (1 baseline + 2 bonus), not a percent.

Unlock gate​

Every perk declares an UnlockLevel (player level) gate plus a one-time cost in PerkConfig: UnlockCost (coins) and UnlockPointCost (points from the perk's own pool — Personal points for Personal perks, Party points for Party perks). The level is the first wall; once reached, the player pays coins + points. Unlock points count toward spent, so Respec returns them with no stored counter. A perk with all three at 0 is a free starter, auto-unlocked: PlayerHP (Vitality) and JunkRarity (Salvage Luck).

Unlock is permanent: it persists on the PlayerPerks profile as an Unlocked map ({ [perkId]: boolean }), alongside PerkLevels and a PerkSchemaVersion guard.

function PerkManager.UnlockPerk(player: Player, perkId: string): (boolean, number)

UnlockPerk validates with PerkState.canUnlock (order: UNKNOWN_PERK → ALREADY_UNLOCKED → LEVEL_REQUIRED → NO_POINTS → NOT_ENOUGH_COINS), deducts UnlockCost via CoinManager.DeductCoins, marks the perk unlocked (which spends UnlockPointCost — points are derived), and replicates. Allocating a point on a locked perk returns PERK_LOCKED (PerkState.canAllocate checks unlocked[perkId] before the level/point checks). The frozen enum (PerkResultCodes) shared by server and client:

CodeValueMeaning
OK0Success
NO_PROFILE1Profile not loaded
UNKNOWN_PERK2Perk id not in PerkConfig
AT_MAX_LEVEL3Already at MaxLevel
NO_POINTS4Pool can't pay (allocate: < 1; unlock: < UnlockPointCost)
PERK_LOCKED5Perk not yet unlocked

LEVEL_REQUIRED7Below UnlockLevel
NOT_ENOUGH_COINS8Below UnlockCost
NOTHING_TO_RESET9Per-perk respec on a perk at level 0 that is locked or a starter

Unlocking a perk changes no buffs (its level is still 0), so PerkManager.UnlockPerk does not fire Signals.OnPerkStateChanged; PerkEffectsDispatcher is untouched by an unlock.

Migration: the first load after this shipped wipes all existing PerkLevels/Unlocked once (clean slate — derived points return automatically), guarded by PerkSchemaVersion < 1 (then set to 1) so it fires exactly once per profile. migrateAndSeed re-seeds starters immediately after so play never begins with zero unlocked perks. UnlockPointCost shipped with no migration: a pre-release profile that unlocked perks under the coin-only rule may read 0 available points until it respecs.

Respec (PerkManager.Respec) fully resets the chosen pool: it clears PerkLevels and Unlocked for every perk in that pool, refunds each unlocked perk's UnlockCost via CoinManager.RefundCoins — an exact, un-inflated refund, not scaled by the Fortune perk's CoinGainBonus (unlike CoinManager.AddCoins) — then re-seeds free starters so the pool isn't left fully locked. Level points and unlock points return automatically because points are derived.

Per-perk respec (PerkManager.RespecPerk, packet ReqRespecPerk) resets ONE perk: validated by PerkState.canRespecPerk (UNKNOWN_PERK → NOTHING_TO_RESET), it clears that perk's level and — unless it is a starter — re-locks it and refunds its exact UnlockCost. Starters keep Unlocked and refund nothing. It fires OnPerkStateChanged (buffs change) and replicates. The starter rule itself lives in one place, PerkState.isStarter (all of UnlockCost, UnlockLevel, UnlockPointCost are 0/nil), used by both seedStarters and the respec checks.

The client-facing PerkView descriptor (PerkClient.luau) carries IsUnlocked, UnlockCost, UnlockLevel, and MeetsUnlockLevel fields. PerkClient.Unlock(perkId) is the fire-and-forget command that sends ReqUnlockPerk; reconciliation arrives via the next PerkStateSync.

Party-max resolution​

Party perks (Salvage Luck, Fuel Efficiency, Thrift, Shield Capacity, Heavy Ordnance) apply to the entire server, but only the highest level held by any single player is active. If Player A has Salvage Luck 6 and Player B has Salvage Luck 3, the server resolves at 6. PerkEffectsDispatcher recomputes the max on every allocate, respec, player join, and player leave.

Buff contract​

PerkEffectsDispatcher is the sole writer of the buff folders — every other system reads, never writes. It listens to Signals.OnPerkStateChanged, PlayerAdded, and PlayerRemoving, then calls publishPersonal (per-player attributes) and publishParty (server-max across all players). It also bridges Junk Rarity to Signals.ApplyTierMultiplier, which JunkService already consumes. PerkManager.GetPerkLevels(player) returns the live reference PerkEffectsDispatcher reads from.

Armor damage mitigation​

Crafted armor (see Armor / ArmorConfig / ArmorManager) is the base of this mitigation, not the perk. HealthManager's damage sink calls ArmorManager.Absorb(player, amount, efficiency), passing the player's ArmorEfficiency perk bonus read fresh on every hit. The Armor perk does not reduce damage on its own; it's an efficiency multiplier on the equipped kind's BaseReduction, applied identically whether the worn kind is Ballistic or Energy:

reduction = clamp(kind.BaseReduction * (1 + ArmorEfficiency), 0, ArmorConfig.MaxReductionCap)

Absorb scales amount by (1 - reduction) as the final step before it reaches health, and drains the worn kind's pool by whatever was absorbed — mitigation and pool drain happen in the same call, because the two cannot be split without the pool going stale (see Armor — Mitigation). With nothing equipped, or an Energy kind at zero pool, the perk contributes nothing. Because the attacker's DamageBonus is already applied upstream in WeaponServer, attacker bonus and defender mitigation multiply independently: base * (1 + DamageBonus) * (1 - reduction). Coverage is every path routed through CombatService/HealthManager (Bullet/AOE and NPC hits); damage written directly to Humanoid.Health bypasses the sink and is not mitigated (see Health).

Client​

PerkClient.luau is the GUI-agnostic data layer (owns no GUI). It caches the authoritative PerkStateSync snapshot (perkLevels, unlocked, personalAvailable, partyAvailable, playerLevel) and watches the replicated PartyPerkBuffs folder. Queries return PerkView descriptors via GetPerks/GetActivePerks/GetAvailablePoints/GetPerk. Commands: optimistic-prediction Allocate/Respec/CanRespec, plus Unlock(perkId) (no optimistic coin prediction — the server owns the balance; the next PerkStateSync reflects success or failure), and a Changed signal fired on every snapshot update.

"Active" is category-aware: a Personal perk is active at the player's Level > 0; a Party perk is active at its server-wide ActivePartyLevel > 0. PerkView also carries UnlockPointCost, NextEffectText (the effect at Level + 1, nil at max), CanRespec (this perk alone can be reset), and for Party perks ActivePartyHolder: Player? (from <BuffKey>HolderId). PerkClient.RespecPerk(perkId) sends ReqRespecPerk; PerkClient.CanRespec(category) is true when a pool respec would change anything — a level spent or a refundable (non-starter) unlock. PerkController.client.luau is the one-line bootstrap that calls PerkClient.Init() once on join so the data layer is warm before any GUI opens.

Perk menu. PerkUpgradeGuiController.client.luau binds the Studio-authored StarterGui.PerkUpgradeGui. It opens and closes from a TopbarPlus "Perks" icon (toggle key P; the icon's selection is the single source of truth, and CloseButton deselects it). It never builds layout — it clones the authored examples:

  • List (TechScrollingFrame, filtered by the Personal / Party tabs): unlocked perks, locked perks the player is high enough to buy, and locked perks at the next level milestone (the lowest UnlockLevel above the player's level, across both pools) as a preview. Perks further out stay hidden, so the list stays short as perks are added.
  • Unlocked card (ExampleItem1 clone): effect text and LV n/max (MAX at the cap). Locked card (ExampleItem3 clone): level-1 effect, coin + point price (red when short), and a red "Requires Lv N" line on milestone previews.
  • Detail panel: current and next effect, CURRENT LEVEL: n/max, and ActionContainer.UpgradeButton — REQUIRES LV N / NEED POINTS / NEED COINS / UNLOCK / MAXED / NO POINTS / UPGRADE. Only UNLOCK (PerkClient.Unlock) and UPGRADE (PerkClient.Allocate) act. Button gating blocks doomed requests; there are no error toasts — the next PerkStateSync reconciles a server rejection.
  • Reset: ActionContainer.RespecButton is a hold-to-reset (see below) for the selected perk → PerkClient.RespecPerk; enabled when view.CanRespec.
  • Header: coins (cached from Signals.OnCoinsChanged) and Personal / Party points, dot-grouped like the authored 10.000.000.

Active Perks menu. ActivePerksGuiController.client.luau binds the Studio-authored StarterGui.ActivePerksGui, a read-only view. It opens from a TopbarPlus "Active Perks" icon (toggle key O); TopbarPlus deselects other icons by default, so it and the Perk menu never stack. Personal / Party tabs filter PerkClient.GetActivePerks(tab) into PerkContainer (clones of ExampleItem). The detail panel shows the name, Level N (Party: the active server level), one effect line, PerkOwner (Personal: you; Party: ActivePartyHolder, hidden when nil), and PerkConfig.CategoryBlurb (all under BottomSection.RightContainer.InfoContainer). A tab with nothing active hides the detail panel. RightContainer.ResetPersonalPerksButton is a hold-to-reset for the open tab's pool → PerkClient.Respec(tab); enabled when PerkClient.CanRespec(tab), its authored #CATEGORY placeholder replaced with the tab name.

Hold-to-reset. HoldButton.luau drives both reset buttons. Each button holds a Studio-authored HoldFill (Frame, 7F639F) with a UIGradient whose transparency has a hard edge at 0.5, and a Label (the button's own Text is empty; UIPadding / UITextSizeConstraint live on the Label so the fill spans the button). Pressing sweeps the gradient Offset from (-0.5, 0) to (0.5, 0) over PerkConfig.RESPEC_HOLD_TIME (MotionMaster, linear). Releasing anywhere, closing the menu, or changing the selection / tab cancels and empties the fill. A disabled button dims its Label and ignores presses.

Gotchas​

Points are derived, not stored

Available points are never stored directly — only PerkLevels, Unlocked, and PerkSchemaVersion persist. Available points = level - spent. Never add a separate stored point counter — it will desync.

Party perk levels shown in the GUI are per-player, not the resolved active level

A Party card's LV n/max and the detail panel's CURRENT LEVEL show how many points this player has invested. The Active Perks menu shows the server-resolved max. Both are expected: a player at level 3 in a party where someone else is at level 7 sees the card at LV 3/10 and Level 7 for Salvage Luck in the Active Perks menu.

PerkEffectsDispatcher must run before PerkManager on join

PerkEffectsDispatcher seeds its folder at boot. PerkManager fires OnPerkStateChanged after profile load, which triggers a republish. The ordering is correct because both are ServerScriptService scripts and PerkManager.Initialize() is called from PerkSystemLoader, which yields on ProfileStore:StartSessionAsync before firing the signal.

HPBonus subscription attaches once at join

HealthManager subscribes to the HPBonus attribute change in PlayerAdded, not CharacterAdded. If PerkBuffs/<UserId> does not exist at join time (the dispatcher hasn't seeded yet), the subscription is skipped for that session. In practice the dispatcher seeds synchronously at boot, so the folder exists before any player's PlayerAdded fires normally.

Data flow​

sequenceDiagram
    participant Client as PerkController (client)
    participant Manager as PerkManager (server)
    participant Dispatcher as PerkEffectsDispatcher (server)

    Note over Manager: JOIN
    Manager->>Manager: profile loaded (migrateAndSeed: one-time wipe + seedStarters)
    Manager->>Client: PerkStateSync(levels, unlocked, personalAvail, partyAvail, playerLevel)
    Client->>Client: perkLevels / unlocked / available updated; repaint()
    Manager->>Dispatcher: publish personal buffs (0s); publishParty()

    Note over Client,Manager: UNLOCK
    Client->>Manager: ReqUnlockPerk(perkId)
    Manager->>Manager: UnlockPerk — canUnlock (level+points+coins) then DeductCoins then Unlocked[perkId]=true
    Manager->>Client: PerkStateSync (no OnPerkStateChanged fired — buffs unchanged)
    Manager-->>Client: (success, reasonCode)

    Note over Client,Manager: ALLOCATE
    Client->>Client: optimistic level++, avail--; repaint()
    Client->>Manager: ReqAllocatePerk(perkId)
    Manager->>Manager: AllocatePoint — canAllocate then mutate
    Manager->>Dispatcher: Signals.OnPerkStateChanged:Fire(player)
    Manager->>Client: PerkStateSync(levels, unlocked, ...)
    Client->>Client: reconcile to authoritative state; repaint()
    Dispatcher->>Dispatcher: publishPersonal(player); publishParty()
    Manager-->>Client: (success, reasonCode)

    Note over Manager: LEVEL UP
    Manager->>Manager: XPManager level increases; Signals.OnPlayerLevelUp:Fire(player, newLevel)
    Manager->>Client: PerkStateSync(levels, unlocked, personal+1, party+1, newLevel)
    Client->>Client: repaint() — new points visible
