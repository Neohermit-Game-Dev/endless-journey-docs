Settings (User Preferences)

A generic, server-authoritative user-preferences system. Every persisted preference — the four audio bus volumes (MasterVolume, MusicVolume, SFXVolume, AmbienceVolume) and CameraSensitivity today, anything else in the future — is one entry in a single typed registry, validated by one shared schema, and synced/saved through one packet pair. There is no per-setting packet, no per-setting DataStore key, and no bespoke client-side state machine; adding a setting is a config-table edit, not a new subsystem.

At a glance​

How it works​

Config & schema​

SettingsConfig is pure data with no client dependencies, so the server can require it directly. SettingsConfig.Definitions is the single registry — one entry per setting key, typed as:

export type Definition = {
    type: "number" | "boolean" | "enum",
    default: any,
    category: string,
    label: string,
    order: number,
    min: number?,
    max: number?,
    step: number?,
    options: { string }?,
}

SettingsConfig.GetDefaults() returns a fresh { [string]: any } map of every key to its default — this seeds both a brand-new ProfileStore profile and profile:Reconcile() for existing ones. SettingsConfig.VolumeBusByKey maps the four volume setting keys to their SoundConfig/Groups bus name (Master, BGM, SFX, Ambience) — the one place that mapping is declared, reused by both the migration step and SettingsAppliers. SettingsConfig.STORE_NAME ("PlayerSettings") is the ProfileStore name and must not change without a migration plan, since it is also where the legacy Volumes table is read from.

SettingsSchema is the single validator, called identically by server and client so the two sides can never disagree on what's valid. SettingsSchema.Validate(key, value): (boolean, any) looks key up in Definitions (unknown key is rejected, acting as an allowlist); for "number" it rejects non-numbers/NaN then clamps to [min, max]; for "boolean" it requires an exact boolean; for "enum" it requires membership in options. SettingsSchema.Sanitize(map) builds a complete settings map from GetDefaults() overlaid with every entry in map that passes Validate — anything invalid or no longer in the registry is silently dropped.

Server authority​

SettingsManager owns one ProfileStore session per player (PlayerStore:StartSessionAsync(tostring(player.UserId), ...)), following the same lifecycle pattern as CoinManager/XPManager: it kicks the player if the session fails to start, ends the session and re-kicks on OnSessionEnd, and ends the session on PlayerRemoving.

On join, before profile:Reconcile() runs, migrateLegacyVolumes(profile) does a one-time, idempotent copy: for every key in VolumeBusByKey, if Settings[key] is unset and the legacy profile.Data.Volumes[bus] is a valid number, it's validated and copied into Settings[key]. Once a key exists in Settings it is never overwritten from Volumes again, so this is safe to leave running indefinitely. The legacy Volumes table itself is left in place (not cleared) after migration.

SettingsManager.Initialize() — called once per server by SettingsSystemLoader.server.luau — wires Packets.SaveSetting.OnServerEvent: it looks up the player's profile (drops the message if none), checks key is a string, re-validates (key, value) through SettingsSchema.Validate, and on success writes profile.Data.Settings[key] = coerced. There is no explicit save call — ProfileStore autosaves the profile. Any invalid or unknown-key message is silently dropped.

Client API​

SettingsClient — initialized once via SettingsController.client.luau calling SettingsClient.Init() at startup — is the only module the settings GUI talks to. It holds a local cache of every setting's current value and exposes Get(key), Set(key, value): boolean, GetAll(), GetDefinition(key), and GetByCategory() (every definition grouped by category and sorted by order; today: "Audio" with 4 entries, "Controls" with 1, CameraSensitivity).

Internally, applyAndNotify(key, value) is the shared path for both the join-sync handler and Set: it writes the cache, calls SettingsAppliers.Apply(key, value), then fires Signals.OnSettingChanged:Fire(key, value). The join-sync path calls only applyAndNotify (never scheduleSave), which is what prevents applying the server's own synced values from looping back into another save. scheduleSave(key, value) debounces persistence per key: the latest value is stashed in a pending table, and a single task.delay(0.25, ...) per key sends the trailing value via Packets.SaveSetting:Fire(key, value) — rapid changes (e.g. dragging a volume slider) collapse into one network send 0.25s after the drag settles.

Client appliers​

SettingsAppliers is a client-only key -> (value) -> () registry, kept deliberately separate from SettingsConfig so the shared config module stays free of client-only dependencies (Groups, UserSettings()) that the server must never require. The four volume keys are wired generically by iterating VolumeBusByKey and calling Groups.SetVolume(bus, value) — see Sound for the underlying SoundManager.SetVolume/GetVolume primitives; persistence lives here, not in SoundManager. Apply(key, value) looks up and calls the applier for key, or no-ops silently if the key has no client-side effect — CameraSensitivity is a deliberate example of the no-entry-needed case: it has no applier because CameraController reads it directly via SettingsClient.Get("CameraSensitivity") at startup and stays live via Signals.OnSettingChanged (see Camera).

Adding a new setting​

Two steps, at most:

  1. Add one entry to SettingsConfig.Definitions — a unique key, a type ("number" | "boolean" | "enum"), a default, a category + label for the GUI, an order within that category, and the relevant bounds (min/max/step for "number", options for "enum"). That's enough for the setting to round-trip end to end: it seeds into new profiles, syncs on join, validates, and persists.
  2. If the setting has a direct client-side effect, add a matching entry to SettingsAppliers's appliers table — a one-argument function that applies value. Skip this step for settings with no client effect.

No packet, schema, or ProfileStore change is needed for a new setting — SettingsSchema.Validate and SettingsManager are fully generic over the Definitions table.

Gotchas​

Never call SettingsAppliers or SettingsManager's internals directly

GUI code should only ever call SettingsClient.Get/Set/GetAll/GetDefinition/GetByCategory and listen to Signals.OnSettingChanged. Calling SettingsAppliers.Apply directly skips validation, caching, and persistence — the value will apply visually but never save and will be wiped out by the next join-sync. SettingsManager is server-only and cannot be called from client code; firing Packets.SaveSetting directly skips client-side validation and the cache, desyncing SettingsClient.Get from what the server actually has.

  • The join-sync path never re-saves. SettingsClient.Init()'s SyncSettings handler calls applyAndNotify directly, not Set — applying the server's own synced values must never re-fire a save back to the server in a feedback loop.
  • SettingsManager.Initialize() re-validates every SaveSetting message. A modified or out-of-date client can fire any (key, value) pair; the server drops anything that fails SettingsSchema.Validate rather than trusting the client's own clamping.
  • Legacy Volumes data is migrated, not deleted. migrateLegacyVolumes copies old per-bus volumes into the generic Settings map once, but the old Volumes table is left on the profile afterward. Don't write new code that reads profile.Data.Volumes.
  • Removing a Definitions entry doesn't delete saved data, but does stop syncing it. SettingsSchema.Sanitize drops any key no longer present in Definitions, so a removed setting simply disappears from SyncSettings/GetAll going forward — it does not actively scrub the old key from the ProfileStore document.
  • CameraSensitivity scales GetMouseDelta(), not an engine property. UserGameSettings.MouseSensitivity is gated behind the RobloxScript capability (CoreScript-only) and throws if a game LocalScript writes it. UserInputService.MouseDeltaSensitivity is settable but only scales GetMouseDelta() consumers — it would have had no effect on the old default Roblox camera, which didn't consume GetMouseDelta() for look/rotation at all. That constraint is why CameraController is a fully script-owned Scriptable camera that reads raw GetMouseDelta() and scales it by CameraConfig.MouseLookBaseSpeed * sensitivity itself. See Camera.

Data flow​

sequenceDiagram
    participant Player
    participant SM as SettingsManager
    participant SC as SettingsClient
    participant Appliers as SettingsAppliers

    Note over SM: Join
    Player->>SM: onPlayerAdded
    SM->>SM: PlayerStore:StartSessionAsync ("PlayerSettings")
    SM->>SM: migrateLegacyVolumes(profile) - idempotent Volumes -> Settings copy
    SM->>SM: profile:Reconcile() - fill missing keys from GetDefaults()
    SM->>SM: SettingsSchema.Sanitize(profile.Data.Settings)
    SM->>SC: Packets.SyncSettings(settings)
    SC->>SC: for each key: SettingsSchema.Validate -> applyAndNotify
    SC->>Appliers: SettingsAppliers.Apply(key, value)
    SC-->>SC: Signals.OnSettingChanged(key, value) - no re-save

    Note over SC: Manual change (GUI calls SettingsClient.Set)
    Player->>SC: SettingsClient.Set(key, value)
    SC->>SC: SettingsSchema.Validate(key, value)
    SC->>Appliers: SettingsAppliers.Apply(key, coerced) - immediate local effect
    SC-->>SC: Signals.OnSettingChanged(key, coerced)
    SC->>SC: scheduleSave(key, coerced) - debounced 0.25s
    SC->>SM: Packets.SaveSetting(key, coerced)
    SM->>SM: SettingsSchema.Validate(key, value) - server re-validates, never trusts client
    SM->>SM: profile.Data.Settings[key] = coerced - ProfileStore autosaves
