Research Bench

A cooperative, server-wide, session-only (no DataStore) research system replaces the old Tech Tree. Players pay materials up front to enqueue a node's next level at one fixed bench; a single active job advances over real time, gated by a shared fuel reserve that only drains while a job is progressing. Nodes are leveled (1..MaxLevel, each level re-payable and re-timed) rather than binary unlocks, and a node with no Effect is a pure recipe node — it exists only to gate a Workbench recipe via the ResearchUnlocked folder.

How it works​

Core loop​

  1. Enqueue — player spends materials immediately (pay-on-enqueue, not pay-on-complete) to queue the next level of an eligible node. If nothing is active, the job just enqueued starts immediately.
  2. Advance — a server tick burns bench fuel and advances the active job's elapsed time. Progress pauses whenever fuel hits 0; it resumes the instant fuel is added back.
  3. Complete — when elapsed >= duration, the node's level is recorded, Signals.OnResearchLevelUp fires, and the next queued job (if any) becomes active.
  4. Refuel — a player feeds a held Energy tool into the bench via a second ProximityPrompt; the tool's tier maps to a fuel amount (ResearchConfig.EnergyFuelValue).
  5. Cancel — a player cancels a specific level of a node (queued or active); see Cascade-cancel — this is the trickiest part of the system.

Because there is one shared queue and one shared fuel pool for the whole server, this is explicitly a co-op system: any player at the bench can enqueue, cancel, or refuel, and progress benefits everyone.

Leveled nodes vs. recipe nodes​

Every entry in ResearchConfig.Nodes is a Node with MaxLevel and a Levels table ({ [1] = {Cost, Duration}, [2] = ..., ... }, one entry per level). Two shapes exist:

  • Leveled upgrade nodes have an Effect ({Type = "StatBuff", Key, PerLevel} or {Type = "FuelEfficiency", DrainPerLevel}). Each completed level contributes to a running total recomputed by ResearchEffectsDispatcher (see Buff/unlock folders).
  • Recipe nodes have Effect = nil. Completing level 1 (recipe nodes are always MaxLevel = 1) writes only a ResearchUnlocked/<nodeId> BoolValue; there is no buff to compute. The shipped example is RepeaterRifle, which demonstrates the shape of a pure recipe node but has no Workbench recipe wired to it yet in the shipped WorkbenchConfig. The one recipe gate actually in use — CraftSMG's RequiresNode = "Durability_T1" — instead points at a leveled StatBuff node, showing that any node id can gate a recipe, not just Effect = nil ones. See Workbench Crafting for the consumer side.

A node may declare Prereq (another node's id) and PrereqLevel (default 1) — the prereq node must have reached at least that level before this node accepts enqueues (ResearchState.isEligible).

Cascade-cancel​

Cancelling is keyed by (nodeId, fromLevel) — the target level of the specific job the player clicked Cancel on (the active job's targetLevel, or a specific queued row's targetLevel). ResearchState.cancel does not cancel just that one job:

  • Every queued job of the same node with targetLevel >= fromLevel is removed and its full cost refunded (fraction 1.0 — no penalty).
  • If the active job belongs to the same node and active.targetLevel >= fromLevel, it is cancelled too, and its cost is refunded at ResearchConfig.ACTIVE_REFUND_FRACTION (0.5 — the "partial progress lost" penalty). If the active job was cancelled, the next queued job (of any node) immediately becomes active with elapsed = 0.

The reasoning: levels are sequential and dependent — you cannot legally hold "Durability_T1 level 3" without level 2 and level 1 having already resolved (pendingLevel stacks consecutively). Cancelling a lower level therefore must also cancel every already-queued higher level of that node, or the queue would contain an orphaned level 3 with no level 2 underneath it.

Concretely, with Durability_T1 active at level 1 and level 2 queued behind it:

  • Cancelling from level 1 (the active job's row) cancels both: the active level-1 job gets 50% of its cost back, the queued level-2 job gets 100% back, and the queue's next job (if any, possibly for a different node) starts immediately.
  • Cancelling from level 2 (the queued row) cancels only the queued level-2 job (100% refund) — level 1 keeps advancing untouched, because active.targetLevel (1) >= fromLevel (2) is false.

If neither the queue nor the active job matches, ReqResearchCancel returns NOTHING_QUEUED and nothing is refunded. Refunds are ejected at the bench via MaterialEjector along the same TrajectoryPoints → SpawnPoint → scattered LandingPoint arc used by the old Tech Tree (ported verbatim into ResearchConfig).

Fuel and pause behavior​

  • Fuel is a single server-wide reserve, capped at ResearchConfig.FUEL_CAP (100).
  • While a job is active, fuel burns at ResearchConfig.FUEL_BURN_RATE (1.0/sec) — burn only happens while a job is active; an idle bench (no active job) never burns fuel.
  • ResearchState.advance clamps effectiveDt = min(dt, fuel / burnRate) so a job's elapsed only ever grows in step with fuel actually spent — the moment fuel reaches 0, elapsed stops advancing (the job pauses, it does not fail or lose progress). Refueling resumes it on the next tick.
  • Refueling is Energy-tool based: ResearchService.Initialize's ReqResearchRefuel handler reuses the existing ServerStorage/SharedModules/EnergyToolHelper.luau (GatherEnergyTools/GetEnergyTier/ConsumeTool) — the same helper the Train Fuel and Train Shield recharge flows use — rather than hand-rolling Tool-attribute detection. It takes the first Energy tool found (backpack, then equipped), maps its Tier (1–5) through ResearchConfig.EnergyFuelValue (20/35/55/80/110), consumes the tool, and adds the value to fuel (clamped to FUEL_CAP).
Fuel and queue are shared, not per-player

There is exactly one fuel value and one queue for the entire server. Any player at the bench can enqueue against the shared queue, refuel the shared reserve, or cancel any job — including jobs another player paid for. This is intentional (co-op resource pooling, same spirit as the old Tech Tree's shared pools) but means griefing-by-cancel is possible; there is no per-player ownership check.

Buff/unlock folders​

ResearchEffectsDispatcher.server.luau is the sole writer of two ReplicatedStorage folders, both recomputed from scratch (not delta-accumulated) on every Signals.OnResearchLevelUp:

FolderShapeWritten byRead by
ReplicatedStorage/ResearchBuffsAttributes on the folder itself: one numeric attribute per StatBuff.Key (summed PerLevel * level across all nodes with that key), plus FuelEfficiency (product of DrainPerLevel ^ level across all FuelEfficiency nodes; 1 = no effect)ResearchEffectsDispatcherTrainShieldManager (MaxHP), TrainFuelManager (FuelEfficiency)
ReplicatedStorage/ResearchUnlockedOne BoolValue (named by nodeId, Value = true) per node at level ≥ 1 — recipe nodes includedResearchEffectsDispatcherWorkbenchService (server gate), WorkbenchGuiController (client greying)

Recompute-from-levels means totals are always correct with no drift risk, at the cost of iterating every node in ResearchConfig.Nodes on every level-up (cheap — the node count is small). ResearchEffectsDispatcher also seeds both folders once at server boot (before any player joins) so WaitForChild consumers never race an empty folder.

Client / Server / Shared responsibilities​

Shared — ResearchState.luau is a pure, stateless module with no Roblox service calls: newState, levelOf, pendingLevel, isEligible, validateEnqueue, enqueue, cancel (cascade logic), advance (tick), refuel, serialize. Both the server (authority) and the client GUI (asState() cast over the cached snapshot, for greying/afford checks) call the same pure helpers, so the rules can never drift between sides. validateEnqueue deliberately does not check whether the player holds the materials — that check is server-only and layered on top by ResearchService.

Server — ResearchService.luau is the authoritative owner of ResearchState.State. It is a ModuleScript, not a .server.luau Script — see ModuleScript + loader split below. Initialize() (idempotent, guarded by a boot flag) wires all four packet handlers plus the RunService.Heartbeat tick loop. GetLevels() exposes the live levels table for ResearchEffectsDispatcher to read.

Server — ResearchSystemLoader.server.luau is a one-line boot script: require(...ResearchService) then ResearchService.Initialize(). Mirrors PerkManager.luau / PerkSystemLoader.server.luau.

Server — ResearchEffectsDispatcher.server.luau connects Signals.OnResearchLevelUp and republishes both buff/unlock folders from scratch. See Buff/unlock folders.

Client — ResearchGuiController.client.luau builds the entire ResearchGui ScreenGui in code (no Studio template) and opens it via the bench ResearchPromptPart ProximityPrompt. Node rows are grouped by Category (fixed order Train/Player/Equipment/Recipes) and sorted by prereq depth then DisplayName. A side panel shows the active job (MotionMaster-spring-driven progress bar, Cancel button) and the queue (each entry independently cancellable), plus a fuel gauge (also spring-driven) with a "PAUSED" badge shown whenever fuel is at 0 while a job is active, and a Refuel button. Between ResearchStateUpdate broadcasts, interpolated() fast-forwards the active job's elapsed time and the fuel gauge locally using the known burn rate and the synced server clock, so the bars move smoothly every frame rather than stepping only on broadcast. Uses a Janitor per GUI open/close lifecycle (springs + the per-frame RenderStepped connection are recreated on open and destroyed on close).

ModuleScript + loader split (caution)​

ResearchService is a ModuleScript, booted by a separate loader

ResearchService.luau lives under ServerStorage/SharedModules/ as a ModuleScript, not ServerScriptService/ResearchService.server.luau. This is deliberate: Roblox's require() only accepts ModuleScript instances — a *.server.luau file compiles to a plain Script, which can never be required by another script. Because ResearchEffectsDispatcher.server.luau needs to call ResearchService.GetLevels(), ResearchService has to be a ModuleScript.

The split mirrors the existing PerkManager.luau (ModuleScript, state + Initialize()) / PerkSystemLoader.server.luau (thin boot Script) pattern:

  • ResearchService.luau defines state + an idempotent Initialize() that wires packets and the tick loop, but does nothing until Initialize() is called.
  • ResearchSystemLoader.server.luau is the only script that calls ResearchService.Initialize(), exactly once per server.

If you ever see require() fail on a *.server.luau/*.client.luau path in this codebase, this is the fix: split the requirable state into a ModuleScript and add a thin loader Script that calls its Initialize().

Studio setup​

Manual, one-time Studio work — none of this is created automatically by code:

  1. Bench Model. One Model tagged ResearchBench (CollectionService) with its PrimaryPart set.
  2. Refund-arc trajectory. A child Model named TrajectoryPoints (tagged PlacementIgnore, per the Placement "tag the CollisionBox only" rule) holding two BasePart children: SpawnPoint (arc start, the bench's output mouth) and LandingPoint (arc end, the floor drop zone). If missing, MaterialEjector degrades gracefully and drops refunded pieces at the bench pivot instead of erroring.
  3. Research prompt. A child BasePart named ResearchPromptPart holding a ProximityPrompt — opens the GUI. MaxActivationDistance is set to ResearchConfig.INTERACT_DISTANCE by the client controller at runtime.
  4. Refuel prompt. A separate child BasePart named RefuelPromptPart holding a ProximityPrompt — feeds a held Energy tool into the bench.
  5. Material templates. ReplicatedStorage/CraftingMaterials must hold Wood and Metal Tool templates with IsCraftMaterial = true and ItemType attributes set — shared with the Shredder and Workbench, no duplication needed.

Gotchas / anti-exploit​

Server re-checks proximity on every request

The client's ProximityPrompt distance is never trusted. ReqResearchEnqueue, ReqResearchCancel, and ReqResearchRefuel all re-run isNearBench on the server using INTERACT_DISTANCE + INTERACT_DISTANCE_TOLERANCE. A player invoking from range receives TOO_FAR.

Validate-then-consume ordering on enqueue

ReqResearchEnqueue calls countMaterial for every cost entry before calling consumeMaterial for any of them. If the player is short on any single material, nothing is consumed — there is no partial-payment state.

Cost is paid on enqueue, not on completion

Unlike the old Tech Tree's pooled-contribution model, materials are deducted the instant a level is successfully enqueued — the queue holds already-paid-for jobs. Cancelling is therefore the only way to get materials back, and only at the refund fractions described in Cascade-cancel.

Data flow​

sequenceDiagram
    participant P as Player
    participant C as ResearchGuiController
    participant S as ResearchService
    participant D as ResearchEffectsDispatcher

    P->>C: Walk within INTERACT_DISTANCE
    C->>C: ProximityPrompt fires (ResearchPromptPart)
    C->>S: ReqResearchSnapshot()
    S->>C: { levels, active, queue, fuel }
    C->>C: cache populated; rows/queue/fuel repainted

    P->>C: Click Enqueue on a node row
    C->>S: ReqResearchEnqueue(nodeId)
    S->>S: re-check bench + proximity
    S->>S: ResearchState.validateEnqueue (unknown/prereq/max level/queue full)
    S->>S: countMaterial then consumeMaterial for each cost entry
    S->>S: ResearchState.enqueue(...) - starts immediately if idle
    S->>C: (success, reasonCode)
    S->>C: ResearchStateUpdate(state, serverTime)

    loop every TICK_INTERVAL
        S->>S: ResearchState.advance(state, dt, FUEL_BURN_RATE)
        Note over S: effectiveDt = min(dt, fuel/burnRate) - progress pauses at fuel==0
        alt elapsed >= duration
            S->>D: Signals.OnResearchLevelUp(nodeId, level)
            S->>S: startNext() - pop next queued job
        end
        S->>C: broadcast() on completion, or at most every HEARTBEAT_BROADCAST_INTERVAL
    end
    C->>C: interpolate elapsed/fuel locally between broadcasts (synced server clock)

    D->>D: republish(): recompute ResearchBuffs from GetLevels()
    D->>D: publish ResearchUnlocked/<nodeId> if level >= 1

    P->>C: Click Cancel (active job or a queued row)
    C->>S: ReqResearchCancel(nodeId, fromLevel)
    S->>S: ResearchState.cancel -> (activeRefund?, queuedRefund)
    S->>S: eject queuedRefund @ 1.0, activeRefund @ ACTIVE_REFUND_FRACTION
    S->>C: (success, reasonCode) + broadcast()

    P->>C: Click Refuel (or trigger RefuelPromptPart)
    C->>S: ReqResearchRefuel()
    S->>S: EnergyToolHelper.GatherEnergyTools/GetEnergyTier/ConsumeTool
    S->>S: ResearchState.refuel(state, value, FUEL_CAP)
    S->>C: (success, reasonCode) + broadcast()
