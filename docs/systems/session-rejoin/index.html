Party Lock + Mid-Run Rejoin

Two related guarantees for a live run, both enforced authoritatively on the server: only the party that started a run may be in its server (party lock), and a player who drops mid-run can rejoin the same live server and get their health/inventory back (mid-run rejoin). Parties are formed in a separate lobby place and teleported in via PartySystem:TeleportMembers; this repo is the gameplay place on the receiving end. Persistent progression (XP, coins, perks) is unaffected — it's handled by ProfileStore independently of this system, which only concerns itself with a run's ephemeral, in-server state.

How it works​

Threat model​

A reserved server (created by the lobby via TeleportService:ReserveServerAsync) already blocks the normal server-list join and rejects follow-a-friend joins. Two vectors remain: launching the gameplay placeId directly and landing in a non-reserved public server (game.PrivateServerId == ""), or a non-roster user reaching a reserved server with a stale access code or expired session.

JoinGuard closes both by validating every joiner against an authoritative roster keyed off the engine-set game.PrivateServerId, which cannot be spoofed from the client — so authorization can never be forged.

Cross-place contract​

Coordination between the lobby and gameplay places goes through two MemoryStore hash maps (fast, TTL-native, built for ephemeral cross-server state — unlike DataStore, which is slower, rate-limited, and has no native expiry). SessionStore is the only module that touches them.

Roster — keyed by privateServerId:

{ partyId, authorizedUserIds: {number}, leaderUserId, createdAt }

The lobby writes this immediately before TeleportAsync, so it exists by the time the gameplay server boots. SessionStore.GetRoster reads it on boot with a short retry loop (GET_RETRIES × GET_RETRY_WAIT) to cover the boot/write race. SessionCoordinator mutates it via RemoveFromRoster when a grace window expires, and clears it entirely via ClearRoster on run end.

Session pointer — keyed by userId:

{ placeId, accessCode, privateServerId, jobId, status, heartbeatAt }

This lets the lobby route a rejoiner back to the exact live server. The lobby seeds placeId/accessCode/privateServerId at teleport time, obtaining accessCode + privateServerId from the server-only TeleportService:ReserveServerAsync(gameplayPlaceId). Gameplay fills jobId and heartbeats the entry via SessionStore.RefreshPointer(userId, jobId), which uses UpdateAsync to stamp only jobId/status/heartbeatAt onto the already-seeded entry — it returns without creating a pointer if the lobby never seeded one, since gameplay never learns the raw accessCode and must not fabricate it.

jobId is informational/liveness only — it is not used to route the rejoin. On the lobby side, rejoin must set opts.ReservedServerAccessCode = accessCode alone; the engine API forbids combining ReservedServerAccessCode with ServerInstanceId or ShouldReserveServer on the same TeleportOptions. The access code alone resolves to the one reserved server it was issued for. TeleportData may additionally carry { partyId, rosterVersion } for diagnostics/logging — never trusted for authorization.

Components​

  • JoinGuard — IsReservedServer() is true only for a non-empty PrivateServerId with PrivateServerOwnerId == 0 (rejects both a directly-launched public server and a VIP server). IsAuthorized(roster, userId) checks roster.authorizedUserIds. BounceToLobby(player) retry-teleports to DisruptionConfig.LOBBY_PLACE_ID, reusing that config and its TELEPORT_RETRIES count from the Disruption system.
  • SessionState — RegisterProvider(name, capture, restore) lets other managers plug into the grace/restore flow (see below). Capture(player) must run synchronously from PlayerRemoving, before any deferred teardown clears state. HoldForGrace/HasGrace/TakeBundle/Discard manage the grace window via a Janitor per held entry.
  • SessionSystemLoader — registers AmmoManager.Snapshot/RestorePool and HealthManager.GetHealth/SetHealth as SessionState providers (under the keys "ammo" and "health"), then calls SessionCoordinator.Initialize().

Grace and restore flow​

On an unexpected PlayerRemoving (no prior ReqLeaveToLobby), SessionCoordinator.handleLeave synchronously calls SessionState.Capture(player) — which clones every Tool from the player's Backpack and Character into a per-user folder under ServerStorage.SessionToolCache, then runs every registered provider's capture (ammo pool snapshot, current health) — and holds the bundle via SessionState.HoldForGrace(userId, bundle, SessionConfig.GRACE_WINDOW_SECONDS, onExpire). The player stays on the roster while held.

ScenarioWhat happens
Rejoin within the grace windowJoinGuard re-admits the player (still authorized). SessionCoordinator.handleJoin sees SessionState.HasGrace(userId) and calls scheduleRestore, which waits for CharacterAdded (or applies immediately if a character already exists) and, deferred one frame so HealthManager's full-health CharacterAdded reset runs first, calls SessionState.Restore(player, bundle) — reattaching cached Tools to the fresh Backpack and running every provider's restore. The player respawns at the normal train/party spawn; character position is never captured or restored.
Grace window expires without a rejoinThe task.delay in HoldForGrace fires onExpire, which clears the session pointer and removes the user from the roster so they can no longer rejoin; the bundle's Janitor destroys the cached Tools folder.
Clean leave (ReqLeaveToLobby)SessionCoordinator marks the userId in cleanLeaving before bouncing, so the ensuing PlayerRemoving calls SessionState.Discard (no grace hold) and clears the pointer + roster entry immediately.
Run endWhen PlayerRemoving leaves the server empty (#Players:GetPlayers() <= 1, checked before removal completes) or on game:BindToClose, runEnded clears the roster and every remaining pointer for this privateServerId. No live-server rejoin is possible once the run has ended — a later rejoin attempt lands in the normal lobby flow.

SessionState's tools-folder cleanup uses an explicit Janitor index (Janitor:Add(toolsFolder, "Destroy", TOOLS_JANITOR_INDEX)), not the implicit form, specifically so TakeBundle can detach the folder without destroying it: it calls Janitor:RemoveNoClean(TOOLS_JANITOR_INDEX) (clears the index with no side effect) rather than Janitor:Remove (which would run the cleanup method immediately and destroy the very folder the caller is about to restore Tools from).

A SESSION_HEARTBEAT_SECONDS loop in SessionCoordinator periodically refreshes the roster TTL (SessionStore.RefreshRosterTTL) and every present, authorized player's pointer TTL (SessionStore.RefreshPointer), so a live run never expires while a dead run (crashed process, no clean shutdown) self-expires after ENTRY_TTL_SECONDS.

Non-goals​

  • Live-server rejoin only — rejoin works only while the reserved server stays alive (≥ 1 member keeps it running). If the server empties, the run ends and rejoiners return to the lobby fresh; there is no shared-world snapshot or run resurrection.
  • No character-position restore — a rejoining player always respawns at the normal train/party spawn.
  • No DataStore for ephemeral state — health/ammo/Tools grace-window state lives only in server memory (SessionState) and is lost if the server itself dies during the grace window; this is a deliberate scope cut, not an oversight.
  • The lobby implementation (reserve, roster write, rejoin UI) is a separate project; only the cross-place contract above is specified here.

Gotchas​

BYPASS_GUARD_IN_STUDIO still exercises grace/restore

In Studio, SessionConfig.BYPASS_GUARD_IN_STUDIO (default true) makes SessionCoordinator authorize everyone unconditionally, since no reserved server or lobby exists locally. It does not disable the grace/restore code paths — a Studio playtest still exercises Capture/HoldForGrace/Restore normally.

Tuning​

  • Config module: SessionConfig — src/ReplicatedStorage/SharedModules/Configs/SessionConfig.luau

Its names and GAMEPLAY_PLACE_ID/map-name values are shared verbatim with the separate lobby project.

FieldEffect
GRACE_WINDOW_SECONDSHow long (120s) a dropped player's slot + cached health/ammo/Tools are held for a live-server rejoin before being discarded.
SESSION_HEARTBEAT_SECONDSHow often (30s) the live gameplay server refreshes the roster + session-pointer TTLs in MemoryStore.
ENTRY_TTL_SECONDSTTL (90s, 3x heartbeat) written on both MemoryStore structures; refreshed every heartbeat, so a server that dies unobserved self-expires roughly this many seconds later.
GAMEPLAY_PLACE_IDThis place's PlaceId. Used by the lobby to reserve + teleport in; 0 = unset (fill in before launch).
ROSTER_MAP_NAMEMemoryStore hash-map name for the roster ("EJ_SessionRoster"), shared with the lobby project.
SESSION_MAP_NAMEMemoryStore hash-map name for the session pointer ("EJ_SessionPointers"), shared with the lobby project.
BYPASS_GUARD_IN_STUDIOWhen true (default), authorizes everyone in Studio so local playtests work without a reserved server, while still exercising grace/restore logic.
