Lobby Place

The Lobby is a separate place (PlaceId 110735101010502, Studio name "Endless Journey (WIP)"). Players walk into a room, the first player picks a party size, a countdown runs, and the whole party teleports into a reserved Game Instance server. Its code lives in places/Lobby/ and syncs through Lobby.project.json. See Multiple Places for how the place is wired.

The Lobby code predates the repo conventions. It uses its own Packets registry and its own copies of PartySystem, Zone and Satchel, not the SharedModules copies. It does not use Janitor, Signals or SoundManager yet.

How it works​

Room states​

Each Studio part tagged trigger becomes a Zone. A clone of ServerStorage.RoomTexts sits under it and shows the room state.

StateEntered whenBillboard shows
EmptyServer start, or 1 s after the room clears0 / 5
SelectingA player with no party enters an empty room. A party is created with that player as leader."choosing party size"
CountdownThe leader picks a size in the GUI (SetRoomSize)members / size, countdown, optional "friends only"
TeleportingThe countdown reaches 0"teleporting"

Flow​

  1. Leader enters an empty room. The server creates a party, sets the room to Selecting, opens the GUI (ToggleRoomSizeGui) and locks the leader's controls (SetPlayerControl false).

  2. Leader picks a size (1–5) and friends-only. SetRoomSize sets MaxMembers, moves the room to Countdown and starts a 30 s countdown. The leader's controls unlock. The server ignores the packet unless the sender is the leader, the size is 1–5 and the room is still Selecting.

  3. Other players enter during the countdown. They join if the party has space. When friends-only is on, the leader must be their friend. Otherwise the server sends EjectPlayer and the client steps them 12 studs back.

  4. A player leaves the room. A member leaves the party. If the leader leaves, leadership moves to another member. If the leader is alone, the party disbands, the countdown stops and the room resets.

  5. 2 s before the end, every member's controls lock.

  6. At 0, TeleportParty fulfils the Session Rejoin contract:

    1. TeleportService:ReserveServerAsync(GAMEPLAY_PLACE_ID) returns an access code and the PrivateServerId.
    2. SessionStore.WriteRoster writes the party's user ids under that PrivateServerId. If this fails, the party does not teleport.
    3. SessionStore.SeedPointer writes one session pointer per member. A failure here only disables mid-run rejoin.
    4. party:TeleportMembers(GAMEPLAY_PLACE_ID, { ReservedServerCode = accessCode }) teleports the party.

    The room resets 5 s later.

  7. If any step fails (always in Studio, where teleports do not work), the server clears what it wrote, unlocks and ejects every member, disbands the party and resets the room.

Cancel: the GUI's cancel button sends CancelRoom. The server ejects the player. The playerExited handler then disbands the party.

Studio-only instances​

These exist only in the Lobby place file. Scripts fail or do nothing without them.

  • Room trigger parts tagged trigger.
  • ServerStorage.RoomTexts — a Part tagged roomtexts, with a BillboardGui that holds the TextLabels PartyMemberSizeText, ChoosingPartySizeText, StartCountdownText, FriendsOnlyText and TeleportingPartyText.
  • StarterGui.RoomSizeSelectionGUI — Frame.N1Top.Body holds one ImageButton per size (its TextLabel.Text is the size). Frame.N2Decision.CancelButton is the cancel button. N1FriendOnlyButton.ImageButton is the checkbox fill. The scripts inside sync from the repo through init.meta.json files; the GUI itself does not.
  • Animations tagged autoplay, each parented to an Animator.
  • ReplicatedStorage.PartySystem.PhysicalParties — a runtime folder that PartySystem fills.

Shared modules the Lobby uses​

PartyCreation requires SharedModules.Configs.SessionConfig and ServerStorage.SharedModules.SessionStore. Lobby.project.json lists these two files one by one; it does not sync the rest of src/. A Rojo sync of the Lobby must run before a playtest.

Known gaps​

  • Mid-run rejoin routing is not built. The Lobby seeds the session pointers, but it does not read a returning player's pointer and send them back to their live server (spec steps 1–5 of the rejoin flow). A returning player goes through the normal room flow.
