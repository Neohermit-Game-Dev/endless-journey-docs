Lobby Place

The Lobby is a separate place (PlaceId 110735101010502, Studio name "Endless Journey (WIP)"). Players walk into a room, the first player picks a party size, a countdown runs, and the whole party teleports into a reserved Game Instance server. Its code lives in places/Lobby/ and syncs through Lobby.project.json. See Multiple Places for how the place is wired.

The room code predates the repo conventions. It uses its own Packets registry and its own copies of PartySystem, Zone and Satchel, not the SharedModules copies. The economy and perk code (coins, XP, permanent perks, shop perk inventory) is the shared src/ code, mapped module by module; it uses the shared Packets at ReplicatedStorage.SharedModules.Packets, which does not clash with the room registry.

How it works​

Room states​

Each Studio part tagged trigger becomes a Zone. A clone of ServerStorage.RoomTexts sits under it and shows the room state.

StateEntered whenBillboard shows
EmptyServer start, or 1 s after the room clears0 / 5
SelectingA player with no party enters an empty room. A party is created with that player as leader."choosing party size"
CountdownThe leader picks a size in the GUI (SetRoomSize)members / size, countdown m:ss, access mode (PUBLIC / FRIENDS ONLY / INVITE ONLY)
TeleportingThe countdown reaches 0"teleporting"

Flow​

  1. Leader enters an empty room. The server creates a party, sets the room to Selecting, opens the GUI (ToggleRoomSizeGui) and locks the leader's controls (SetPlayerControl false).

  2. Leader picks a size (1–5) and who can join. SetRoomSize sets MaxMembers and the access mode, moves the room to Countdown and starts the 5-minute forced launch. The leader's controls unlock. The server ignores the packet unless the sender is the leader, the size is 1–5, the access mode is 0–2 and the room is still Selecting. During the countdown the leader can change the mode with SetRoomAccess; this never removes members.

  3. Other players enter during the countdown. PartyRoomRules.canJoin decides, in this order: the room must be in Countdown and not locked; a saved ban refuses; a full crew refuses; an invite lets them in; INVITE ONLY refuses; FRIENDS refuses a non-friend of the leader (IsFriendsWithAsync). A refused player gets a RoomNotice line ("This crew is full.", …) and EjectPlayer steps them 12 studs back. A player already in a crew who walks through another dock is ignored.

  4. A player leaves the room. A member leaves the party. If the leader leaves, leadership moves to another member. If the leader is alone, the party disbands, the countdown stops and the room resets.

  5. Countdown rules. Each second the server applies PartyRoomRules.nextEndsAt: when every member is ready (ReqSetReady), the end moves to now + 5 s (never later); while an invite waits, the end stays at least 10 s away. It writes EndsAt and InviteHold; clients compute the timer from workspace:GetServerTimeNow(). 2 s before the end (lock-in), every member's controls lock; ReqSetReady, SetRoomAccess and CancelRoom are ignored from then on.

  6. At 0, TeleportParty fulfils the Session Rejoin contract:

    1. TeleportService:ReserveServerAsync(GAMEPLAY_PLACE_ID) returns an access code and the PrivateServerId.
    2. SessionStore.WriteRoster writes the party's user ids under that PrivateServerId. If this fails, the party does not teleport.
    3. SessionStore.SeedPointer writes one session pointer per member. A failure here only disables mid-run rejoin.
    4. PersistenceRegistry.ReleaseForTeleport(members) saves and ends each member's coin, XP, perk and inventory sessions without a kick, so the Game Instance opens them without waiting on the session lock.
    5. party:TeleportMembers(GAMEPLAY_PLACE_ID, { ReservedServerCode = accessCode }) teleports the party.

    The room resets 5 s later.

  7. If any step fails (always in Studio, where teleports do not work), the server clears what it wrote, unlocks and ejects every member, disbands the party and resets the room. If the failure comes after the release (TeleportMembers errors, or TeleportService.TeleportInitFailed fires for one member), PersistenceRegistry.Reopen also gives those members their sessions back. In Studio ReserveServerAsync fails first, so no session is released and nothing reopens.

Cancel: the panel's LEAVE button sends CancelRoom. The server ejects the player. The playerExited handler then removes them (a leader with crew hands leadership to another member; a leader alone disbands the party).

Panel open / close: the server fires ToggleRoomSizeGui(true) to every player who joins a party (leader included) and false when they leave or the party disbands.

No client party remote. The vendored PartySystem used to create a PartyRemoteFunction that let any client create parties, accept invites, change the size, toggle invite-only or set an unfiltered party name. The Lobby no longer creates it: every party change goes through the room packets above, which PartyCreation validates.

Invites​

Leader only, during the countdown, before lock-in. Only friends in the same Lobby server (no cross-server invites).

  1. ReqInvite(userId): the server checks the sender leads a room in Countdown, the crew is not full, the target is in this server, in no crew, not already invited, not on the leader's saved ban list, and a friend (IsFriendsWithAsync, checked again after the yield). One invite every 3 s per leader. Then party:InvitePlayer(target) (PartySystem's 20 s expiry), EndsAt on the Invites/<name> ObjectValue, and InviteOffer(partyId, inviterUserId, dock, endsAt) to the target.
  2. Invites do not hold seats. The leader can invite more friends than there are open seats; the first to accept takes the seat. When the crew fills, the other waiting invites are revoked and the leader gets "Crew is full. Your other invites were cancelled."
  3. Hold: while any invite waits, the countdown end stays at least 10 s away (InviteHold is true).
  4. ReqAnswerInvite(partyId, accept): no → the invite is revoked (the hold ends). Yes → canJoin with invited = true and the leader's saved bans; OK → the character is pivoted into the dock's trigger box, so the normal zone join adds them (no second join path). Refused → RoomNotice ("This crew is full.", …).

Saved bans​

Decided: a ban is saved for good on the leader's account and works in every Lobby server. It refuses the banned player from any crew that leader leads, until the leader unbans them. It acts only while its owner leads: as a member you can still share a crew led by someone else. Players already in a crew stay when leadership moves.

  • Store. ProfileStore PlayerBans, key UserId: { Bans = { [userIdString]: bannedAtUnix }, SchemaVersion = 1 }, max 100 entries (PartyRoomRules.MAX_BANS). Registered with PersistenceRegistry (save + teleport hand-off) and JoinSync like the other Lobby profiles.
  • Ban. ReqBanCrew(userId): sender leads a room in Countdown, not locked; target is in the crew. BanStore.Add (refused when full: "Ban list is full. Unban someone first."), then party:BlacklistPlayer (removes the member; RoomChat drops their TextSource), EjectPlayer, and "You were removed from Dock N." to the target. The notice does not say the ban is saved.
  • Join check. The zone join and the invite answer pass banned = BanStore.IsBanned(currentLeader, userId); a ban beats an invite.
  • Unban. ReqUnbanCrew(userId) removes the entry and, when the sender leads a crew that blacklisted that player, calls party:UnblacklistPlayer. It does not pull anyone into the dock.
  • Client. MyBansSync sends the owner's whole list on load and after each change; the panel's My bans manager reads it.

Party room panel​

PartyRoomGuiController opens the panel on ToggleRoomSizeGui(true) and finds the local player's PhysicalParty (it waits up to 5 s for it to replicate). It never asks the server for state: PartyView.Watch repaints on any attribute or child change (at most once per frame) and PartyView.Snapshot reads everything.

  • Layout. Wide is authored at 1920×1022: UIScale = min(W/1920, (H-58)/1022). Under 0.68 the compact layout is used (same instances, other sizes; authored at 844×332, scale clamped 0.75–1.5): CREW / CHAT tabs, 330-wide crew list without perk chips, chat full width. While the compact panel shows, ProximityPromptService.Enabled is false (it covers the thumbstick).
  • Head. State chip: CHOOSE SIZE (amber) · LAUNCH IN m:ss (teal) · WAITING FOR INVITE (amber, InviteHold) · LOCKED IN m:ss (orange, last 2 s) · TELEPORTING (mint); the timer is EndsAt - workspace:GetServerTimeNow(). The leader gets AccessControl (SetRoomAccess); others see AccessTag. READY sends ReqSetReady; LEAVE sends CancelRoom and reads LOCKED once locked in. HIDE folds the panel into the pill.
  • Size bar (leader while Selecting): crew size 1–5 and who can join, START sends SetRoomSize(size, access).
  • Crew list. One row per seat up to the size: avatar in the seat color, LEADER / YOU tags, "@name · Lv N", up to 4 party perk chips, a ready mark. A party perk equipped by two players turns wine (COUNTS ONCE in the loadout box). An open seat shows "Walk into Dock N to join" / "Friends of <leader> only" / "Invite only", or "2 invites waiting · 0:14". Tapping a row shows that player's loadout; tapping a chip fills PerkInfo with the ShopPerkConfig description.
  • Mute / ban. Tap a name in the chat (the NameHit button over the name at the start of a line) to open the ActionBar, or select a crew row to swap its perk chips for RowActions: MUTE / UNMUTE (ReqMuteCrew), BAN (leader only, hidden once locked in, BANS FULL at 100) → YES, BAN / NO → ReqBanCrew. The muter sees "Kai is muted for you. Tap the name to unmute."
  • Invite picker (leader, open seat INVITE): friends in this server (Players:GetPlayers() filtered by a cached LocalPlayer:IsFriendsWithAsync). Button states: INVITE · SENT m:ss · IN DOCK N · IN YOUR CREW · BANNED · CREW FULL. The list stays open for more invites and closes at lock-in.
  • My bans. MyBansBar (anyone with saved bans) → MANAGE opens BanManager: one row per ban, names of players who are not in the server from one batched UserService:GetUserInfosByUserIdsAsync per open, UNBAN → ReqUnbanCrew.
  • Chat badge. Player lines that arrive while the chat is hidden (pill, or the compact CREW tab) count on the CHAT tab and pill badges.
  • Invite prompt. InvitePromptController shows "Nova invites you to Dock 2", "3 / 4 crew · launch in 0:24 · invite ends in 0:20", JOIN / NO. It closes on an answer, when the invite ends or is revoked, and on a RoomNotice (shown in the Toast for 3 s).
  • Update in place. Lists are rebuilt only when their content key changes; the 0.2 s timer only sets Text, so a button is never destroyed mid-press.

Room chat​

Roblox rule: every game with text chat must use TextChatService; a custom chat window is fine only when it sends through a TextChannel.

  • Server (RoomChat). The first member join opens TextChatService.Room_<PartyId>. Every join calls channel:AddUserAsync(userId) (in a pcall, on its own thread); it returns nil when the player's chat is off, and then nothing happens. Leave, eject and ban destroy that player's TextSource. Disband and a successful teleport destroy the channel.
  • What the channel handles for us: the text filter per viewer, parental controls, age groups, blocked users, Roblox's flood limit, and abuse reports from the Roblox menu. Do not add a custom filter, a custom report button, or a user-made party name (it would need its own filter).
  • Client. SEND calls channel:SendAsync(text) (cut to 200 characters). Lines are drawn only from channel.MessageReceived; TextChatMessage.Text is already filtered for this viewer, and it is RichText-escaped (PartyRoomRules.escapeRichText) before display. The raw TextBox text is never shown to anyone else. A player with chat off (TextChatService:CanUserChatAsync false) sees "Chat is off for your account." and no input. The channel's own OnIncomingMessage prefixes room lines with [Dock N] in the Roblox chat window and bubbles.
  • Mute. ReqMuteCrew(userId, muted) fills a per-viewer set; the channel's ShouldDeliverCallback drops a muted sender's lines for that viewer only. Muting needs the target in the viewer's crew; unmute is always allowed. Session only (cleared on PlayerRemoving).

Known gaps​

  • Party room icons have no asset ids (hide, leave, send, chat, ready check, muted, open-seat plus); the ImageLabels are empty until they are uploaded (see TODO.md).

  • Invite hold has no cap. Each waiting invite holds the launch at least 10 s away, for up to 20 s; a leader who keeps re-inviting a friend who never answers can push the 5-minute forced launch back.

  • Cross-server invites are out of scope (decided): only friends in the same Lobby server.

  • Mid-run rejoin routing is not built. The Lobby seeds the session pointers, but it does not read a returning player's pointer and send them back to their live server (spec steps 1–5 of the rejoin flow). A returning player goes through the normal room flow.
