Train Shield

A single global shield pool governs the train's structural integrity for all players. Unlike fuel, the shield has no continuous drain — it is event-driven: damage events deplete it, and players restore it by feeding Energy tools into a ShieldConsole. Depleting the shield to 0 is no longer a game over; once the shield is down, further attacks bleed through to fuel instead. TrainShieldManager is the sole authority — clients receive snapshots and update the diegetic shield monitor.

How it works​

Recharge​

Triggering a ShieldConsole-tagged prompt sends ReqRechargeShield(console). The server validates the tag and proximity, gathers the player's Energy tools via EnergyToolHelper.GatherEnergyTools, and consumes them smallest-ShieldRecharge-value-first until currentShield == maxShield (never over-filled). An isRecharging boolean mutex serializes concurrent requests — like the fuel system's isRefueling, it is not a queue: a second request in flight returns SHIELD_FULL or NO_ENERGY rather than a queued success. On success the client plays SoundManager.PlaySFX("ShieldRecharge").

Damage / fuel bleed-through​

TrainShieldManager.ApplyDamage(amount, source?) is the single damage entry point for the train — all incoming attack/hazard damage, whether it lands on the shield or bleeds through to fuel, routes through this call. No system calls it yet; it is designed for a future combat/hazard system. Guards (all must pass or the call is a no-op): hasStarted must be true, TrainGameOver.HasFired() must be false, amount must be > 0 and not NaN.

Shield > 0 (absorbs):  currentShield = max(0, currentShield - amount); broadcast()
                       -- a hit that drives it exactly to 0 discards its excess; this does NOT end the round
Shield == 0 (bleeds):  TrainFuelManager.ApplyFuelDamage(amount * TrainConfig.FUEL_DAMAGE_FACTOR, source)
                       -- see Train Fuel: Combat fuel-kill for what happens if this zeroes fuel

This replaced the old behavior where the shield reaching 0 called TrainGameOver.Trigger directly — shield depletion by itself no longer ends the round, it just removes the train's damage buffer. TrainConfig.CORE_TAG ("TrainCore") is reserved for the train's structural model for a future combat system to tag; ApplyDamage does not read it directly.

Max formula (buffs)​

maxShield = (BASE_SHIELD + ResearchBuffs.MaxHP) * (1 + PartyPerkBuffs.TrainShieldBonus)
  • Research Bench additive: each completed level of Durability_T1 accumulates onto ResearchBuffs.MaxHP (+50/level, up to MaxLevel = 3 for +150 total), added before the perk multiplier.
  • Party perk multiplicative: TrainShieldBonus = 0.05 * maxLevel across all players (server-max resolution), applied on top of the base + Research sum.
  • Ratio-preserving recompute: when either buff changes, recomputeMax preserves the current fill ratio (currentShield / oldMax) and rounds to the nearest integer — a player at 60% shield stays at ~60% after an upgrade.

subscribeBuffs attaches GetAttributeChangedSignal listeners to both buff folders via WaitForChild, then calls recomputeMax once after attach to catch any missed signals during the wait. See Research Bench and Perks for the upstream buff systems.

Shield monitor (SurfaceGui)​

The shield HUD is diegetic, not on-screen: TrainShieldGuiController clones the ReplicatedStorage.GuiAssets.TrainShieldGui SurfaceGui template onto every BasePart tagged TrainConfig.SHIELD_MONITOR_TAG ("TrainShieldMonitor"), discovered via CollectionService:GetTagged plus live add/remove signals. The clone is created client-side, so each player drives their own independent copy on the same shared surface — no server/replication involvement in the GUI itself. Each registered monitor owns a Janitor that destroys the clone and disconnects its RenderStepped loop when the tag is removed.

The monitor drives two readouts, both eased every frame via exponential smoothing:

  • Shield — from Signals.OnTrainShieldChanged (current / max). Reads "Online" (cyan) above 25%, flips to "Critical" (red) at or below 25%, with hysteresis — it doesn't return to Online until the displayed percentage rises back above 28%. Entering/exiting Critical also swaps the Shield ImageLabel asset.
  • Fuel reserve — extrapolated from Signals.OnTrainStateChanged exactly like the separate on-screen TrainFuelGui HUD. Cyan normally, red at or below 25% fuel. This is purely a second readout on the same monitor face — it does not replace TrainFuelGui, which continues to run unchanged.

No server, packet, or signal changes were needed for the monitor — it consumes the same signals the old HUD already used.

Studio setup​

Each ShieldConsole-tagged root (Model or BasePart) must contain a child BasePart named TrainConfig.SHIELD_PROMPT_PART_NAME ("ProxPromptPart") with a child ProximityPrompt, resolved recursively via PromptResolver. Multiple consoles are supported, each registered independently. Tag every BasePart that should display a monitor with TrainConfig.SHIELD_MONITOR_TAG; the template is authored at ReplicatedStorage.GuiAssets.TrainShieldGui and its element names are load-bearing — TrainShieldGuiController resolves them with WaitForChild and errors on startup if any are missing or renamed. Tag the train's structural model with TrainConfig.CORE_TAG ("TrainCore") — currently unused by TrainShieldManager but reserved for future combat systems.

Gotchas​

Recharge mutex is not a queue

isRecharging is a boolean, not a queue. A second recharge request while one is in-flight returns SHIELD_FULL or NO_ENERGY — not a queued success. The player can try again immediately after.

Pre-game freeze

hasStarted is false until Signals.SetTrainStarted fires (the first brake release on the fuel side). ApplyDamage is a no-op until then.

Passive regen is off by default

SHIELD_REGEN_ENABLED = false and SHIELD_REGEN_PER_SEC = 0. No regen loop exists yet. To add passive regen, implement a RunService.Heartbeat-based loop in TrainShieldManager gated on SHIELD_REGEN_ENABLED, and update this page and the config map.

Shield depletion is no longer a game over

The shield can sit at 0 indefinitely; only fuel reaching 0 (natural stall-out or combat bleed-through) ends the round. See Train Fuel — game-over reasons.

typeof guard on OnServerInvoke

ReqRechargeShield.OnServerInvoke receives (player, console) where console is client-supplied. A typeof(console) == "Instance" guard runs before acquiring the isRecharging lock, so a malformed invocation (nil or non-Instance) is rejected cleanly without erroring.

Data flow​

sequenceDiagram
    participant Sv as TrainShieldManager
    participant Cl as TrainShieldController
    participant Gui as TrainShieldGuiController

    Sv->>Sv: Initialize() - maxShield=computeMax(), currentShield=maxShield
    Sv->>Cl: TrainShieldSync(currentShield, maxShield)
    Cl->>Gui: Signals.OnTrainShieldChanged(current, max)

    Note over Cl,Sv: RECHARGE
    Cl->>Sv: ReqRechargeShield(console)
    Sv->>Sv: isRecharging mutex, validate tag + proximity
    Sv->>Sv: GatherEnergyTools smallest-first, consume until full
    Sv-->>Cl: (success, shieldAdded, code)
    Sv->>Cl: TrainShieldSync(...)

    Note over Sv: DAMAGE (future combat/hazard caller)
    Sv->>Sv: ApplyDamage(amount, source) - guard hasStarted, not HasFired, amount>0
    alt currentShield > 0
        Sv->>Sv: currentShield = max(0, currentShield - amount); broadcast()
    else currentShield == 0
        Sv->>Sv: TrainFuelManager.ApplyFuelDamage(amount * FUEL_DAMAGE_FACTOR, source)
    end

    Note over Sv: BUFF CHANGE
    Sv->>Sv: ResearchBuffs.MaxHP or PartyPerkBuffs.TrainShieldBonus changes
    Sv->>Sv: recomputeMax() - ratio-preserving rescale, broadcast()

    Note over Gui: MONITOR UPDATE (RenderStepped, per tagged part)
    Gui->>Gui: displayedShieldPct eased toward shieldSnap; Online/Critical + image swap
    Gui->>Gui: fuel reserve readout extrapolated from OnTrainStateChanged
