Introduction

Endless Journey is a Roblox game inspired by Void Train, built with Rojo. Luau source lives under src/ and syncs live into the Roblox DataModel via default.project.json. This site is the maintenance and architecture reference for everyone working on the project.

Systems at a glance​

Core Loop​

SystemWhat it does
PlacementGrid and free-placement of world objects; client previews, server validates.
Placeable ActionsStash returns a placed item to the Backpack, Move re-equips it; both server-validated.
JunkServer spawns weighted floating debris; client renders pooled visuals and simulates movement locally.
GrabhookTool-driven traversal; client drives raycast and rope visuals, server validates the claim and awards it.
Proximity PickupDropped craft materials and shredder-ejected items auto-register for proximity claim or delayed auto-collect.
ShredderTwo-step server handshake converting non-Energy junk into crafting materials at a Workbench.
Workbench CraftingServer-authoritative, instant crafting of weapons/armor/placeables from config-defined recipes.
Research BenchServer-wide, session-only research: enqueue, advance, complete, refuel, and cancel jobs gated by shared fuel.

Train​

SystemWhat it does
Train FuelSingle global fuel value computed algebraically by the server; clients predict the bar locally.
Train ShieldGlobal, event-driven shield pool depleted by damage and restored with Energy tools.
CannonGrid-placeable, manned cannon firing server-authoritative explosive arc shells.
Events OrchestratorServer-authoritative scheduler deciding when and which in-game events fire per channel.
Disruption / MaintenanceNotifies players, force-saves progress, and teleports to the lobby on shutdown or maintenance.

Combat​

SystemWhat it does
WeaponsClient-predicted / server-authoritative combat with a shared validator; all damage applies server-side.
Enemy CombatA centralized AI director ticks every armed enemy, reusing the player weapon and damage stack.
Enemy SpawnerGeneric server-authoritative spawner selecting weighted spawn points and validating placement.
HealthThe server is the single source of truth for health; it drives regen and syncs the client HUD.
Damage NumbersClient-only, render-only floating world-space damage numbers; never computes or applies damage.

Player​

SystemWhat it does
Stamina & SprintClient-predicted, server-authoritative stamina simulation synced at up to 10 Hz.
CameraA fully script-owned third-person camera computing Camera.CFrame every frame.
SettingsGeneric server-authoritative user-preferences registry for audio volumes and sensitivity.

Progression & Economy​

SystemWhat it does
Progression (XP & Level)Server-authoritative, party-shared XP & Level system persisted with ProfileStore.
Economy (Coins)Server-authoritative coin wallet persisted with ProfileStore, shared across lobby and gameplay places.
QuestsRotating ProfileStore-backed quest system with four buckets plus a Season scope feeding the Battle Pass.
Battle PassMonthly ProfileStore-backed 60-tier track with Free and Premium reward rows.
PerksLevel-driven permanent progression spending Personal/Party points on persistent buffs.

Platform​

SystemWhat it does
SoundA layered client audio system; all game audio flows through the SoundManager facade.
NotificationsA signal-driven client toast stack; NotificationManager is the sole subscriber.
Party Lock + Mid-Run RejoinServer-enforced party lock and mid-run rejoin guarantees for a live run.

Design philosophy​

Every gameplay system follows a client predicts / server authoritative pattern with a shared validator. The client runs local prediction (placement preview, stamina drain, fuel bar interpolation) so interaction feels instant, while the server re-validates every request and broadcasts the authoritative result. Protocol changes must go through src/ReplicatedStorage/SharedModules/Packets/init.luau; cross-module events go through src/ReplicatedStorage/SharedModules/Signals/init.luau. When in doubt, the server wins.

  • Architecture — runtime layers, cross-cutting modules, and the authority pattern.
  • Systems — one page per system, grouped by family (Core Loop, Train, Combat, Player, Progression & Economy, Platform); the API sidebar sections mirror these same families.
  • How-To Playbooks — step-by-step safe-change guides, grouped the same way (plus a Backbone group for packets/signals).
  • Reference — the networking / signals / config maps, Janitor and MotionMaster cheat-sheets, plus the Moonwave-generated API docs for every annotated module.
