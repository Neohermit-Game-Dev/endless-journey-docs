Join-Sync Snapshot Handshake

JoinSync (ServerStorage/SharedModules/JoinSync.luau) is the project's sole mechanism for delivering a join-time snapshot of a server-authoritative value. Never connect Players.PlayerAdded to push a snapshot to a client. Register a sender with JoinSync.Register instead.

See Networking Map for the ClientReady packet this mechanism is built on, and the design spec at docs/_superpowers/specs/2026-09-17-join-sync-snapshot-handshake-design.md for the full incident writeup this page distills (SDD artifacts under _superpowers/ are excluded from the published Moonwave site, so this is a repo path, not a doc link).

Why a PlayerAdded push is unreliable​

Packet (the vendored networking library) connects the underlying RemoteEvent at module-require time and dispatches every incoming payload into a plain Signal with no backlog. That connection is almost always live well before the script that actually cares has connected its own handler — every client script that requires Packets at the top of the file opens the door before anything downstream is listening. Anything the server sends in that window is dispatched into a signal with no subscribers and is gone. There is no retry, and no way for a late subscriber to ask for the current value.

Players.PlayerAdded compounds this: it is not guaranteed to fire for the first player in a server, who may already be in Players when the server script runs. A manager that only connects the event — never also iterating Players:GetPlayers() — can miss that player's join entirely.

Put together: a one-shot PlayerAdded → FireClient push can be dropped by either the player already being present, or the client not yet listening, and the sender has no idea it happened.

The mechanism​

JoinSync inverts the direction. The client, not the server, decides when it is ready:

  1. ClientReadyController.client.luau fires Packets.ClientReady (client → server, zero payload) exactly once, after game.Loaded plus a task.defer — giving every other StarterPlayerScript a chance to finish connecting.
  2. JoinSync.Initialize() (called once, from JoinSyncLoader.server.luau) handles that packet by running every registered sender for that player, each isolated in its own task.spawn + xpcall so one erroring sender can't starve the rest.
  3. JoinSync.Register(name, sender) also serves any player who is already ready at the moment of registration. This is what makes registration order and script-load timing irrelevant — a manager whose Initialize() runs late still reaches everyone.
  4. A per-player ready flag (cleared on PlayerRemoving) means a repeated ClientReady is a no-op, so a client can't make the server replay every system's snapshot in a loop.

name must be unique per system — it exists only to label the warning if that sender's send errors, or to catch a double-registration (skipped, with a warning, rather than double-sending).

The rules​

Follow these when adding any new server-authoritative readout that a client needs on join:

  1. Register a JoinSync sender; never connect PlayerAdded to push a snapshot. PlayerAdded fires too early relative to the client's own readiness, and can miss the first player outright. JoinSync fires exactly when the client says it's listening.
  2. Read state at send time, inside the sender; never capture it at registration. Register is called once, at server startup, long before any player exists. A sender is a closure that reads live state (an upvalue, a table lookup) each time it runs — it must never close over a value snapshotted at registration, or every player will be served whatever the state happened to be at boot.
  3. Server-side record creation stays on PlayerAdded; only the send moves. If a manager's PlayerAdded handler both creates a per-player record and pushes it, keep the record creation where it is — gameplay code may read that record before the client is ready — and move only the FireClient call into a JoinSync.Register sender. That handler still needs the usual Players:GetPlayers() bootstrap loop alongside its PlayerAdded connection, so a player already present when the server script runs still gets a record.
  4. Never invent a client-side default for a server-authoritative value. Render a placeholder ("—", a neutral colour, a zero-width bar — whatever fits the widget) until the real snapshot arrives, and snap directly to the first real value instead of easing from a guess. A guessed default is worse than no data: it looks like an answer.
  5. Never seed an extrapolation baseline from a client-read clock. workspace:GetServerTimeNow() is the client's own converging estimate of server time; read early in the client's life (module load, script start) it has not converged yet. Extrapolate only from a serverTime the server itself stamped onto the snapshot it sent.

Rule 4 and rule 5 are what actually fixed the reported bug — JoinSync alone makes the send reliable, but the old fallback snapshots (seeded from config defaults, timestamped from an unconverged client clock) were what turned an occasional dropped packet into a HUD that always swept 100% → 0% on join. See TrainFuelGuiController and TrainShieldGuiController for the placeholder pattern, and TrainStateCache for the shared extrapolation helper that returns nil until a real snapshot lands.

Worked example​

TrainFuelManager.Initialize() registers its join-time sender instead of connecting Players.PlayerAdded:

-- The client send waits until the client is listening; see JoinSync.
JoinSync.Register("TrainFuel", function(player: Player)
    Packets.TrainStateSync:FireClient(player, fuelAtLastEvent, currentRate, isBraked, isStalled, lastEventTime)
end)

fuelAtLastEvent, currentRate, isBraked, isStalled, and lastEventTime are all upvalues read fresh every time the closure runs (rule 2) — a player who joins mid-round gets the fuel level as of their join, not whatever it was when the server booted.

The two deliberate exclusions​

Not every server-authoritative system needs a JoinSync sender. Two managers were deliberately left out of this conversion:

  • AmmoManager pushes nothing at join. Ammo pools start empty, and an empty pool is the correct initial state — there is nothing to snapshot. AmmoPoolSync only fires on award, consume, or equip, none of which need a join-time replay.
  • ArmorManager replicates through an attribute folder, not a packet. Attributes are ordinary replicated Instance state — readable by the client at any time, including before it has connected anything. There is no connect-after-the-fact race to guard against, so JoinSync would add nothing.

If a future system's join state is provably always correct with no send at all (like AmmoManager), or replicates through Instance/attribute state rather than a packet (like ArmorManager), it does not need a JoinSync sender either. Everything else that pushes a one-shot snapshot to a joining player does.
