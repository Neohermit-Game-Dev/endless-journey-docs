Multiple Places

Endless Journey has up to three places in one universe (GameId 9507850633). All three live in this repo.

PlacePlaceIdProject fileservePortRuns gameplay (src/ scripts)
Game Instance107438402196338default.project.json34872Yes
Lobby110735101010502Lobby.project.json34873No
Tutorialnot created yetTutorial.project.json (not yet created)34874Yes

The places must stay in the same universe. TeleportService and the shared DataStores / MemoryStores depend on it.

Rules​

  • Every project file has servePlaceIds. The Rojo plugin then refuses to sync into a different place. A wrong-place sync can delete work.
  • Every project file has its own servePort. Two places can then sync at the same time.
  • Ownership comes from the path, not from game.PlaceId. Shared code never branches on game.PlaceId. Storing a target PlaceId for a teleport is fine (see PlaceIds in config).
  • Set $ignoreUnknownInstances: true on every service node. With a $path, Rojo defaults it to false and deletes Studio-only instances (maps, GUI prefabs, terrain).
  • Use { "optional": "<path>" } for folders that can be missing. Rojo then skips the node instead of failing. An empty place folder is not tracked by git, so this matters on a fresh clone.

What each place gets​

src/ is not shared by every place. It is the gameplay code, and it runs in Game Instance and Tutorial. The Lobby gets only the single modules it requires, listed one by one in Lobby.project.json.

TreeGame InstanceTutorialLobby
src/ReplicatedStorage/SharedModulesYesYesListed modules only
PackagesYesYesJanitor only
src/ServerStorage + ServerPackagesYesYesListed modules only (no ServerPackages)
src/ServerScriptServiceYesYesNo
src/StarterPlayer/StarterPlayerScriptsYesYesListed scripts only
src/StarterPackYesYesNo
places/<Place>/...own onlyown onlyown only

Mapping the whole SharedModules tree into the Lobby would sync hundreds of gameplay modules it never uses. Some shared modules also start work on require (for example Chrono); keep those out of the Lobby.

Code that must run in Game Instance but not Tutorial goes in places/GameInstance/, or stays in src/ behind a PlaceConfig flag. Do not copy it.

Layout​

Game Instance/                 # repo root
  src/                         # gameplay + shared modules (see table above)
  places/                      # create only when a place needs its own scripts
    Lobby/
      ReplicatedStorage/       # lobby modules (Packets, PartySystem, Zone, Satchel, ...)
      ServerScriptService/
      StarterGui/              # GUI scripts; see "Scripts inside Studio-only instances"
      StarterPlayer/StarterPlayerScripts/
    Tutorial/
      ServerScriptService/
      StarterPlayerScripts/
  default.project.json         # Game Instance
  Lobby.project.json
  Tutorial.project.json

default.project.json stays the Game Instance file. Then rojo serve with no argument and the sourcemap command keep working.

The Lobby project file​

See Lobby.project.json. What the Lobby code does is on the Lobby Place page. The pattern: a service points its $path at places/Lobby/<Service>. Each shared module the Lobby needs is added by hand at its normal path, so require paths match the Game Instance:

"ReplicatedStorage": {
  "$className": "ReplicatedStorage",
  "$ignoreUnknownInstances": true,
  "$path": "places/Lobby/ReplicatedStorage",
  "SharedModules": {
    "$className": "Folder",
    "$ignoreUnknownInstances": true,
    "Configs": {
      "$className": "Folder",
      "$ignoreUnknownInstances": true,
      "SessionConfig": { "$path": "src/ReplicatedStorage/SharedModules/Configs/SessionConfig.luau" }
    }
  }
}

To share another module with the Lobby, add one $path node for it. Also add every module it requires, or its require fails in the Lobby. Check what the module creates on require, too: the Game Instance Packets creates placement UnreliableRemoteEvents, so the Lobby maps places/Lobby/SharedModules/Packets.luau (which returns only Packets/LobbyShared) at the same path. A new packet that Lobby code uses goes in LobbyShared. The Lobby maps only the Wally packages it uses, one by one (today: Janitor, for PerkClient and PerkInventoryClient). Never map the whole Packages folder: packages ship instances too (chrono has a Remotes folder of RemoteEvents). The Lobby Place page lists every mapped module.

The Lobby still has its own older copies of Packets, PartySystem, Zone and Satchel at the ReplicatedStorage root.

Scripts inside Studio-only instances​

Rojo makes a directory into a Folder and deletes children it does not know. A script that lives inside a GUI, a model, or next to Studio-only children therefore needs an init.meta.json in each directory above it:

{
  "className": "Frame",
  "ignoreUnknownInstances": true
}
  • className must match the Studio class exactly (ScreenGui, Frame, ImageButton, ...). A wrong class replaces the Studio instance and loses its children.
  • ignoreUnknownInstances: true keeps the Studio-only children (labels, layouts, UIStroke, runtime folders).
  • A Script with RunContext = Client (for example SatchelLoader in ReplicatedStorage) is init.server.luau plus "properties": { "RunContext": "Client" }. A .client.luau file becomes a LocalScript, which does not run in ReplicatedStorage.

Recipe: import a place from Studio​

Azul (or any Studio-to-file sync) writes a script with children as X.luau beside a folder X/. Rojo wants X/init.luau (keep the .server/.client suffix: X/init.server.luau).

  1. Sync the place to a temporary folder and move it to places/<Place>/.
  2. Move every X.luau that has a sibling X/ folder to X/init.luau.
  3. Read the class of every non-script ancestor from Studio. Add the init.meta.json files from the section above.
  4. Run rojo sourcemap <Place>.project.json and compare its classes with the Studio tree.
  5. Turn off Azul before you connect Rojo. Two sync tools on one place fight each other.

Recipe: Tutorial project file​

Copy default.project.json. Change name, servePort (34874) and servePlaceIds. Then merge the place folders under the shared services with a named child:

"ServerScriptService": {
  "$className": "ServerScriptService",
  "$ignoreUnknownInstances": true,
  "$path": "src/ServerScriptService",
  "PlaceScripts": {
    "$className": "Folder",
    "$ignoreUnknownInstances": true,
    "$path": { "optional": "places/Tutorial/ServerScriptService" }
  }
}

Do the same under StarterPlayerScripts. The child name (PlaceScripts, PlaceConfig) must not collide with a folder in src/<Service>/.

Each file repeats the full tree. This is deliberate: three short files are easier to read than a nested-project setup.

Recipe: place-specific settings​

Shared code must not branch on the place. Each place that runs the shared code supplies a module at the same path instead:

-- places/Tutorial/ReplicatedStorage/PlaceConfig.luau
return {
	EnemyWavesEnabled = false,
}
-- shared code
local PlaceConfig = require(ReplicatedStorage.PlaceConfig)

Once shared code requires PlaceConfig, every place that runs that code must supply one (make the path required, not optional). A missing module fails loudly at require, which is correct. Do not add PlaceConfig before a flag needs it.

PlaceIds in config​

Teleport targets live in the existing configs, not in project files:

  • SessionConfig.GAMEPLAY_PLACE_ID — Game Instance. The Lobby reserves a server here and teleports the party in. See Session Rejoin.
  • DisruptionConfig.LOBBY_PLACE_ID — Lobby. Players return here after a disruption. See Disruption.

Add a TUTORIAL_PLACE_ID beside them when the tutorial teleport exists.

Recipe: add a place​

  1. Create the place in the Creator Dashboard, inside the Endless Journey universe. Copy its PlaceId (Studio: print(game.PlaceId)).
  2. Create <Place>.project.json from the recipe above. Use the next free servePort.
  3. Create places/<Place>/ only when the place has its first script.
  4. Add the PlaceId to the table at the top of this page and to the teleport configs.
  5. Open the place in Studio and pick <Place>.project.json in the Rojo extension.
  6. Re-set the TweenPlus TweenPreallocations attribute in that place (see Toolchain). It is per place file.

Luau LSP​

The sourcemap covers one project file. To get autocomplete in places/<Place>/, regenerate it from that place's file:

rojo sourcemap Lobby.project.json -o sourcemap.json --include-non-scripts

Or set "luau-lsp.sourcemap.rojoProjectFile": "Lobby.project.json" in your local .vscode/settings.json (.vscode/ is not tracked).

Cross-place gotchas​

  • ProfileStore session lock. A profile that is still open in one place delays the session start in the next place. The Lobby ends every member's sessions with PersistenceRegistry.ReleaseForTeleport right before the teleport and reopens them if it fails (see Perk Inventory). A new profile manager must call PersistenceRegistry.RegisterHandoff.
  • Studio-only content (maps, GUI prefabs, terrain) lives only in each place file. If a script waits for an instance that is not in the repo, look in that place. TODO.md in the repo root tracks the Game Instance gaps.
  • Place files (.rbxl/.rbxlx) stay out of git. Publish from Studio.

Checklist before you finish a change​

  • Every *.project.json has servePlaceIds and a unique servePort.
  • Every required $path exists (rojo sourcemap <file>.project.json fails if not).
  • No shared code reads game.PlaceId to pick behaviour.
  • New place-only code is under places/<Place>/, not src/.
  • Lobby code does not require a module that starts gameplay systems.
