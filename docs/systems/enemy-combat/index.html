Enemy Combat

Server-authoritative combat for spawned enemies, driven by a single centralized AI director rather than a script-per-enemy. EnemyBrain ticks every armed enemy at a fixed 10 Hz, deciding movement and firing as two independent concerns each tick. Enemy weapons reuse the exact same damage layer as player weapons — FastCast2 projectiles, ServerProjectile lobs, WeaponValidation melee hitboxes, and CombatService routing — so the fairness and anti-exploit guarantees that apply to player guns (dodgeable travel time, no hitscan instakills, spread, range caps) apply identically to enemy fire. An archetype only becomes armed if it has a matching EnemyCombatConfig profile; archetypes without one spawn and walk around (via EnemySpawner) but never fire.

How it works​

The EnemyBrain director​

EnemyBrain is a single module-level loop, not one script per enemy. EnemyBrain.Init() connects one RunService.Heartbeat listener and accumulates dt until TICK_INTERVAL (1 / TICK_HZ, TICK_HZ = 10) has elapsed, then calls tick() once. Every registered enemy is iterated in that single tick — there are no per-enemy RunService connections, task.spawn loops, or while true do task.wait() end patterns. This keeps the cost of N enemies roughly linear and avoids N independent scheduler entries.

Each registered enemy is a Record (an in-memory table, not an Instance) keyed by its Model in a module-level records dictionary:

type Record = {
    model: Model,
    humanoid: Humanoid,
    root: BasePart,
    profile: Profile,          -- EnemyCombatConfig.Profile
    cleaner: Janitor.Janitor,

    target: Player?,

    -- movement
    waypoints: { PathWaypoint },
    waypointIndex: number,
    pathGoal: Vector3?,
    nextRepathAt: number,

    -- firing
    fireState: "Idle" | "Bursting" | "Cooldown",
    shotsLeft: number,
    nextShotAt: number,
    nextBurstAt: number,
    telegraphUntil: number?,
}

Every tick, for every record that is still alive and rooted, EnemyBrain:

  1. Reacquires a target if the current one is missing or dead — nearestPlayer scans Players:GetPlayers() for the closest player with a living Humanoid and a HumanoidRootPart. Targeting is pure distance; there is no aggro persistence, threat table, or line-of-sight requirement to pick a target (LOS only gates firing, see below).
  2. Steps movement (stepMovement) — independent of firing.
  3. Steps firing (stepFiring) — independent of movement.

This is the two-concern (move ‖ fire) model: an enemy can be walking toward the player and shooting at the same time (run-and-gun), because neither step blocks or depends on the other completing first within the tick.

Movement and path-compute budgeting​

stepMovement holds the enemy still (Humanoid:MoveTo(currentPosition)) once it is within profile.CloseDistance (default 30) of the target — this "comfort band" makes ranged enemies stop closing once they're inside a distance they consider safe to shoot from, rather than walking into melee range. Outside that band, it paths toward the target's HumanoidRootPart position.

Paths are computed via PathfindingService:CreatePath/ComputeAsync, but not on every tick for every enemy. A shared pathBudget of PATH_BUDGET_PER_TICK (1) ComputeAsync calls is allocated per tick and decremented as enemies consume it — with a 10 Hz tick this caps fresh pathfinding compute at ~10 calls/sec total across all enemies, naturally staggering large waves instead of bursting 40 simultaneous ComputeAsync calls in one frame. An enemy only requests a new path when it has none yet, REPATH_INTERVAL (1.0s) has elapsed since its last compute, or the target has drifted more than REPATH_THRESHOLD (8 studs) from the path's original goal — most ticks for most enemies do no path computation at all, they just step along existing waypoints (WAYPOINT_REACHED = 3 studs advances to the next one). If ComputeAsync fails or the budget is exhausted, the enemy falls back to beelining straight at the goal with Humanoid:MoveTo — pathfinding failure is non-fatal, it just degrades to dumb-walk.

Melee firing​

stepFiringMelee is a simple range-gated, single-swing cooldown: if the target is within profile.Range (default 8 studs), call EnemyWeapon.MeleeSwing and roll a fresh cooldown (rollCooldown, uniform between AttackCooldownMin/Max). There is no melee combo system for enemies (unlike the player's ClassicSword combo in Weapons) — every swing is identical.

Ranged firing: the burst/cooldown state machine​

stepFiringRanged drives a three-state machine per enemy: "Idle" → "Bursting" → "Cooldown" → back to "Idle".

  • No target, out of range, or no line of sight: firing is suspended and movement keeps closing/repositioning. Critically, if the enemy was mid-burst ("Bursting") when any of these interruptions occurs, its state is reset to "Idle" rather than left to resume later:

    if rec.fireState == "Bursting" then
        rec.fireState = "Idle"
    end

    This reset exists specifically so that re-engagement always rolls a brand-new burst (startBurst) instead of resuming a stale partial burst whose nextShotAt/shotsLeft may be long expired or, for a sniper, whose Telegraph window has already elapsed. Without the reset, a player could duck behind cover for a moment to skip past a sniper's aim-telegraph and pop back out already inside the weapon's nextShotAt window — defeating the reaction-window fairness the telegraph exists to provide. The fix applies identically to the out-of-range case (LOS-break and range-break share the same reasoning) so the dodge counter-play stays consistent regardless of why the enemy lost its shot.

  • "Cooldown": holds fire until now >= nextBurstAt, then transitions to "Idle".

  • "Idle": immediately calls startBurst, which rolls shotsLeft between BurstMin/BurstMax, sets fireState = "Bursting", and sets nextShotAt = now + Telegraph (0 for non-snipers). For a sniper (Telegraph > 0), this delay before the first shot is the player's reaction window — telegraphUntil is exposed on the record so a future client-side "enemy is aiming at you" cue could read it, though nothing currently renders it.

  • "Bursting": once now >= nextShotAt and shotsLeft > 0, fires one shot (fireOneShot — routes to EnemyWeapon.Lob or EnemyWeapon.FireProjectile depending on profile.FireMode), decrements shotsLeft, and schedules the next shot at now + ShotInterval. When shotsLeft reaches 0, transitions to "Cooldown" and rolls the next burst's start time.

Line of sight is checked every tick a ranged enemy considers firing (hasLineOfSight): a raycast from the muzzle origin to the target's root, excluding the shooter's own model, treats a hit against the target's own character as clear (not blocked) and anything else solid as blocked. This stops enemies shooting through walls; it is a fairness check, not a cover-seeking AI — enemies make no attempt to flank around an obstruction, they simply hold fire and let stepMovement keep closing the distance.

Fairness rationale​

  • No ammo, ever. Enemies have no magazine or reload — the only throttle on rate of fire is the burst/cooldown rhythm in EnemyCombatConfig. This is a deliberate simplification versus the player's ammo system (Weapons); the challenge lever is burst size and cooldown length, not resource starvation.
  • No hitscan. EnemyWeapon.FireProjectile always launches a travelling FastCast2 projectile at a finite ProjectileSpeed; damage applies on Hit after real flight time elapses, so a player who strafes out of the bullet's path after it's fired takes no damage, exactly like dodging a player-fired bullet.
  • No target leading. Both FireProjectile and Lob aim at the target's current position (targetPos) at the moment of firing, never a predicted future position. Combined with finite projectile speed and Spread (an aim-error cone in degrees, via WeaponValidation.applySpread), this makes every ranged archetype dodgeable by lateral movement, not just by breaking LOS.
  • Sniper telegraph as a reaction window. PirateSniper's Telegraph = 0.6 inserts a fixed delay between entering "Bursting" and the first (and only) shot, giving the player six-tenths of a second of visible aim-up before the highest single-hit damage in the game (Damage = 40) fires. The reset-on-interrupt fix above ensures this window cannot be bypassed by ducking LOS or range right before the shot and popping back — the telegraph always re-applies on re-engagement.

EnemyWeapon​

EnemyWeapon is the enemy attack action — it owns no timing or ammo state (that's EnemyBrain's job) and instead reuses the exact same player damage layer end to end:

  • EnemyWeapon.MuzzleOrigin(model, profile) — returns the world position fire should originate from. If the rig has a descendant Attachment named "Muzzle" (an authored weapon model), its WorldPosition is used. Otherwise it falls back to the root part's CFrame offset by profile.MuzzleOffset (default (0, 1.5, -1)) — an art-less first pass that still produces a sensible shoulder-height, slightly forward origin.
  • EnemyWeapon.FireProjectile(model, profile, origin, targetPos) — fires one travelling bullet through a dedicated module-level FastCast2.new() caster (bulletCaster, separate from the player gun caster in WeaponServer, but wired the same way: LengthChanged steps an optional cosmetic part, Hit resolves the struck model via WeaponValidation.resolveHumanoidModel and applies damage via CombatService.ApplyToModel(model, humanoid, damage, "Bullet", enemyModel)). Fires Packets.WeaponFired on both a real hit and a miss-timeout backstop (task.delay guarded by a data.fired flag so a real hit and the timeout can never both resolve), so the tracer always renders even when nothing is struck. The optional cosmetic bullet comes from ServerProjectile.spawnRocket(profile.Weapon, ...) — nil-safe; if no WeaponAssets/<Weapon> template exists, fire still works, just without a visible bullet model.
  • EnemyWeapon.Lob(model, profile, origin, targetPos) — reuses the player grenade path: ServerProjectile.spawnThrowable(weapon, origin, unit, speed, "Bounce", { model }) for a server-replicated physics throw, biased upward (+ Vector3.yAxis * 0.5) so it arcs rather than fires flat. After profile.FuseTime, detonates via CombatService.ApplyAOE and fires Packets.ExplosionAt, then destroys the charge instance.
  • EnemyWeapon.MeleeSwing(model, profile) — one swing from the rig's current root CFrame, reusing WeaponValidation.queryMeleeTargets (the same box-overlap query the player melee handler uses) over profile.Range/HitboxSize, applying damage via CombatService.ApplyToModel(..., "Melee", enemyModel) to every struck target and firing Packets.WeaponImpact on a landed hit.

In every case the attacker argument passed to CombatService is the enemy Model, not a Player — CombatService/Factions already supports a non-Player attacker (the Faction of a Model is resolved by its EnemyNPC/FriendlyNPC CollectionService tag), so no changes were needed to the damage router itself to support enemies attacking players. Factions.canDamage("Enemy", "Player") is true by default; the reverse and same-faction pairs are not, which is what prevents enemies from ever damaging each other or friendly NPCs by the same mechanism that prevents player-on-player damage. See Weapons → CombatService and Architecture → Backbone for the faction model itself.

EnemyCombatConfig profiles​

EnemyCombatConfig holds one Profile per archetype name, keyed identically to the archetype names used in EnemySpawnerConfig.Archetypes. An archetype with no entry here stays passive — EnemyBrain.Register looks up EnemyCombatConfig.GetProfile(archetypeName) and simply returns without arming the enemy if it's nil. This is the only "is this archetype armed" check in the system — see Studio setup below for the common mistake this invites.

export type Class = "Ranged" | "Melee"
export type FireMode = "Projectile" | "Lob"

export type Profile = {
    Class: Class,
    Weapon: string,              -- FX/sound key (WeaponFx) + WeaponAssets cosmetic name

    Damage: number,

    -- Ranged-only
    FireMode: FireMode?,          -- "Projectile" | "Lob"; nil for melee
    ProjectileSpeed: number?,     -- studs/s; finite + dodgeable
    Spread: number?,              -- aim-error cone (degrees)
    Range: number?,               -- max distance the enemy will fire from
    CloseDistance: number?,       -- pathfind until generously inside Range, then hold
    MuzzleOffset: Vector3?,       -- HRP-relative origin until a "Muzzle" attachment exists

    -- Burst rhythm (no ammo)
    ShotInterval: number?,
    BurstMin: number?,
    BurstMax: number?,
    BurstCooldownMin: number?,
    BurstCooldownMax: number?,

    Telegraph: number?,           -- sniper: seconds aiming before the shot

    -- Lob-only
    AOERadius: number?,
    FuseTime: number?,

    -- Melee-only
    HitboxSize: Vector3?,
    AttackCooldownMin: number?,
    AttackCooldownMax: number?,

    -- Optional animation asset ids (server rig)
    FireAnimId: string?,
    SwingAnimId: string?,
}

EnemyCombatConfig.FindByWeapon(weaponName) linear-scans Profiles for a matching Weapon key — used by WeaponFx to resolve enemy weapon FX by name, the mirror of how it resolves player weapons via WeaponConfig.

WeaponFx bridge and the widened WeaponFired packet​

Player weapon FX (impact/explosion sounds) are looked up by weapon name in WeaponConfig. Enemy weapons are a different name (EnemySMG, not SMG) living in a different config module, so a single client FX controller needs a single resolver that checks both. WeaponFx.resolve(weaponName) checks WeaponConfig[weaponName] first, then falls back to EnemyCombatConfig.FindByWeapon(weaponName), returning { ImpactSound?, ExplodeSound? } either way (or an empty table if neither matches). WeaponEffectsController.client.luau calls this for WeaponFired/WeaponImpact/ExplosionAt instead of indexing WeaponConfig directly — this is the only client-side change needed to render enemy weapon FX through the existing tracer/spark/explosion rendering code.

This works because the WeaponFired packet's shooter field was widened from Player to Instance so it can carry either a Player (player guns) or an enemy Model (EnemyWeapon fire):

local WeaponFired = Packet(
    "WeaponFired",
    Packet.Instance :: Instance, -- shooter (Player or enemy Model)
    Packet.String,               -- weaponName
    Packet.Vector3F32,           -- origin (muzzle)
    Packet.Vector3F32,           -- endpoint (hit position or max-range point)
    Packet.Boolean8              -- isHit
)

WeaponEffectsController ignores WeaponFired only when shooter == player (the local player's own gun already drew its own tracer client-side); an enemy Model shooter is never equal to a Player instance, so enemy shots always render for every client, including the player they're aimed at. See the WeaponFired row in the Networking Map for the full packet contract.

Lifecycle and cleanup​

EnemyBrain.Register(model, archetypeName) is idempotent (returns immediately if the model is already registered) and requires the model to have both a Humanoid (via FindFirstChildOfClass) and a root part (PrimaryPart or HumanoidRootPart) — if either is missing, registration silently no-ops and the enemy stays unarmed. On success, one Janitor is created per record (cleaner) and two connections are added to it, both tagged "Disconnect":

  • humanoid.Died → EnemyBrain.Unregister(model)
  • model.AncestryChanged (fires when parent becomes nil) → EnemyBrain.Unregister(model)

EnemyBrain.Unregister(model) removes the record from the module-level records table and calls cleaner:Destroy(). This covers both lifecycle exits an enemy can take: dying (Humanoid.Died) and being despawned without dying (wave Despawn/Destroy, or any other code that removes the model from the DataModel — see EnemySpawner → WaveHandle lifecycle). There is no Destroy/Cleanup distinction here (unlike some other Janitor-owning modules in this codebase) because an unregistered enemy record has no further use — the Janitor is always fully torn down.

Within tick() itself, a record whose root.Parent is falsy or whose humanoid.Health <= 0 is skipped for that tick (continue) rather than acted on — the actual removal from records happens asynchronously via the Died/AncestryChanged connections above, so there's a brief window (within the same frame) where a dead enemy's record can still exist but is simply not ticked.

Edge cases​

CaseBehavior
No target found (no living, rooted player)stepMovement halts the enemy in place (MoveTo(currentPosition)); stepFiringRanged resets fireState to "Idle" so the next valid target starts a fresh burst.
Target dies or leaves mid-burstNext tick's targetRoot lookup fails, rec.target is re-acquired via nearestPlayer (or left nil if no one is left), and a stale "Bursting" state is abandoned the same way as the out-of-range/LOS-blocked cases.
Target goes out of Range mid-burstFiring is suspended; a "Bursting" state resets to "Idle" (see the telegraph-reset fix); movement keeps closing.
Line of sight blocked mid-burstSame reset-to-"Idle" behavior as out-of-range; the enemy holds fire and lets movement reposition rather than trying to flank.
Friendly fire (enemy vs. enemy, enemy vs. friendly NPC)Physically impossible by design — CombatService.ApplyToModel gates every hit through Factions.canDamage, and Enemy -> Enemy / Enemy -> Friendly are not in the allow table.
Wave despawn while enemies are armedEnemyWave's Despawn/Destroy removes the enemy Model from the DataModel, which fires model.AncestryChanged with a nil parent, which calls EnemyBrain.Unregister — the brain record and its Janitor are torn down in the same tick the model is destroyed, with no dangling references.
Archetype has no EnemyCombatConfig profileEnemyBrain.Register returns early; the enemy spawns and is fully visible/collidable but never moves toward or fires at players.
Enemy model missing Humanoid or root partEnemyBrain.Register returns early without warning (mirrors EnemySpawner's existing tolerance for placeholder/incomplete rigs during early development).

Studio setup​

EnemyAssets rig requirements​

An enemy Model in ServerStorage/EnemyAssets/ needs the same minimum viable rig that EnemySpawner already requires for spawning at all: a Humanoid and a PrimaryPart or HumanoidRootPart. EnemyBrain.Register re-checks both of these independently and silently skips arming the enemy if either is missing — so a rig that spawns fine but never moves or fires is almost always missing one of these two parts.

Optional Muzzle attachment​

For a visually accurate origin, add an Attachment named exactly Muzzle anywhere in the rig's descendant hierarchy (typically welded to a held weapon model's barrel tip). EnemyWeapon.MuzzleOrigin finds it via model:FindFirstChild("Muzzle", true) (a recursive search) and fires from its WorldPosition. Without one, fire still works — it falls back to the root part's CFrame offset by the profile's MuzzleOffset, a perfectly playable art-less placeholder. Add the attachment (and a welded weapon model, and optional FireAnimId/SwingAnimId) whenever art is ready; no code changes are needed either way.

Arming an archetype: the two-registry relationship​

This is the most common setup mistake, so it's worth stating explicitly: an archetype needs entries in BOTH registries to be a functioning armed enemy.

  1. EnemySpawnerConfig.Archetypes[name] — required for the archetype to spawn at all (Model name, Health, WalkSpeed, DefaultRadius, optional Faction). See Enemy Spawner → Tuning.
  2. EnemyCombatConfig.Profiles[name] — required for the spawned enemy to be armed (move toward and fire at players). Keyed by the same archetype name as above.

An archetype with only #1 spawns, walks nowhere on its own, and never fires — useful for cosmetic/decorative NPCs or placeholder testing before combat tuning is ready. An archetype with only #2 (a profile with no matching spawner entry) is simply dead config — EnemySpawner.placeAt is the only call site for EnemyBrain.Register, so a profile with no way to spawn the archetype never gets used. There is no validation or warning today if these two registries drift out of sync (e.g. renaming an archetype in one but not the other) — check both tables by hand when adding or renaming an archetype.

Verifying combat in Studio​

No additional Studio-side wiring is required beyond the two config entries above and the rig requirements — EnemyBrain.Init() is called once automatically by EnemyCombatSystemLoader.server.luau at server start, the same pattern as EnemySpawnerSystemLoader.server.luau calling EnemySpawner.Init(). Spawn a wave with an archetype that has both registry entries and the enemy should path toward the nearest player and open fire once in range.

Gotchas​

Telegraph and burst values are tuned by feel, not measured

ProjectileSpeed, Spread, Telegraph, and the burst/cooldown ranges directly control how dodgeable and how punishing each archetype is. There is no automated test for "is this fair" — these are Studio-playtest-and-adjust knobs, the same as PATH_BUDGET_PER_TICK/REPATH_INTERVAL/REPATH_THRESHOLD/TICK_HZ at the top of EnemyBrain.luau. Adjust archetype values in EnemyCombatConfig directly; avoid touching EnemyBrain's tick/path constants unless movement itself feels laggy or pathfinding spikes with large waves.

Cosmetic bullet/throwable templates are optional, not required

EnemyWeapon.FireProjectile's cosmetic bullet (ServerProjectile.spawnRocket) and EnemyWeapon.Lob's throwable charge (ServerProjectile.spawnThrowable) both look up a template by profile.Weapon in ReplicatedStorage/WeaponAssets. If the named template doesn't exist yet, both functions are nil-safe — the shot/lob still fires, damages, and broadcasts its FX packet; it just has no visible travelling model. Add WeaponAssets/EnemySMG (etc.) whenever art is ready; this is a drop-in, no code change.

Re-engagement always restarts the burst from scratch

By design (see the telegraph-reset fix), an enemy that loses LOS or range mid-burst does not "remember" how many shots it had left — it goes back to "Idle" and rolls an entirely new BurstMin–BurstMax count next time it can see and reach the target. This is intentional fairness behavior, not a bug: do not "fix" it by trying to persist shotsLeft/nextShotAt across an interruption, as that would let a player skip past a sniper's telegraph window by breaking LOS for a single frame.

Data flow​

sequenceDiagram
    participant B as EnemyBrain (10 Hz tick)
    participant W as EnemyWeapon
    participant FC as FastCast2 (bulletCaster)
    participant CS as CombatService
    participant Fx as WeaponEffectsController (all clients)

    Note over B: tick(): reacquire target -> stepMovement -> stepFiring
    B->>B: stepFiringRanged: fireState machine (Idle -> Bursting -> Cooldown)
    B->>B: hasLineOfSight? in Range? else reset "Bursting" -> "Idle"
    B->>W: fireOneShot -> EnemyWeapon.FireProjectile(model, profile, origin, targetPos)
    W->>FC: cast bullet at ProjectileSpeed (+ Spread)
    FC-->>W: LengthChanged (steps optional cosmetic part)
    FC-->>W: Hit(target) OR miss-timeout backstop
    W->>CS: CombatService.ApplyToModel(model, humanoid, Damage, "Bullet", enemyModel)
    CS->>CS: Factions.canDamage("Enemy","Player") gate
    CS->>CS: HealthManager.ApplyDamage (armor mitigation)
    W->>Fx: Packets.WeaponFired(shooter=enemyModel, weaponName, origin, endpoint, isHit)
    Fx->>Fx: WeaponFx.resolve(weaponName) -> WeaponConfig or EnemyCombatConfig.FindByWeapon
    Fx->>Fx: render tracer + impact FX (shooter is never == local Player, so always renders)
