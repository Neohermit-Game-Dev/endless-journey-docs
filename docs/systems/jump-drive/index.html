Jump Drive

A server-authoritative, player-initiated biome transition: a charge gauge fed by deposited Energy tools, a party vote, and a phased wormhole sequence that swaps workspace.CurrentBiome. It replaces the old ambient BiomeChange orchestrator event — biome change used to happen to players on a random roll; now it is something a party decides to do.

See the design spec at docs/_superpowers/specs/2026-09-15-jump-drive-biome-transition-design.md for the full rationale and decision log (SDD artifacts under _superpowers/ are excluded from the published Moonwave site, so this is a repo path, not a doc link).

How it works​

The charge gauge​

A single scalar 0..JumpDriveConfig.MAX_CHARGE, server-authoritative and global (one drive for the whole train, not per player). It does not decay. ReqDepositJumpCharge(bench) mirrors TrainFuelManager.handleRefuel: an isDepositing guard serializes concurrent deposits, tools are gathered via EnergyToolHelper.GatherEnergyTools and consumed smallest-tier-first (so a large stockpile isn't spent on a small top-up), and no tool is ever consumed without crediting the charge it bought. JumpDriveConfig.EnergyChargeValue maps tier to charge, the same shape as ResearchConfig.EnergyFuelValue.

Phase machine​

JumpDriveManager owns a single server-side phase. Every advance is guarded by a generation nonce, so a scheduled callback left over from a previous jump can never advance a later one (the same pattern TrainFuelManager.reschedule() uses).

stateDiagram-v2
    [*] --> Idle
    Idle --> Ready: gauge reaches MAX_CHARGE
    Ready --> Voting: a player starts a jump vote
    Voting --> Ready: vetoed, or expires with no > yes
    Voting --> Engulf: vote passes (charge consumed)
    Engulf --> InWormhole: EngulfDuration elapsed
    InWormhole --> Exit: biome ready AND MinWormholeHold elapsed
    InWormhole --> Exit: MaxWormholeHold watchdog fires
    Exit --> Idle: ExitDuration elapsed, rewards granted
PhaseMeaning
IdleGauge not full; deposits accepted
ReadyGauge full; a vote can be opened
VotingVote open, countdown running (VoteDuration)
EngulfBlack hole grows ahead of the train and swallows it (EngulfDuration)
InWormholeHeld while the destination biome prepares (MinWormholeHold..MaxWormholeHold)
ExitLightspeed burst out into the new biome (ExitDuration)

The whole state — phase, gauge, and ballots — travels in one JumpStateSync broadcast rather than three, so a client can never render a phase and a gauge from two different moments. phaseEndsAt is a workspace:GetServerTimeNow() deadline; clients extrapolate their own countdown against it (the same prediction pattern TrainStateSync uses for the fuel bar), so there's no per-frame server traffic. InWormhole broadcasts phaseEndsAt = 0, meaning indefinite — hold the current visual state until the next broadcast; clients must treat 0 as "no known end," never as "already expired." Joining players get the current snapshot via a JoinSync sender ("JumpDrive"), run once the client announces readiness with ClientReady — not from Players.PlayerAdded, which is unreliable (see Join-Sync Snapshot Handshake). JumpDriveGuiController needs no client-side cache for this: phaseEndsAt is always a server-supplied absolute timestamp, and countdownText() already renders "--" when it is unset, so a dropped or delayed snapshot just leaves the countdown honestly blank rather than wrong.

The vote​

Opening a vote (ReqStartJumpVote) requires standing at the bench and phase Ready; the opener is recorded as an automatic yes. Casting a ballot (ReqCastJumpVote) has no proximity check — see "Why the vote banner is pushed, not bench-gated" below — and may be changed freely while the countdown runs. Players.PlayerRemoving drops a leaver's ballot so they can't hold a decision hostage.

Resolution is a pure function so it can be exercised in isolation (JumpDriveManager._resolveVoteForTest exposes it for a Studio command-bar check):

resolveVote(yes, no) -> yes > 0 and no <= yes

It passes if at least one player approved and the objectors do not outnumber them; abstaining (AFK, loading, never walked to the bench) is neutral and can never deadlock a jump. The countdown also resolves early — as soon as every present player has voted, or as soon as no remaining ballot could change the outcome — so a decided vote doesn't sit on screen for the rest of the 60 seconds.

Why the vote banner is pushed, not bench-gated​

Abstaining is neutral in resolveVote. If casting a ballot required standing at the bench, everyone who never walked over would abstain — over a 60-second window mid-combat, that's most of the party. The vote would then resolve on the initiator's lone yes every time: no > yes is nearly impossible to reach with a single voter, so the veto would exist in the resolution rule and never fire in practice. Pushing a non-modal banner to every player the moment Voting starts (JumpDriveGuiController) is what makes the vote a vote — opening it still requires the bench; casting a ballot in response to the pushed banner does not. The banner must not capture input (no ModalEnabled, nothing over the crosshair) so a player under attack can keep fighting and vote with one click when they choose to.

Cross-system state during a jump​

Signals.OnJumpPhaseChanged(phase: string) is the single broadcast point for suspending world activity. JumpDriveConfig.IsJumpActive(phase) is true for Engulf/InWormhole/Exit (not Voting — the train runs normally while players decide). Five consumers:

ConsumerBehavior while IsJumpActive
JunkServiceCurrentState.IsSpawning = false; restored on return to Idle
EventOrchestratorSetJumpPaused(true) — odometer and channel ticking suspended, and any Active handler is force-finished
TrainFuelManagerSetJumpFreeze(true) — drain rate pins to 0; ApplyFuelDamage early-returns
TrainShieldManagerSetJumpFreeze(true) — ApplyDamage early-returns
QuestSourcesLoaderReports QuestConfig.Metrics.BiomeJumps progress once, on the IsJumpActive -> false edge (arrival, not vote-pass)

Why SetTrainStarted is not reused to halt junk spawning​

JunkService already gates spawning on Signals.SetTrainStarted, which looks like the obvious signal to reuse for a jump. It is not: EventOrchestrator.Init wires SetTrainStarted(true) to EventOrchestrator.Reset(). Re-firing it after a jump would silently zero the event odometer and desynchronize encounter pacing. OnJumpPhaseChanged is a dedicated signal precisely so the jump doesn't carry that invisible side effect.

Why jumping despawns an active encounter wave​

EventOrchestrator.SetJumpPaused(true) calls each channel's existing activeFinish() — the same path the MaxActiveDistance watchdog and Reset() already use. PirateAttackEvent registers its spawned wave as ctx.janitor:Add(wave, "Destroy"), so force-finishing it despawns any surviving pirates. This is deliberate, not a side effect: it's what makes "players are safe inside the wormhole" actually true — without it, a live wave would keep shooting people through the transition — and it doubles as a panic button, a balance lever the later chase-timer/pressure-loop spec should be aware of.

The biome seam​

-- inside JumpDriveManager
local function prepareBiome(biomeId: string, done: () -> ())
    workspace:SetAttribute(JumpDriveConfig.BIOME_ATTRIBUTE, biomeId)
    done()
end

This local function — not a separate module — is the entire seam the future biome-content overhaul replaces. Today it writes the CurrentBiome attribute and calls done() immediately. The InWormhole hold already waits on done() (floored by MinWormholeHold, capped by the MaxWormholeHold watchdog), so real scenery/weather/hazard load time is absorbed with no other change to this module — the overhaul only needs to replace prepareBiome's body.

Rewards on arrival​

Two separate call sites fire on arrival, not one:

JumpDriveManager.finishJump, on the Exit -> Idle transition, grants CoinManager.AddCoins, XPManager.AddXP, and BattlePassManager.AddExp to every player in Players:GetPlayers() (each pcall-wrapped so one player's DataStore hiccup can't rob the rest of the party). Values live in JumpDriveConfig.ArrivalReward. JumpDriveManager never requires QuestManager.

Quest progress is a different module entirely: QuestSourcesLoader listens to Signals.OnJumpPhaseChanged itself and reports QuestManager.ReportPartyProgress(QuestConfig.Metrics.BiomeJumps, 1) once, on the same IsJumpActive -> false arrival edge (see the cross-system table above). It lives there, not in JumpDriveManager, because of the convention documented on QuestConfig.Metrics itself: every quest metric gets its source wired in QuestSourcesLoader, so all quest sources stay discoverable in one file instead of being scattered across each feature that can grant progress.

Client presentation​

JumpTransitionController owns one Janitor per jump and captures Lighting's pre-jump values before applying any post-processing, registering their restoration on that Janitor — a mid-jump disconnect, error, or out-of-order phase packet can never leave a player's Lighting permanently altered. Nothing in this system takes camera or movement control; the player keeps playing while the world changes around them.

JumpDriveGuiController drives both GUI surfaces off the single JumpStateSync payload so they can never disagree. It sets ResetOnSpawn = false on both cloned ScreenGuis in code, regardless of how the template was authored — a clone with ResetOnSpawn = true would be destroyed on the player's first respawn, silently killing the bench panel or banner for the rest of the session.

Not in scope​

These are deliberately deferred to their own future specs; each has a named seam so an implementer doesn't need to touch anything documented above:

  • Destination choice. Today pickDestination() rolls uniformly at random (never the current biome). A premium-unlock → Research node → picker chain is deferred; the seam is pickDestination() itself, a single function.
  • Chase timer / pressure loop. A timer forcing a jump, with escalating warnings and a boss encounter, is deferred. The seam is the Exit -> Idle transition, already broadcast via OnJumpPhaseChanged.
  • Biome content overhaul — per-biome scenery, skybox, lighting, weather, ambience, spawn tables, hazards. The seam is prepareBiome(biomeId, done) (see above).
  • Reward scaling by biome tier or jump count — flat values belong with the content overhaul, which is what introduces tiers.
  • EnemySpawner is not an OnJumpPhaseChanged consumer: it has no ambient spawn loop of its own, only SpawnAt/SpawnWave called from event handlers, so gating at EventOrchestrator is sufficient.
