Quests (Daily & Weekly)

A rotating, ProfileStore-backed quest system layered on top of the coin/XP economy. Four buckets — Personal/Party × Daily/Weekly — rotate on a global, deterministic schedule so every player and server in a given period sees the same active quests. A fifth, non-rotating Season scope additionally feeds the Battle Pass. Progress is server-authoritative; rewards pay coins, exp, and an optional battle pass EXP feed. The system is split shared/server/client exactly like Perks.

How it works​

Buckets​

Each period (Daily or Weekly) rotates a fixed count of quests per category, set by QuestConfig.Counts:

ScopePersonalParty
Daily12
Weekly11

Personal quests credit only the player who performed the action (e.g. collecting junk). Party quests credit every player in the server for ownerless world events (enemy kills, train distance) — a shared team objective, but the reward is still claimed and paid out per player.

Global rotation​

The active quest ids for a scope are never stored — they're recomputed deterministically from the period index alone:

QuestState.selectQuests(scope: "Daily" | "Weekly" | "Season", periodIndex: number): { string }

A seeded Fisher-Yates shuffle (distinct large-prime seeds per category so Personal and Party picks don't correlate) runs over the sorted id pool for that scope+category, sliced to Counts, then re-sorted for stable display order. Given the same periodIndex, every machine — client or server, any server in the universe — produces the identical set. Only progress, claimed flags, period indices, and lifetime stats persist on the PlayerQuests profile; the set itself is derived, not saved.

Period math​

Period indices come from os.time() (UTC), never client input:

FunctionFormula
QuestState.dayIndex(now)floor((now - DailyResetOffset) / 86400)
QuestState.weekIndex(now)floor((now - WeeklyResetOffset) / 604800)
QuestState.dailyExpiresAt(now)Unix timestamp the current daily period ends
QuestState.weeklyExpiresAt(now)Unix timestamp the current weekly period ends

Daily rolls at 00:00 local (QuestConfig.DailyResetOffset); Weekly rolls Monday 00:00 local (QuestConfig.WeeklyResetOffset, a 4-day base offset — the Unix epoch was a Thursday, so shifting 4 days aligns week starts to Mondays). Both offsets are derived from QuestConfig.ResetTimezoneOffset — a fixed seconds-from-UTC offset defining the timezone "midnight" is measured in (pre-launch default US Eastern, -5 * 3600). It's fixed, so it does not track daylight saving; set it to 0 for pure UTC resets (DailyResetOffset = -ResetTimezoneOffset; WeeklyResetOffset = 345600 - ResetTimezoneOffset). The expiry functions are sent to the client so it can drive a live countdown with no client-side period math.

Season quests​

A fifth Scope = "Season" exists alongside Daily/Weekly, dedicated to feeding the Battle Pass. It doesn't rotate — selectQuests("Season", periodIndex) returns the entire curated set (Personal ids then Party ids, each sorted), not a Counts-limited shuffle-and-slice, so every Season quest is active for the whole month. Its period index is BattlePassState.seasonIndex(now) (a calendar-month index, not a quest-owned index), so a season's quests reset in lockstep with the battle pass itself — the profile's SeasonPeriod/SeasonProgress/SeasonClaimed fields follow the exact same rollover/auto-grant pattern as Daily/Weekly.

The shipped pool (SeasonJunk, SeasonKills, SeasonDistance) pays Coins = 0, Exp = 0 and a large BPExp (3000 each) — Season quests exist purely to move the battle pass track, not the coin/XP economy. Any quest, of any scope, can additionally carry an optional Reward.BPExp: number?; the shipped Daily/Weekly pool also pays smaller BPExp amounts alongside normal coins/exp, so ordinary questing keeps the pass moving too.

Attribution​

Two entry points on QuestManager mirror XPManager.AddXP/AddPartyXP:

function QuestManager.ReportProgress(actor: Player, metricKey: string, amount: number)
function QuestManager.ReportPartyProgress(metricKey: string, amount: number)
FunctionHas an actorAdvances
ReportProgressYes (e.g. junk collection)Bumps the actor's own Lifetime metric, advances the actor's Personal quests, and fans the same amount out to every online player's Party quests for that metric
ReportPartyProgressNo (e.g. enemy died, train distance)Advances every online player's Party quests and bumps each player's Lifetime metric total

Either path calls ensureCurrent first (rolls any elapsed period before applying progress) and only replicates (QuestStateSync) to players whose progress actually changed.

Claim and auto-grant sweep​

function QuestManager.ClaimQuest(player: Player, questId: string): (boolean, number, number, number)

Manual claim is wired to Packets.ReqClaimQuest and invokes ClaimQuest, which validates in order — profile loaded, quest exists, quest is in the currently active set for its scope, progress ≥ target, not already claimed — and returns (ok, reasonCode, coinsGranted, expGranted). The claimed flag is set before the reward is granted, so a re-entrant or duplicate call cannot double-pay: the second call fails fast with ALREADY_CLAIMED.

The auto-grant sweep runs inside ensureCurrent (called on join, before every progress report/claim, and on the periodic rollover tick). When a scope's stored period index differs from the current index, it walks the old set (selectQuests(scope, oldPeriodIndex)) and grants any quest that was completed but never claimed, before resetting that scope's Progress/Claimed maps. A player who finishes a quest right before rotation and never opens the claim UI is still paid.

Both paths share one grantReward function, which pays coins/exp then fires Signals.OnQuestRewardGranted(player, quest.Reward). BattlePassManager connects to this signal and reads reward.BPExp off the payload regardless of whether the grant came from a manual claim or an auto-grant sweep — see Battle Pass — EXP earning.

Sources​

QuestSourcesLoader (gameplay-only — safe to run in the lobby place, where these events simply never fire) wires the three QuestConfig.Metrics to their gameplay triggers:

MetricCategoryTrigger
EnemyKillsPartyHumanoid.Died on any CollectionService-tagged ENEMY_TAG ("EnemyNPC") model — one Janitor per tracked enemy
DistanceTravelledPartyA recurring task.wait(DISTANCE_TICK_SECONDS) loop credits DISTANCE_PER_TICK while Signals.SetTrainState reports the train running
JunkCollectedPersonalSignals.OnJunkCollected — fired by JunkService once per successful finalized junk grab (collector, junkId)

Adding a quest that reuses one of these Metric keys needs no source code change — only a new entry in QuestConfig.Quests. Wiring a brand-new metric needs one new source hookup in QuestSourcesLoader (see Tune Quests).

Perk seam​

profile.Data.Lifetime is a { [key]: number } table that is never reset by rollover — distinct from the per-period Progress maps. advancePlayer bumps Lifetime["QuestsCompleted"] by 1 on every below-target → at-target transition, and both report functions bump Lifetime["metric:"..metricKey] by the raw reported amount.

function QuestManager.GetLifetimeStat(player: Player, key: string): number

This is a deliberate seam for a future PerkConfig unlock criterion (e.g. "unlock this perk after QuestsCompleted >= 25") — not wired to any perk this cycle.

Client​

QuestClient is a GUI-agnostic read-model, the same shape as PerkClient. It caches the authoritative QuestStateSync snapshot, recomputes the active set client-side with the same QuestState.selectQuests the server uses (so client and server never disagree), and exposes a QuestView descriptor:

export type QuestView = {
    Id: string, Scope: "Daily" | "Weekly" | "Season", Category: "Personal" | "Party",
    DisplayName: string, Description: string, Icon: string?, Metric: string,
    Target: number, Progress: number, IsComplete: boolean, IsClaimed: boolean,
    IsClaimable: boolean, RewardCoins: number, RewardExp: number, ExpiresAt: number,
}

Queries: GetQuests/GetActiveQuests/GetCompletedQuests/GetQuest, plus GetLifetimeStat and a fire-and-forget Claim(questId) command. A Changed signal fires on every snapshot update. No GUI ships this cycle — a future screen requires QuestClient and subscribes to Changed, exactly like PerkClient.

Gotchas​

Changing STORE_NAME orphans saved quest data

QuestConfig.STORE_NAME ("PlayerQuests") is the ProfileStore key for progress, claimed flags, and the never-reset Lifetime table. Changing it points every player at a brand-new, empty profile — all prior quest progress and lifetime stats are orphaned (not deleted, just unreachable). It must stay identical in the lobby and gameplay places for the cross-place session handoff to share the same record.

Personal progress from ReportProgress also advances Party quests

ReportProgress(actor, metricKey, amount) is not Personal-only — it fans the same amount out to every online player's Party quests for that metric, then additionally advances the actor's Personal quests. A quest author reusing a Personal-sourced metric (JunkCollected) for a new Party quest gets it "for free" — no new source wiring needed.

The active set query needs the correct period index

QuestState.selectQuests takes a periodIndex, not a timestamp. Always derive it via QuestState.dayIndex/weekIndex(os.time()) (server) or read it from the cached QuestStateSync snapshot (client, via QuestClient) — never hardcode or guess an index.

Data flow​

sequenceDiagram
    participant Source as QuestSourcesLoader
    participant Manager as QuestManager (server)
    participant Client as QuestClient (owning client)

    Note over Source,Manager: REPORT
    Source->>Manager: ReportProgress(actor, metric, amt) / ReportPartyProgress(metric, amt)
    Manager->>Manager: ensureCurrent() — roll elapsed periods first
    Manager->>Manager: advancePlayer() bumps Progress[questId] (clamped to Target)
    alt progress changed
        Manager->>Client: QuestStateSync(periods, expiry, progress, claimed, lifetime)
    end

    Note over Manager: COMPLETE (progress[questId] >= Target)
    Manager->>Manager: bumpLifetime("QuestsCompleted", 1) on the below→at-target transition
    Client->>Client: QuestView.IsClaimable becomes true (IsComplete and not IsClaimed)

    Note over Client,Manager: CLAIM
    Client->>Manager: ReqClaimQuest(questId)
    Manager->>Manager: validate (active set, progress >= Target, not claimed)
    Manager->>Manager: claimed[questId] = true (BEFORE grant — idempotent guard)
    Manager->>Manager: CoinManager.AddCoins(.., "Quest:"..questId); XPManager.AddXP(..); Signals.OnQuestRewardGranted:Fire(player, reward)
    Manager-->>Client: (ok, reasonCode, coinsGranted, expGranted)
    Manager->>Client: QuestStateSync (reconciled snapshot)
