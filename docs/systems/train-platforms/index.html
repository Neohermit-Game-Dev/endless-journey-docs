Train Platforms

The train starts with 2 of its 6 platforms. Players build platforms 3–6 in order by holding F at the rear seam, which deposits Wood and Metal from the shared Material Pool. A completed platform appears behind a neon-wall "extrude" reveal.

How it works​

  • Order: at boot the server numbers every Model under Workspace.TrainPlatforms: FrontPlatform (FRONT_PLATFORM_NAME) is 1, the rest by distance from it. It writes the number to a PlatformIndex attribute. No Studio setup is needed; adding or removing a platform Model in Studio changes the count (add a Costs entry for each new locked index).
  • Starting count: STARTING_PLATFORMS platforms start built. The server raises any value below 2 to 2 (with a warn); a value above the platform count means all start built.
  • Boot: platforms above the starting count move to ServerStorage/LockedPlatforms. A copy with every CollectionService tag removed goes to ReplicatedStorage/PlatformGhosts/<index> (tags must go: GetTagged also returns ReplicatedStorage instances, so a tagged copy would count as a BuildArea). Each locked platform gets Seam and SeamAxis attributes.
  • State: attributes on TrainPlatforms — BuiltCount, DepositedWood, DepositedMetal (progress of platform BuiltCount + 1). Attributes replicate to late joiners, so there is no JoinSync sender.
  • Deposit: the handler moves min(cost − deposited, pool) of each material via MaterialPool.Spend, with no yield between reading and writing. A second request in the same frame sees the new totals; a request for an already-finished platform returns STALE. Material is never spent past the cost.
  • Build: when both materials are full, the locked platform is parented back into TrainPlatforms. Placement and drop code find its BuildArea / DroppableSurface tags at run time — no placement change.
  • Client: the ghost and billboard show only while the prompt is shown (PromptShown / PromptHidden). The prompt is disabled in build mode, where F toggles grid mode.
  • Reveal: on ChildAdded of a platform not present at load, the client hides the real platform (LocalTransparencyModifier) in the same callback, extrudes a visual copy behind a neon wall (SWEEP_DURATION), then shows the real one. Collision is live the whole time.

Dev command​

/expand (alias /platform) in chat builds the next platform at once, free, and plays the normal reveal. It sends ReqDevExpandPlatform; DevCommandsService gates it on place owner / group rank 250+ and calls PlatformExtendService.DevBuildNext(). Any Wood/Metal already deposited toward that platform is cleared (it was spent from the pool).

Fallback reveal

If the scan sweep is rejected after playtesting, replace only the body of playReveal with a dust-cloud burst that shows the platform while it is hidden.

Tuning​

All values are in PlatformConfig: STARTING_PLATFORMS (minimum 2), Costs (3 → W50/M30, 4 → W90/M55, 5 → W155/M90, 6 → W270/M160; ×1.75 per platform), HOLD_DURATION, PROMPT_DISTANCE, SERVER_DISTANCE_TOLERANCE, DEPOSIT_COOLDOWN, ghost colour/transparency, and SWEEP_*. Sound ids: SoundConfig keys PlatformDeposit, PlatformBuilt.

Not included​

No persistence (platforms reset with the server, like the pool), no out-of-order building, no refunds or demolition.
