Disruption / Maintenance

On server shutdown or maintenance the game notifies players, force-saves their persisted data, and teleports them to the lobby place. Transient run state (fuel, shield, health, stamina, in-progress research, placed items, ammo, backpack junk) intentionally resets — session-state recovery is out of scope. DisruptionCoordinator is the server-side authority; ProfileStore session-locking is the correctness backstop underneath it.

At a glance​

LayerFileRole
Clientsrc/StarterPlayer/StarterPlayerScripts/DisruptionController.client.luauShows the non-blocking countdown notice; no input is blocked
Serversrc/ServerStorage/SharedModules/DisruptionCoordinator.luauTrigger funnel (automatic + manual) and the full drain sequence
Serversrc/ServerScriptService/DisruptionSystemLoader.server.luauBootstrap — calls DisruptionCoordinator.Initialize(), runs in both the lobby and gameplay places
Serversrc/ServerStorage/SharedModules/PersistenceRegistry.luauForce-save registry; gameplay managers register a flush callback in their Initialize
Configsrc/ReplicatedStorage/SharedModules/Configs/DisruptionConfig.luauLobby place id, timing budgets, admin command, player-facing copy

Packets: DisruptionBegan — see Networking Map Signals: none — DisruptionController reuses Signals.RequestNotification for the countdown toast, but the disruption system itself defines no signals

How it works​

Trigger​

Two paths funnel into the same drain sequence, guarded by an isDisrupting flag so it only ever runs once:

  • Automatic — game:BindToClose fires beginDisruption("shutdown") when Roblox shuts the server down.
  • Manual — DisruptionCoordinator.BeginMaintenance(reason) (an admin chat command, DisruptionConfig.ADMIN_COMMAND, default "!maintenance") publishes to every server in the universe via MessagingService, so a fleet-wide maintenance drain doesn't require restarting each server individually. If the publish fails, it falls back to draining just the local server.

Drain sequence​

beginDisruption(reason) runs in order, all timed from a single drainStart:

  1. Notify — broadcasts the DisruptionBegan packet (reason, NOTICE_SECONDS); each client shows a non-blocking countdown via Signals.RequestNotification.
  2. Wait — task.wait(NOTICE_SECONDS) so players can read the notice.
  3. Flush — PersistenceRegistry.FlushAll(FLUSH_TIMEOUT_SECONDS) force-saves every registered profile. profile:Save() is used, not EndSession(), so players stay connected until the teleport.
  4. Teleport — TeleportService:TeleportAsync(LOBBY_PLACE_ID, …) per player, retried up to TELEPORT_RETRIES times. Skipped entirely in Studio or when LOBBY_PLACE_ID <= 0 — players then disconnect with data already saved.
  5. Drain-wait — yields until the server empties or MAX_DRAIN_SECONDS (measured from drainStart, so steps 1–4 eat into the same budget rather than adding to it) elapses; leftover players disconnect with data already saved. Skipped in Studio, where no real teleport occurs and waiting would hang every Studio "Stop" for the full budget.

A player joining mid-drain is caught by Players.PlayerAdded, which starts a teleport attempt immediately — this cannot wait on the client, or the drain would never finish emptying the server. The DisruptionBegan notice, being a client render rather than drain bookkeeping, is instead registered with JoinSync and sent once that player's client announces readiness (or not at all, if the drain has already ended by then).

Correctness​

ProfileStore session-locking is the backstop: even if a save is in flight when a player reaches the lobby server, that server's StartSessionAsync waits for the old lock to release, so no data is lost. The explicit flush in step 3 just tightens the window and gives a "saved before we move you" ordering — it is not the only thing preventing data loss.

Force-save registrants​

PersistenceRegistry.Register(flush) is called from each manager's Initialize; FlushAll invokes every registered callback with a shared timeout. Current registrants: CoinManager, ArmorManager, PerkManager, QuestManager, SettingsManager, XPManager, BattlePassManager.

Known limitation​

Direct teleport to the lobby can bounce if the lobby place is also restarting during a universe-wide Roblox update. The reliable path is the manual maintenance command, which drains the gameplay place while the lobby stays up.

Gotchas​

MAX_DRAIN_SECONDS bounds the whole sequence, not just the final wait

Notice + flush + drain-wait together must fit under Roblox's ~30s BindToClose budget. Tuning NOTICE_SECONDS or FLUSH_TIMEOUT_SECONDS eats into the same budget rather than adding to it.

LOBBY_PLACE_ID = 0 skips the teleport, not the flush

While unset, the coordinator still runs the full notify/flush sequence — players just disconnect afterward instead of being teleported. Data is not lost, but there's no lobby to land in.

Data flow​

sequenceDiagram
    participant Trig as Trigger (BindToClose / admin command)
    participant Co as DisruptionCoordinator
    participant Pers as PersistenceRegistry
    participant Cl as DisruptionController

    Trig->>Co: beginDisruption(reason)
    Co->>Co: isDisrupting guard (idempotent)
    Co->>Cl: DisruptionBegan(reason, NOTICE_SECONDS) - all clients
    Cl->>Cl: Signals.RequestNotification countdown

    Co->>Co: task.wait(NOTICE_SECONDS)
    Co->>Pers: FlushAll(FLUSH_TIMEOUT_SECONDS)
    Pers->>Pers: profile:Save() per registered manager

    alt LOBBY_PLACE_ID > 0 and not Studio
        Co->>Co: TeleportAsync(LOBBY_PLACE_ID, player) per player, retry TELEPORT_RETRIES
    else Studio or unset
        Co->>Co: warn - players disconnect, data already flushed
    end

    Co->>Co: wait until server empties or MAX_DRAIN_SECONDS (from drainStart)

Tuning​

  • Config module: DisruptionConfig — src/ReplicatedStorage/SharedModules/Configs/DisruptionConfig.luau
FieldDefaultEffect
LOBBY_PLACE_IDgame-specific PlaceIdTeleport target. 0 skips the teleport (players disconnect after flush); also skipped automatically in Studio.
NOTICE_SECONDS4Seconds between showing the notice and starting the drain
FLUSH_TIMEOUT_SECONDS6Max seconds to wait for PersistenceRegistry.FlushAll() before proceeding anyway

TELEPORT_RETRIES3Retries per player on TeleportInitFailed

ADMIN_USER_IDS{}UserIds allowed to invoke the manual maintenance chat command
ADMIN_COMMAND"!maintenance"Chat command (case-insensitive, first word) that starts manual maintenance
NOTIF_TYPE"warn"Notification type passed to Signals.RequestNotification
DEFAULT_MESSAGE / REASON_MESSAGES—Player-facing copy, keyed by trigger reason (shutdown / maintenance)
