Tune Quests

Goal: Add a quest, adjust how many quests rotate in per period, or shift the daily/weekly reset boundary.

Steps​

  1. Add a quest. Open src/ReplicatedStorage/SharedModules/Configs/QuestConfig.luau and add an entry to QuestConfig.Quests:

    JunkDailyC = { Scope = "Daily", Category = "Personal", Metric = QuestConfig.Metrics.JunkCollected,
        Target = 60, DisplayName = "Junk Fanatic", Description = "Collect 60 junk",
        Reward = { Coins = 350, Exp = 160 } },
    • Metric must be one of QuestConfig.Metrics (EnemyKills, DistanceTravelled, JunkCollected). Reusing an already-wired metric needs no code change — QuestManager and QuestSourcesLoader pick it up automatically the next time QuestState.selectQuests includes it in the rotation.
    • To track a new kind of progress, wire it in src/ServerScriptService/QuestSourcesLoader.server.luau first: add a new key to QuestConfig.Metrics, then call QuestManager.ReportProgress(actor, metricKey, amount) (has an actor — credits Personal + fans out to Party) or QuestManager.ReportPartyProgress(metricKey, amount) (ownerless world event — Party only) from wherever the underlying game event fires. See Quests — Sources for the three existing examples.
    • Category ("Personal" or "Party") and Scope ("Daily" or "Weekly") determine which sub-pool the quest rotates into — see Quests — Buckets.

  2. Choose Target and Reward.

    • Target is the raw progress amount required (same units the source reports — e.g. junk count, enemy kills, distance units). Compare against similar existing quests of the same Scope/Metric to keep difficulty consistent (e.g. JunkDailyA = 25 vs JunkWeeklyA = 250, a 10x jump from daily to weekly).
    • Reward.Coins / Reward.Exp are paid once per claim via CoinManager.AddCoins(player, coins, "Quest:"..questId) (scaled by the Fortune perk's CoinGainBonus, like any other earned coins — see Economy) and XPManager.AddXP(player, exp). Scale both together with Target so effort-to-reward stays proportionate; weekly quests in the shipped pool pay roughly 8x their daily counterparts.
    • DisplayName/Description are shown by a future GUI via QuestClient's QuestView; Description should read as an activity sentence (e.g. "Collect 25 junk") since there's no separate progress-text field. Icon is optional (nil = none).

  3. Adjust Counts per period. QuestConfig.Counts controls how many quests of each category rotate in per scope:

    QuestConfig.Counts = {
        Daily = { Personal = 1, Party = 2 },
        Weekly = { Personal = 1, Party = 1 },
    }

    Raising a count (e.g. Daily.Party = 3) requires at least that many quests of that Scope+Category to exist in QuestConfig.Quests — QuestState.selectQuests clamps to math.min(count, #pool), so an under-populated pool silently rotates in fewer quests than configured rather than erroring. Add enough quest entries before raising a count.

  4. Shift reset boundaries. Resets happen at local midnight, where "local" is set by QuestConfig.ResetTimezoneOffset — a fixed offset in seconds from UTC (pre-launch default -5 * 3600 = US Eastern, the largest single Roblox player timezone). This is the one knob to change to re-timezone the whole system; set it to 0 for pure UTC. It's a fixed offset, so it does not follow daylight saving — during summer (EDT) resets land one wall-clock hour later. QuestConfig.DailyResetOffset (= -ResetTimezoneOffset, day rolls at 00:00 local) and QuestConfig.WeeklyResetOffset (= 345600 - ResetTimezoneOffset; the 4-day base aligns week starts to Monday since the Unix epoch was a Thursday) are derived from it — change ResetTimezoneOffset, not these two directly, unless you want the daily and weekly boundaries in different timezones. Changing any of them takes effect immediately for every player on their next ensureCurrent check (the periodic rollover tick, or their next join/progress/claim) — there's no migration needed, but changing a boundary mid-period can make the live rollover fire earlier or later than players expect for whichever period is in flight. Prefer changing these during a maintenance window (see Disruption) rather than live. Keep the value identical in the lobby and gameplay places (it's the same shared file) or the two places will disagree on which period is active.

Verify​

  1. Join in Studio with API Services enabled.
  2. Confirm QuestClient.GetQuests() (or a print in a test script) returns the expected active ids for the current period, matching what QuestState.selectQuests would compute server-side.
  3. Trigger the relevant source (collect junk, defeat a tagged enemy, or wait through a train-running distance tick) and confirm the matching quest's Progress advances and QuestClient.Changed fires.
  4. Complete a quest and call QuestClient.Claim(questId); confirm coins and exp are granted exactly once, and a second claim attempt fails with ALREADY_CLAIMED (result code 5).
  5. If you changed Counts, confirm the newly-added quest pool member actually appears in rotation (rotation is seeded by period index, so you may need to wait for a period boundary or temporarily lower ROLLOVER_CHECK_SECONDS to observe it sooner).

Gotchas​

Changing STORE_NAME orphans saved quest data

QuestConfig.STORE_NAME ("PlayerQuests") must stay identical in the lobby and gameplay places — it's the shared ProfileStore key that lets QuestManager's session-locking hand off cleanly across the teleport boundary. Changing it points every player at a brand-new, empty profile: all prior progress, claimed flags, and the never-reset Lifetime table (the perk seam) become unreachable. Only do this intentionally, and change it in both places together.

Removing a quest id that's currently active can strand progress

QuestState.selectQuests only picks from ids present in QuestConfig.Quests at call time. Deleting an id mid-period means any player with progress toward it simply loses visibility into that entry (the stored Progress[questId] value lingers harmlessly in the profile until the bucket resets, but nothing can claim it). Prefer retiring a quest by leaving it in the pool with an unreachable Target change only at a period boundary, or accept the stranded-progress edge case for a rarely-hit quest.
