Maintaining These Docs

Where Content Lives​

There are two sources of documentation:

  • Narrative pages (docs/) — the files you are reading now. Written by hand in Markdown and checked into this repository. Covers architecture, playbooks, getting-started guides, and everything that isn't a raw API reference.
  • API reference — generated automatically by Moonwave from doc-comments (--[=[...]=] blocks) in the Luau source under src/. Moonwave extracts these at build time; no separate documentation file is needed for module APIs.

Local Preview​

Install Moonwave globally once:

npm i -g moonwave@latest

Then, from the repo root:

CommandEffect
moonwave devStarts a live-reload local server. Edit any docs/ page or source doc-comment and the browser updates instantly.
moonwave buildProduces a static output in build/ for inspection. The CI pipeline runs this automatically — you rarely need it locally.

Publishing​

Pushing to main triggers a GitHub Action that:

  1. Runs moonwave build.
  2. Pushes the static output to the separate endless-journey-docs repository.
  3. GitHub Pages serves the result from that repo.

You do not need to run the build or push to endless-journey-docs manually.

The Discipline Rule​

When a code change touches a system, the same commit must also update:

  • That system's narrative page under docs/.
  • Any affected playbook in docs/playbooks/.
  • The networking map or signals map if a new packet or signal was added.

This extends the project's existing "record any new signal/packet" rule (see old guide § Recommended Update Process) to cover the Moonwave site. Keeping documentation and code in the same commit makes it easy to find the change context later and prevents the docs from silently drifting out of date.

tip

If the change is large (e.g. a new system), write the narrative page first as a draft, then implement the code, then finalize both in the closing commit. This forces you to articulate the design before you are buried in implementation details.

System page template​

Every page under docs/systems/ follows this H2 skeleton, in this order:

# <System Name>

<1 short paragraph: what it does, why it exists, authority model.>

## At a glance

| Layer | File | Role |
|---|---|---|
| Client | `src/...` | ... |
| Server | `src/...` | ... |
| Shared | `src/...` | ... |
| Config | `src/ReplicatedStorage/SharedModules/Configs/...` | ... |

**Packets:** `PacketA`, `PacketB` — see [Networking Map](../reference/networking-map.md)
**Signals:** `SignalA` — see [Signals Map](../reference/signals-map.md)

## How it works

### <one H3 per mechanism>
<paragraphs ≤ 4 sentences; show code for any call/shape being described>

## Data flow

<Mermaid sequenceDiagram>

## Tuning

<Config module link + relevant playbook links, bullet list>

## API

<Bullets linking Moonwave classes, e.g. [`QuestManager`](/api/QuestManager)>

Prose rules: paragraphs ≤ 4 sentences; enumerable facts in tables; anything invocable as code; bold sparingly; relative links between doc pages (../systems/foo.md style, matching existing pages); Mermaid over ASCII for any diagram.

Playbook template​

Every page under docs/playbooks/ follows this skeleton:

# <Task Name>

**Goal:** <one sentence>

## Steps

1. <one action per step; exact file paths; code blocks for edits>

## Verify

<How to confirm the change works in Studio.>

## Related

- <system page link>
- <API class links>

Adding a page or class (checklist)​

  • New doc page → add its id to .moonwave/sidebars.js in the right family (pages not listed there do not appear).
  • New @class in source → add it to the fitting [[classOrder]] section in moonwave.toml in the same commit (unlisted classes sink to an unsorted lump; a typo fails the build).
  • Adding a packet or signal → update docs/reference/networking-map.md / signals-map.md in the same commit.
  • Run moonwave build before pushing docs changes.
