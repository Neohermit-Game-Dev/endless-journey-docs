Backbone Modules

These seven modules are the cross-cutting infrastructure that everything else in Endless Journey wires through. Understanding them is prerequisite to safely modifying any system.

Signals​

What. An in-process event bus that decouples controllers and services from each other without direct require chains. Defined in src/ReplicatedStorage/SharedModules/Signals/init.luau.

Why. Direct module coupling creates a tangle of dependencies and makes load order fragile. Signals let a controller fire a named event (Signals.RequestShootingCamera) without knowing which other controllers are listening. This is the preferred pattern for gameplay events and UI intents.

How to use. require the module, then fire or connect named events. Signals are client-only and in-process — they do not cross the network. For cross-boundary traffic, use Packets.

See the full event catalogue in Signals Map.

Packets​

What. Typed network packet definitions. Defined in src/ReplicatedStorage/SharedModules/Packets/init.luau.

Why. Raw RemoteEvent / RemoteFunction usage scatters network contracts across the codebase, making it impossible to audit traffic or catch type errors. Packets centralises every channel in one place with defined types.

How to use. All client↔server traffic must go through Packets — never create ad-hoc RemoteEvent instances. When adding a new network channel, register it in Packets/init.luau and update the Networking Map in the Maintenance Guide.

Configs​

What. A directory of tuning tables at src/ReplicatedStorage/SharedModules/Configs/. Modules cover: Placement, Junk, Stamina, GrabHook, ShiftLock, Health, Shredder, JunkTool, Sound, and Notification.

Why. Keeping tunable values in config modules separates design decisions from code logic, makes auditing changes straightforward, and avoids touching behaviour code for what are purely numerical adjustments.

How to use. Prefer config changes over code changes when tuning gameplay numbers. require the relevant config module; do not hard-code magic numbers in controllers or server scripts. See the Config Map for the full list of tunables per module.

SoundManager​

What. The single entry point for all client-side audio — SFX, BGM, ambience, and looped sound beds. Defined in src/ReplicatedStorage/SharedModules/SoundManager/init.luau.

Why. Ad-hoc Sound instance creation leads to untracked audio, duplicate playback, and no central volume control. SoundManager owns all audio state.

How to use. require the module and call PlaySFX, PlaySFXAt, PlayLooped, PlayMusic, SetAmbience, or SetVolume. Never create Sound instances directly. Asset IDs, volumes, pitch ranges, playlists, and ambience beds all live in src/ReplicatedStorage/SharedModules/Configs/SoundConfig.luau. The client bootstrap script (SoundController.client.luau) calls SoundManager.Init() once on startup.

For a full guide see Sound System.

NotificationManager​

What. A signal-driven toast notification system. Defined in src/ReplicatedStorage/SharedModules/NotificationManager/init.luau.

Why. Centralising toast creation prevents duplicated UI code in every system that needs to surface feedback to the player (e.g., refuel errors on the train, collection results, stamina warnings).

How to use. Fire the relevant Signal to request a notification; NotificationController.client.luau listens and delegates to NotificationManager for rendering. Do not construct toast UI frames directly in other controllers.

For a full guide see Notification System.

Janitor​

What. The project's cleanup primitive, provided by the howmanysmall/janitor Wally package at Packages/Janitor.

Why. Hand-rolled { RBXScriptConnection } arrays and manual disconnect loops are error-prone, easy to forget, and hard to audit. Janitor provides a single, consistent cleanup API for any scope that owns connections or instances.

How to use. Create one Janitor per lifecycle scope. Add connections, instances, and callbacks with :Add. Call :Cleanup to disconnect and destroy everything when the scope ends (e.g., on character removal or session teardown). For keyed collections, store one Janitor per entry under entry.cleaner. Call :Destroy only when the Janitor object itself will not be reused — :Cleanup preserves the Janitor for reuse.

See Janitor Patterns for Cleanup vs Destroy guidance and common lifecycle recipes.

MotionMaster​

What. The project's animation library. Defined in src/ReplicatedStorage/SharedModules/MotionMaster.luau.

Why. TweenService does not support springs, splines, or composable sequences, and scatters animation logic across controllers. MotionMaster provides a unified, expressive API for all client-side motion.

How to use. Do not use TweenService for client-side animations — use MotionMaster instead.

Key entry points:

-- Fire-and-forget tween
MotionMaster.Play(target, goals, { Duration = 0.5, Model = "EaseOutQuad" })

-- Manual lifecycle control
local tween = MotionMaster.Create(target, goals, { Duration = 0.3, Model = "Spring" })
tween:Play()

-- Spring driven by a named preset
MotionMaster.fromPreset("UIPanel", target, "Position")

-- Chained sequence
MotionMaster.Sequence({ tweenA, tweenB })

-- Catmull-Rom spline movement
MotionMaster.SplineMove(target, controlPoints, { Duration = 2 })

-- Model pivot animation
MotionMaster.PivotMove(model, targetCFrame, { Duration = 0.4, Model = "EaseInOutQuad" })

Key config fields: Duration, Model (easing name), TimeWarp, Delay, Repeat, RepeatDelay, From. Sixteen named spring presets are available under MotionMaster.Presets (e.g., "UIPanel", "CameraFollow", "DoorBouncy").

For the full API reference and preset list see MotionMaster Cheatsheet.
