Weapons

Client-predicts / server-authoritative combat with a shared validator (WeaponValidation). All damage is applied server-side; client hit claims are never trusted. Weapons are Roblox Tools equipped from the Backpack; the server infers the weapon from the equipped Tool, so fire packets carry only origin/direction — never a claimed target.

How it works​

Client: controller and handlers​

WeaponController.client.luau is the bootstrap that watches the local character for Tool equip/unequip events. It looks up WeaponConfig[tool.Name].Category and dispatches to the matching category handler (MeleeHandler, GunHandler, or ThrowableHandler). It creates one Janitor per equipped Tool (and one per character) so all connections clean up correctly on unequip, death, or weapon switch. It fires Signals.WeaponEquipped/Signals.WeaponUnequipped for the HUD, and Signals.RequestShootingCamera on equip/unequip to toggle the aim camera mode. It binds R to OnReload and G to OnDetonate for handlers that declare those callbacks.

MeleeHandler — combo stepping: on each left-click it calls WeaponValidation.resolveComboSwing (tolerance 0) to determine the next step. If the click arrives during recovery it buffers one keyed retry via Janitor rather than dropping the input. It executes the predicted step (swing sound via SoundManager, optional AnimationTrack, local hitbox query via WeaponValidation.queryMeleeTargets for an instant hitmarker fired as Signals.WeaponLocalHit, debug box draw, Signals.WeaponComboChanged), then fires payload-less ReqMeleeSwing. Client combo state is cleared on unequip.

GunHandler — hitscan + rocket cosmetic + ammo prediction. On activate, it gates on a client-local fire-rate check and predicted magazine count (via AmmoApi), then fires ReqFireWeapon(origin, dir). It draws the shooter's own tracer (hitscan only; rocket has no local projectile) and supports semi and automatic fire. OnReload fires ReqReloadWeapon and predicts the ammo transition after the server-confirmed reload window. Authoritative ammo is reconciled via WeaponMagSync → Signals.WeaponMagChanged and AmmoPoolSync → Signals.AmmoPoolChanged.

ThrowableHandler — grenade and C4. On activate, it gates on the throw cooldown, plays throw sound, and fires ReqThrowProjectile(origin, dir). There is no local projectile cosmetic — the server-spawned instance replicates to all clients. For C4 (Detonation == "Manual"), OnDetonate fires ReqDetonate. Grenade ignores G.

TrajectoryPreview — a client-local green-neon ballistic arc shown while any throwable is equipped, using a fixed pool of reused BasePart segments updated every RenderStepped. Origin offset (SPAWN_OFFSET = 2.5) and upward aim bias match ServerProjectile/ThrowableHandler exactly so the preview arc matches the real projectile path. Purely cosmetic — no packets sent.

WeaponEffectsController — consumes replicated combat FX packets. WeaponFired is ignored for the local shooter (who already drew its own tracer) and renders tracer + impact spark for other players' shots. WeaponImpact renders an impact spark + sound for all melee/gun hits. ExplosionAt renders an expanding neon sphere + sound for rocket, grenade, and C4 detonations, for everyone including the shooter.

Shared validation (WeaponValidation)​

Pure math run on both client (prediction) and server (authority):

  • canFire(lastFireTime, cooldown, now) — fire-rate gate.
  • meleeHitbox(rootCFrame, range, hitboxSize) — single source of truth for the oriented swing box CFrame and size.
  • queryMeleeTargets(rootCFrame, range, hitboxSize, ignore) — box overlap returning unique Humanoid-bearing Models.
  • resolveComboSwing(state, combo, now, tolerance) — pure combo step resolution; shared so client and server stay in sync.
  • resolveStep(config, step) — merges step overrides with weapon-level defaults into a ResolvedStep.
  • applySpread(direction, spreadDegrees) — applies a random spread cone to an aim direction (cosmetic on client; server does its own authoritative ray).
  • isWithinRange(origin, hitPos, maxDistance) — range cap check.
  • ammoAfterShot(mag) / ammoReloadFromPool(mag, pool, magazineSize) — pure ammo transitions. ammoReloadFromPool returns (newMag, taken) where taken is the pool amount consumed.
  • aoeFalloff(center, hitPos, radius, maxDamage) — linear AOE falloff.
  • queryAOEModels(center, radius, ignore) — sphere overlap returning { model, humanoid, distance } for AOE application.

Server: packet handling​

WeaponServer.server.luau receives all weapon packets and runs per-category validation (fire-rate, ammo, origin tolerance, direction validity) before any damage or projectile spawn. It manages gun ammo initialisation on equip via WeaponState.EnsureAmmo + WeaponMagSync. On reload, it waits ReloadTime, calls ammoReloadFromPool, consumes the drawn ammo from AmmoManager, then fires WeaponMagSync + AmmoPoolSync (the latter emitted by AmmoManager.ConsumeAmmo). On a successful throwable throw, the server destroys the player's matching Tool (onThrowProjectile — 1 Tool = 1 throw). It drives the FastCast2 rocket caster (rocketServerCaster) — its LengthChanged callback steps the cosmetic part, its Hit callback calls CombatService.ApplyAOE and broadcasts ExplosionAt. It also handles throwable throw (onThrowProjectile) and detonate (onDetonate).

Server: damage routing (CombatService)​

CombatService is the single damage router with two primary entry points:

  • ApplyToModel(model, humanoid, amount, attackType, attacker, aoeVariant?) — applies damage to a resolved Model. Players route through HealthManager.ApplyDamage (keeping the HUD-tracked record correct — see Health); faction-tagged NPCs ("EnemyNPC"/"FriendlyNPC") take direct humanoid:TakeDamage. Anything without a recognized faction is ignored. Friendly-fire is enforced via Factions.canDamage: only Player↔Enemy damage lands; players never hurt players or friendly NPCs. A nil attacker is treated as environmental and bypasses the faction gate. Self-damage from one's own AOE is exempt.
  • ApplyAOE(center, radius, maxDamage, attackType, attacker, ignore) — calls queryAOEModels, applies aoeFalloff to each target, and routes through ApplyToModel with aoeVariant = "Explosion".

Also available: ApplyToPart(part, amount, attackType, attacker, aoeVariant?) — resolves a hit part to its Humanoid-bearing Model then calls ApplyToModel. EnemyWeapon calls the same entry points for enemy fire — see Enemy Combat.

Server: per-player state (WeaponState)​

Per-player authoritative state. Fields per player record:

  • lastFire: { [weaponName]: number } — os.clock() of last shot/swing per weapon; gates fire-rate.
  • combo: { [weaponName]: { index, lastHitTime } } — authoritative combo progress.
  • ammo: { [weaponName]: { mag, reloadEndsAt } } — magazine count and reload window (reloadEndsAt is the os.clock() timestamp when a reload finishes; 0 means not reloading). Reserve is no longer stored here — pool ammo is owned by AmmoManager.
  • active: { ActiveCharge } — active manual throwables (C4) awaiting detonation.

Key functions: EnsureAmmo (seeds magazine from config), GetMag/SetMag, GetLastFire/SetLastFire, GetCombo/SetCombo, IsReloading, SetReloadEnd, GetActiveCount, AddActive, TakeAllActive. Clear destroys all active charges and removes the player's record on PlayerRemoving.

Server: projectiles (ServerProjectile)​

Spawns and owns server-authoritative, replicated projectile instances cloned from ReplicatedStorage/WeaponAssets into workspace/ServerProjectiles. Two spawn paths:

  • spawnRocket(templateName, cframe) — anchored, non-collidable cosmetic part; the caller (WeaponServer) steps its CFrame along the FastCast2 cast.
  • spawnThrowable(templateName, origin, direction, speed, rest, ignore) — server-owned physics rigid body. prepareAssembly un-anchors all parts, sets the WeaponProjectile collision group (passes through characters), and applies per-mode elasticity: "Stick" (C4) elasticity = 0 (lands dead); "Bounce" (Grenade) elasticity = 0.15 (one small hop). installSettle polls until the charge has contacted a world surface and come to rest, then anchors it flat. Network ownership is kept server-side via root:SetNetworkOwner(nil).

HUD integration contract​

This system ships no UI. A HUD widget that wants to display ammo or combat feedback must consume:

  • Packets (server → owning client, handled by AmmoApi):
    • WeaponMagSync(weaponName, mag) — authoritative magazine count sent on equip, after each shot, and after reload completion.
    • AmmoPoolSync(ammoType, amount) — authoritative pool count for a given ammo type sent whenever the pool changes (shot, reload, craft).
  • AmmoApi read surface (preferred over raw packets):
    • AmmoApi.GetMag(weaponName) → (mag, magSize) — current magazine and max size.
    • AmmoApi.GetPool(ammoType) → (amount, capacity) — current pool and capacity cap.
    • AmmoApi.GetEquippedAmmo() → (mag, magSize, pool, cap)? — combined ammo for the equipped gun; nil for non-guns.
    • AmmoApi.GetThrowableCount(toolName) → count — counts matching Tools in the Backpack + equipped slot.
  • Signals (client-side):
    • WeaponEquipped(toolName, category) — fired on equip.
    • WeaponUnequipped(toolName) — fired on unequip.
    • WeaponMagChanged(weaponName, mag) — fired by AmmoApi on predicted mag update and on WeaponMagSync reconciliation.
    • AmmoPoolChanged(ammoType, amount) — fired by AmmoApi on AmmoPoolSync or local prediction.
    • ThrowableCountChanged(toolName, count) — fired by AmmoApi when the backpack throwable count changes.
    • WeaponReloadStarted(weaponName, reloadTime) — fired when a reload request is sent.
    • WeaponReloadComplete(weaponName) — fired when the reload window elapses or reload is rejected.
    • WeaponLocalHit(model) — fired on a predicted melee/hitscan hit for hitmarker display.
    • WeaponComboChanged(toolName, stepIndex, totalSteps) — fired on each combo step advance.

Ammo HUD. AmmoHudController (client) drives the authored AmmoGui (bottom-right ScreenGui). The count is split across two labels either side of a divider — MainContainer.AmmoCount and MainContainer.ReserveAmmoCount — laid out horizontally by a UIListLayout. For guns that is the loaded magazine beside the reserve pool; for throwables the carried count goes in AmmoCount and ReserveAmmoCount shows an em-dash, so the widget keeps its shape across weapon swaps. The GUI has no weapon-name label, so the equipped weapon's DisplayName is not shown. It is hidden for melee and when nothing is equipped. All data comes from AmmoApi + the weapon/ammo Signals; the HUD never talks to the server.

The label names are load-bearing

AmmoHudController resolves AmmoCount and ReserveAmmoCount by name with an untimed WaitForChild. Renaming either in Studio stalls the controller at load (Roblox's "Infinite yield possible" warning names the missing instance). Divider is layout-only and is never touched by code.

Ammo economy​

Pool and magazine model​

Ammo is split into two distinct layers:

  • Magazine (WeaponState, server) — per-gun in-memory count representing what is currently loaded. The magazine is seeded to MagazineSize rounds on the gun's first equip (EnsureAmmo) and then persists across deaths within the session (it is not refilled on every equip or on respawn). On each shot the magazine decrements by one. On reload, the magazine refills from the pool. The magazine is the only ammo state WeaponState owns; there is no longer a reserve field per gun.
  • Pool (AmmoManager, server) — per-player, per-type in-memory count of unloaded ammo. Entirely session-only — nothing is persisted to a DataStore. The pool is seeded to each type's Starting value on the player's first spawn only; it then persists across deaths for the rest of the session (dying never refills reserve ammo). Every type's Starting is 0: players are never given free reserve ammo — all reserve ammo is crafted (see Crafting ammo). AmmoManager.EnsureStarting re-syncs the current pool to the owning client on each respawn so the HUD shows the correct value after the character and Backpack rebuild. The pool is shared across all guns of the same ammo type.

A freshly crafted weapon still spawns with one full magazine (the magazine is seeded to MagazineSize on first equip), so it can fire immediately. But once that magazine is emptied the gun cannot be reloaded until the player crafts ammo into the reserve pool.

Reload flow​

  1. Client fires ReqReloadWeapon.
  2. Server checks mag < magSize and pool > 0; rejects otherwise (returns 0 reload time).
  3. Server waits ReloadTime, then calls ammoReloadFromPool(mag, pool, magSize) (in WeaponValidation), which returns (newMag, taken).
  4. AmmoManager.ConsumeAmmo(player, ammoType, taken) is called atomically; it clamps, deducts, and fires AmmoPoolSync to the owning client.
  5. Server sets the new magazine via WeaponState.SetMag and fires WeaponMagSync to the owning client.

Throwables​

Throwables are physical Roblox Tools in the player's Backpack. Each throw consumes exactly one Tool: WeaponServer.onThrowProjectile destroys the equipped throwable Tool server-side on a successful throw. There is no numeric reserve or CarryCount in WeaponState — count is inferred by AmmoApi.GetThrowableCount by scanning the Backpack and equipped slot.

C4 detonation is intentionally decoupled from holding the Tool: ThrowableDetonateController.client.luau listens for the global G keybind and fires ReqDetonate regardless of what is currently equipped. The server no-ops if the player has no active charges. This design handles the edge case where the last C4 was thrown (destroying its Tool) but live charges are still stuck to surfaces awaiting detonation.

Client read surface (AmmoApi)​

AmmoApi is the single client-side cache and read surface for all ammo data. HUD widgets and handlers should call AmmoApi rather than listening to raw packets.

Gotchas / anti-exploit​

Fire-rate enforcement

Guns enforce 60/RPM intervals via WeaponState.GetLastFire; melee enforces Recovery, ChainWindow, and ResetCooldown per combo step via WeaponValidation.resolveComboSwing (server tolerance = 0.05 s). Requests that arrive too early are silently dropped.

Server-authoritative ammo and reload

Magazine counts and reload timing are owned by WeaponState on the server; pool ammo is owned by AmmoManager. Firing at an empty magazine is rejected. Firing while a reload window is active (reloadEndsAt > now) is rejected. Reloading with an empty pool is rejected. Neither the magazine count, pool count, nor the reload timer is read from the client.

Origin, spread, and distance validation

The claimed muzzle origin for guns and throw origin for throwables must be within 14 studs of the server-side HumanoidRootPart position and must be a finite (non-NaN) vector. Claimed directions with zero or non-finite magnitude are rejected before normalization. The server caps hitscan range at MaxDistance on its authoritative ray; applySpread is applied client-side for feel only — the server recasts from the validated origin and does not verify the spread angle.

Friendly-fire prevention

Enforced in CombatService.ApplyToModel via Factions.canDamage. Only Player↔Enemy damage lands. Players never damage other players or friendly NPCs; enemies never damage other enemies or friendly NPCs. Self-damage from one's own AOE is exempt — the self-check bypasses the faction gate so a player's own rocket can still hurt them if they walk into the blast.

NPC pass-through via CollectionService tag: the "EnemyNPC"/"FriendlyNPC" CollectionService tag is the dual-purpose NPC marker. It gates damage routing in CombatService (only tagged NPCs with a Humanoid take weapon damage) and, via NpcCollisionService, places NPC parts in the Character collision group so thrown charges physically pass through them (see Enemy Spawner → Collision and combat wiring). A Model without a recognized faction tag receives no damage and does not block thrown projectiles — tag it or it is invisible to the weapon system.

HealthManager routing via CombatService: HealthManager writes record.Health → humanoid.Health but never reads back from the Humanoid. Any external write that bypasses HealthManager.ApplyDamage (via CombatService) will leave the HUD showing a stale record value. Never write to humanoid.Health directly for player damage. See Health.

Hitbox debugging (WeaponDebug): flip the single ENABLED flag at the top of WeaponDebug.luau and save (Rojo syncs it in — no command bar, no attributes) to draw a bright Neon box for every melee/gun query volume, green on hit and red on whiff, auto-removed after LIFETIME seconds. Every weapon handler requires this module; it's the fastest way to confirm a hitbox query ran even when the part is off-screen.

    S->>C: ExplosionAt per charge

Tuning​

  • Config module: WeaponConfig — src/ReplicatedStorage/SharedModules/Configs/WeaponConfig.luau. Edit stats here — never in handler or server code.
  • Config module: AmmoConfig — src/ReplicatedStorage/SharedModules/Configs/AmmoConfig.luau.

Common fields (all weapons): Category ("Melee"|"Gun"|"Throwable"), DisplayName, ToolName (must match the in-game Tool's Name exactly), Damage (base per-step/per-bullet; 0 for throwables, AOE only), DamageType ("Melee"|"Bullet"|"AOE"), HeadshotMultiplier? (gun only, applied on a ray hit against a part named "Head").

Melee fields: Range (forward reach/hitbox depth), HitboxSize (Vector3 width × height, Z ignored), SwingSound/ImpactSound (SoundConfig.Sfx keys), SwingAnimId?, Combos — map keyed by input ("Primary" = left-click; "Secondary" reserved). Each ComboDef has Steps[] (ordered ComboSteps; combo length = #Steps; each step has Recovery, ChainWindow, and optional overrides Damage?/Range?/HitboxSize?/AnimId?/SwingSound?/ImpactSound?) and ResetCooldown (lockout after the finisher before restarting at hit 1).

Gun fields: FireMode ("Hitscan"|"Projectile"), RPM (fire interval = 60/RPM), Automatic (hold-to-fire vs. semi), MagazineSize (reserve pool lives in AmmoManager, keyed by AmmoType), AmmoType ("Light"|"Heavy"|"Rocket"), ReloadTime, Spread (max cone half-angle, degrees), MaxDistance, FireSound/ReloadSound/DrySound/ImpactSound. Projectile-only additions: ProjectileSpeed, Gravity (Vector3), AOERadius, AOEDamage (center damage, linear falloff to 0 at radius), CosmeticTemplate (name in ReplicatedStorage/WeaponAssets).

Throwable fields: Detonation ("Fuse" auto after FuseTime | "Manual" all charges on ReqDetonate), Rest ("Bounce"|"Stick"), ThrowSpeed, FuseTime (Fuse only), MaxActive (Manual only, max simultaneous charges per player), AOERadius/AOEDamage, CooldownTime, CosmeticTemplate, ThrowSound/ExplodeSound.

Note: CarryCount has been removed. How many throwables a player carries is determined by how many matching Tool instances are in their Backpack (crafted or spawned); AmmoApi.GetThrowableCount reads this count at runtime.
