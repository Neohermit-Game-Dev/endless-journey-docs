Cannon

A grid-placeable, manned cannon that fires server-authoritative explosive arc shells. It hosts the Cannon Damage party perk (CannonDamageBonus) and completes perk Spec 5. The cannon reuses the weapon stack (FastCast2 + ServerProjectile + CombatService.ApplyAOE) and the placement stack (PlaceableItems → PlacedObjects); the server fires from its own muzzle CFrame, so client aim is never trusted for damage.

At a glance​

LayerFileRole
Clientsrc/StarterPlayer/StarterPlayerScripts/CannonController.client.luauMount prompt, movement lock, ballistic arc preview, fire input, CannonFired/ExplosionAt FX
Clientsrc/StarterPlayer/StarterPlayerScripts/CannonGuiController.client.luauProgrammatic heat-bar HUD, shown only while manning a cannon
Serversrc/ServerScriptService/CannonServer.server.luauPlaced-cannon discovery, mount/fire validation, authoritative shell simulation, damage application, heat/overheat
Configsrc/ReplicatedStorage/SharedModules/Configs/CannonConfig.luauBallistics, mount range, overheat params, part/sound keys, EnemyShip tag

Packets: ReqMountCannon, ReqFireCannon, CannonFired (impact reuses ExplosionAt) — see Networking Map Signals: OnCannonMounted — local-client-only bridge from mount state to CannonGuiController

How it works​

Placement → mount → fire​

  1. Place — the cannon is a placeable (PlaceableItems/Cannon + PlaceableTools/Cannon). Placement, stash, and move are inherited from Placement; the placed clone lands in workspace/PlacedObjects with a PlaceableName = "Cannon" attribute (an attribute, not a CollectionService tag — a tag would also match client build-mode ghosts).
  2. Mount — CannonController attaches a ProximityPrompt to each placed cannon's MountPromptPart. Triggering it sends ReqMountCannon(model); the server validates proximity (MountRange) and single-occupancy and records the gunner. Mounting locks the gunner's WalkSpeed/JumpPower and shows a ballistic arc preview raycast client-side every RenderStepped.
  3. Fire — input sends ReqFireCannon(muzzle, aimDir). The server re-derives occupancy, cooldown, and overheat, then simulates the shell from its own muzzle CFrame with a gravity Acceleration via FastCast2 (the same pattern WeaponServer uses for rockets). On impact it applies Damage * (1 + CannonDamageBonus) via CombatService.ApplyAOE and broadcasts CannonFired (muzzle flash + barrel snap + sound) and ExplosionAt (boom + explosion sound).

Occupancy​

A live occupant (character alive) blocks takeover by another player; a dead occupant's seat can be taken over. CannonController releases the player's previous cannon when mounting a new one and dismounts on death, on the cannon being stashed/destroyed (model.AncestryChanged), or on pressing X. Signals.OnCannonMounted fires the model (or nil on dismount) so CannonGuiController can show/hide its heat bar without touching the network layer.

Overheat​

Each shot adds CannonConfig.HeatPerShot; heat decays at HeatDecayPerSec on a server Heartbeat. Reaching MaxHeat locks the cannon for OverheatLockTime. Heat (0–1) and Overheated are attributes on the placed Model (no packet) — CannonGuiController reads them directly every RenderStepped, eases the displayed percentage, and plays the overheat sound once on the transition into overheat.

Server authority & anti-exploit​

Occupancy, cooldown, overheat-lock, and shell origin are all re-validated server-side; the server fires from its own muzzle, so a forged client-side origin or aim direction cannot help. CannonDamageBonus is read server-side from the server-written PartyPerkBuffs folder on every shot — unforgeable. Faction routing is inherited from CombatService.ApplyAOE, so EnemyNPC rigs must be in a hostile faction to take player damage. Direction is sanity-checked (rejects NaN/near-zero magnitude) before the cast fires.

EnemyShip forward seam​

CannonServer.applyCannonAOE damages Humanoids via CombatService.ApplyAOE and, in the same call, decrements a numeric Health attribute on in-radius models tagged CannonConfig.ENEMY_SHIP_TAG ("EnemyShip") with linear falloff to the blast edge, destroying the model at Health <= 0. This is inert until a future enemy-ship spec tags ships; it requires no change to the perk hook.

Gotchas​

OnCannonMounted is not in the shared signals map

The signal is real (ReplicatedStorage/SharedModules/Signals/init.luau) and fires from CannonController on mount/dismount, consumed only by CannonGuiController — it is a pre-existing gap in Signals Map, not a code issue.

Data flow​

sequenceDiagram
    participant Cl as CannonController
    participant Sv as CannonServer
    participant Gui as CannonGuiController

    Cl->>Sv: ReqMountCannon(model)
    Sv->>Sv: validate not-occupied-by-live-player, proximity <= MountRange
    Sv-->>Cl: accepted: boolean
    Cl->>Cl: lock WalkSpeed/JumpPower, start arc-preview raycast loop
    Cl->>Gui: Signals.OnCannonMounted(model)

    loop while mounted, on fire input
        Cl->>Sv: ReqFireCannon(muzzle, aimDir)
        Sv->>Sv: validate occupant, cooldown, overheat; sanity-check direction
        Sv->>Sv: FastCast2 shell from own muzzle CFrame + Gravity Acceleration
        Sv->>Sv: heat += HeatPerShot; lock if heat >= MaxHeat
        Sv-->>Cl: (accepted, remainingCooldown)
        Sv->>Cl: CannonFired(gunner, muzzlePos, velocity) - all clients
        Note over Sv: on shell impact
        Sv->>Sv: applyCannonAOE - CombatService.ApplyAOE + EnemyShip Health falloff
        Sv->>Cl: ExplosionAt(center, radius, "Cannon") - all clients
    end

    Sv->>Sv: Heartbeat: heat -= HeatDecayPerSec*dt; release overheat lock when elapsed

    Cl->>Sv: ReqMountCannon(nil) - dismount (death, X key, or cannon destroyed)
    Cl->>Gui: Signals.OnCannonMounted(nil)
