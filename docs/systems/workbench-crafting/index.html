Workbench Crafting

A placed Workbench station lets players craft weapons, armor, and placeables from config-defined recipes in a single server-authoritative round-trip. Crafting is instant (no hold duration) and per-player. The station is placed in the world by the existing placement system and interacted with through a ProximityPrompt; Stash/Move of the Workbench itself is handled by the existing Placeable Actions system.

How it works​

Opening the bench​

Hovering the MoveButton / StashButton swaps each button's Icon image and eases its ButtonIconContainer.BackgroundColor3 to the dark accent Color3.fromRGB(19, 15, 24) via MotionMaster, restoring the originally-authored icon and color on mouse leave. This is purely cosmetic and is wired in WorkbenchGuiController.client.luau, not PlaceableActions.

On the first open of a session, the detail pane auto-selects the first recipe in the grid's sort order (Category, then DisplayName — the same order shown under the "All" filter) so it never shows the unselected Studio placeholder. This is a one-time default: once any recipe is selected (by this default or by a player click), the selection persists across closes/reopens like any manual pick.

Client — recipe grid and gating​

WorkbenchGuiController opens via the bench CraftPromptPart ProximityPrompt. It builds the recipe grid from WorkbenchConfig.Recipes and greys any recipe whose RequiresNode is not present in ReplicatedStorage/ResearchUnlocked. Fires ReqCraft on the Craft button and fires Signals.OnItemCrafted on a confirmed success. The CloseButton closes the GUI. The DropdownButton is driven by the reusable Dropdown widget, which fires Signals.RequestWorkbenchCategory on selection to re-filter the grid. Uses a Janitor per GUI open/close lifecycle.

Server — authoritative craft handler​

WorkbenchService is the sole owner of the authoritative ReqCraft handler. On ReqCraft(bench, recipeId) it validates, in order:

  1. Look up the recipe in WorkbenchConfig (else UNKNOWN_RECIPE).
  2. Verify the bench is a tagged Workbench Model (else INVALID_TARGET).
  3. Re-check proximity, INTERACT_DISTANCE + INTERACT_DISTANCE_TOLERANCE (else TOO_FAR).
  4. CRAFT_COOLDOWN gate, per-player timestamp (else COOLDOWN).
  5. Check the RequiresNode gate in ResearchUnlocked (else LOCKED).
  6. CraftOutputDispatcher.isFeasible(recipe.Output) — verify the output slot is usable before consuming any materials (else OUTPUT_FAILED).
  7. Confirm the player holds enough cost materials (else INSUFFICIENT_MATERIALS).

On pass: consume materials from the player's Backpack, then call CraftOutputDispatcher.grant(player, recipe.Output) and record the cooldown timestamp. The handler returns (success: Boolean8, code: NumberU8).

Output dispatch​

CraftOutputDispatcher handles the three output kinds:

  • Kind == "Weapon" — clones the named Tool from ServerStorage/WeaponTemplates into the player's Backpack.
  • Kind == "Armor" — calls ArmorManager.SetTier(player, output.Tier), updating ArmorState/<UserId>.ArmorBaseReduction in ReplicatedStorage.
  • Kind == "Placeable" — grants the named Tool from ReplicatedStorage/PlaceableTools/<Name> into the player's Backpack.

isFeasible(output) verifies the target output slot is usable (e.g. the template exists, the tier is valid) before materials are consumed. A misconfigured recipe never costs the player materials.

Recipe schema​

Recipes are declared in WorkbenchConfig.Recipes as a { [string]: Recipe } table keyed by a string recipe ID:

export type Output =
    { Kind: "Weapon",   ToolName: string }
  | { Kind: "Armor",    Tier: number }
  | { Kind: "Placeable", PlaceableName: string }

export type Recipe = {
    Category:    string,    -- one of RecipeCategories ("weapons"|"ammo"|"armor"|"workstation")
    DisplayName: string,
    Description: string,
    Tier:        number,    -- 1..5 flavor/quality badge only; NOT a prerequisite ladder
    Icon:        string,    -- rbxassetid:// string for the grid tile and detail panel
    Cost:        { Wood: number?, Metal: number? },
    RequiresNode: string?,  -- Research Bench nodeId gate or nil = always available
    Output:      Output,
}

Tier is a purely cosmetic quality badge displayed as a star rating in the GUI. It has no prerequisite chain and imposes no unlock order — any recipe with RequiresNode = nil is available to craft at any time regardless of Tier. The only unlock gate is RequiresNode. The Cost table is limited to Wood and Metal because the GUI renders exactly two material rows; adding a third material requires a GUI layout change and a matching config key.

The Recipes table is the live catalog. The shipped placeholder entries:

Recipe IDCategoryCostRequiresNodeOutput
CraftPistolweaponsMetal 10nilWeapon "Pistol"
CraftArmorT1armorMetal 15nilArmor tier 1
CraftWorkbenchworkstationWood 5nilPlaceable "Workbench"
CraftSMGweaponsMetal 25"Durability_T1"Weapon "SMG"

The workstation category currently contains only CraftWorkbench — it exists as its own dropdown filter rather than folding the Workbench into weapons or armor because future placeable stations (e.g. a second crafting structure) are expected to land in the same category.

Research gate seam​

ResearchEffectsDispatcher publishes leveled-up node IDs into a ReplicatedStorage/ResearchUnlocked folder (a BoolValue per node at level ≥ 1, named by nodeId) in parallel to the ResearchBuffs folder. This folder is written by the server whenever a node reaches level 1 and is read by:

  • WorkbenchService (server): authoritative gate check. A craft request whose recipe has a non-nil RequiresNode is rejected with LOCKED if the corresponding BoolValue is absent or false. Because the folder is written by the server, clients cannot forge an unlock.
  • WorkbenchGuiController (client): greying. Recipes with a locked RequiresNode are rendered as unavailable in the grid so players know they need to research the gating node first. The client reads this folder but never writes it.

Unlike the old Tech Tree (where a node auto-unlocked the instant its pooled material cost was met), a gating Research Bench node now also costs time: the player pays materials on enqueue, then the node's level advances in real time (gated by bench fuel) before ResearchUnlocked is written. Recipes behind a RequiresNode are therefore no longer available the moment materials are gathered — see Research Bench for the full enqueue/advance/complete flow and the ResearchBuffs/ResearchUnlocked folder contract.

Studio setup​

  1. Tag the Workbench Model. In ReplicatedStorage/PlaceableItems/Workbench, tag the root Model with the CollectionService tag Workbench (the same tag the Shredder scans for — one Model serves as both crafting station and shredder). Give it a BasePart named CraftPromptPart (anywhere under the Model — PromptResolver finds it recursively) containing a ProximityPrompt. Set the Model's PrimaryPart. The shredder half uses a sibling ShredPromptPart.
  2. Create ServerStorage/WeaponTemplates. Add a folder named WeaponTemplates inside ServerStorage. Place craftable weapon Tools here (e.g. clones of Pistol and SMG from StarterPack). These are separate from the StarterPack copies — the Workbench clones from here into the player's Backpack, so stat changes or visual differences can live here independently.
  3. Ensure craftable placeables exist. Each recipe with Output.Kind == "Placeable" needs a Tool at ReplicatedStorage/PlaceableTools/<PlaceableName>. The Workbench itself already follows this convention as a grid-placeable item.
  4. Material templates are shared. ReplicatedStorage/CraftingMaterials already holds Wood and Metal Tool templates (shared with the Shredder and Research Bench systems). No duplication is needed.
  5. Wire ResearchUnlocked. ResearchEffectsDispatcher creates and writes this folder automatically at runtime. No manual Studio setup is required for the gate to function. If testing in isolation (without a running ResearchService/ResearchEffectsDispatcher), create a Folder named ResearchUnlocked in ReplicatedStorage and add BoolValue children named after whichever node IDs you want to treat as unlocked.

Gotchas / anti-exploit​

Server re-checks proximity on every craft

The client proximity prompt is never trusted. WorkbenchService re-runs the distance check using INTERACT_DISTANCE + INTERACT_DISTANCE_TOLERANCE on every ReqCraft call. A player exploiting from range receives TOO_FAR.

Feasibility is checked before materials are consumed

CraftOutputDispatcher.isFeasible(recipe.Output) runs (and must succeed) before any material Tool is removed from the player's Backpack. A recipe that references a missing weapon template or an invalid armor tier therefore fails without costing the player anything. Misconfigured recipes are safe to ship; they only result in a visible craft failure.

Research gate is read from server-written state

The ResearchUnlocked folder is written exclusively by ResearchEffectsDispatcher on the server. A client cannot create or modify entries in that folder. The server re-reads the folder on every ReqCraft call, so a client that somehow fakes the UI greying cannot bypass the gate.

Cost is limited to Wood and Metal

The GUI renders exactly two material rows. Cost may only specify Wood and/or Metal. Adding a third material type (e.g. Energy) requires a GUI layout change alongside the config key — otherwise the cost is silently unchecked on the client (though the server will still validate it).

Tier is a flavor badge, not a prerequisite ladder

Tier (1–5) drives the star-rating display only. There is no inter-recipe prerequisite chain derived from Tier values. The sole unlock gate is RequiresNode. Do not attempt to use Tier as a crafting order enforcer — it will not work without code changes.

Known edge case: respawn mid-craft (v1)

If a player's Backpack disappears between the feasibility check passing and CraftOutputDispatcher.grant executing (e.g. the player respawns during that narrow window), materials may be consumed but the grant returns OUTPUT_FAILED. The client receives a failure response and the player loses the materials. This is an accepted v1 limitation — the window is sub-frame in practice. A future refund path or a pre-grant Backpack re-check is the recommended fix.

Data flow​

sequenceDiagram
    participant P as Player
    participant C as WorkbenchGuiController
    participant S as WorkbenchService

    P->>C: Walk within INTERACT_DISTANCE
    C->>C: ProximityPrompt fires (CraftPromptPart)
    C->>C: GUI opens; grid from WorkbenchConfig.Recipes
    C->>C: Grey recipes whose RequiresNode is not in ResearchUnlocked

    P->>C: Click a recipe tile
    C->>C: Show DisplayName, Description, Tier badge, Cost rows, RequiresNode note

    P->>C: Click Craft button
    C->>S: ReqCraft(bench, recipeId)
    S->>S: look up recipe (else UNKNOWN_RECIPE)
    S->>S: verify tagged Workbench Model (else INVALID_TARGET)
    S->>S: re-check proximity (else TOO_FAR)
    S->>S: CRAFT_COOLDOWN gate (else COOLDOWN)
    S->>S: check RequiresNode in ResearchUnlocked (else LOCKED)
    S->>S: CraftOutputDispatcher.isFeasible(Output) (else OUTPUT_FAILED)
    S->>S: verify materials held (else INSUFFICIENT_MATERIALS)
    S->>S: consume materials, CraftOutputDispatcher.grant(...)
    S->>S: record cooldown timestamp
    S->>C: (success, code)
    alt success
        C->>C: Signals.OnItemCrafted:Fire(recipeId)
        C->>C: success FX / SoundManager.PlaySFX(CraftSuccess)
    else failure
        C->>C: failure toast / SoundManager.PlaySFX(CraftFail)
    end
