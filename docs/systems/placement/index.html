Placement

The placement system lets players preview and place items in designated build areas. A shared validation module (PlacementSystem) runs identically on the client (preview) and server (authority) — the client predicts and previews instantly, and the server re-validates every placement before committing it.

How it works​

Entering build mode​

On tool equip, PlacementClient creates one PlacementSystem instance (grid size 2, tag BuildArea), calls SetBuildMode(true) and SetGhostModel(template), and fires ClientToggleGhost. It also fires Signals.RequestShootingCamera(false) to disable the aim camera. PlacementCameraController then takes over: it switches to CameraType.Scriptable (near-top-down, follows the player, yaw locked at entry), eases in and out of the angle rather than snapping, and fades any PlacementOccluder-tagged geometry. See Camera.

Tracking the ghost​

A Heartbeat loop rate-limited to GhostUpdateHz (default 20 Hz) raycasts, calls UpdateGhostPosition, and fires ClientUpdateGhost with the resulting CFrame. Signals.OnBuildValidityChanged fires whenever validity changes so UI and audio can react. Grid/free toggle, rotation, confirm, cancel, and ghost-lock are all driven by signals wired to BuildModeGuiController. The client listens for ServerToggleGhost / ServerUpdateGhost and calls SetOtherGhost to render other players' ghost previews.

Server relay and validation​

PlacementServer relays ClientToggleGhost to other players after confirming the item name exists in ReplicatedStorage/PlaceableItems, and relays ClientUpdateGhost (CFrame type-checked) to other players. On PlaceItem it enforces a per-player cooldown (PLACE_COOLDOWN = 0.4 s), character/tool guards, ray-origin distance (MAX_ORIGIN_DISTANCE = 50 studs), final-position distance (MAX_PLACE_DISTANCE = 60 studs), and collision validity — all using an isolated PlacementSystem instance with a ServerStorage-parented ghost that is never replicated.

Finalizing a placement​

On success, the server clones the template, calls finalizeModel (makes CollisionBox invisible + non-collidable, visual parts opaque, and tags the CollisionBox with PlacementObstruction so future placements collide with it), parents it to workspace/PlacedObjects, destroys the player's tool, and broadcasts ghost-clear to all clients. If the placer's own character ends up overlapping the placed item, they are teleported horizontally clear of it, clamped to stay within the same BuildArea part.

Shared PlacementSystem​

PlacementSystem handles ghost model lifecycle, grid-snap vs free-placement position calculation, collision-box derivation, obstruction validity check, and other-player ghost rendering. IS_CLIENT guards prevent Texture and TweenPlus calls from running on the server; SetBuildMode is client-only (it creates grid Texture instances on build area parts), while the server sets IsBuildMode = true directly. Each PlaceItem request creates an isolated PlacementSystem instance — this is intentional, so concurrent requests from different players cannot corrupt shared state. Never cache a server-side PlacementSystem across requests.

Cancelling build mode​

Pressing X (configurable via PlacementConfig.CancelKey) or the on-screen Cancel button (mobile) fires Signals.RequestPlacementCancel. Both paths reach the same cancelPlacement function in PlacementClient, which snaps build-mode visuals off and sends a RequestPlacementRevert RemoteFunction call to the server. Escape is intentionally not used — Roblox reserves it for the in-game menu.

The server checks PlaceableRevertStore to determine the outcome:

Session typeOutcome
Fresh placement (item was never placed before)Server returns false → client calls humanoid:UnequipTools() and the tool returns to the Backpack
Move session, original spot is freeServer re-places the item at its original CFrame, destroys the tool, returns true → item reverts, no unequip needed
Move session, original spot is occupiedServer returns false → client falls back to unequip

See Placeable Actions for how a Move session records the revert entry.

Own-character exclusion and push-out​

PlacementSystem.new(buildAreaTag, gridSize, excludePlayer)'s third argument controls which player's Character is skipped by BuildObstructionFilter. The client always passes its own Players.LocalPlayer; the server passes the requesting player for both PlaceItem and RequestPlacementRevert. Other players' characters are never excluded — they still block placement as before. Because every other player's character remains an obstruction, no other player can ever end up overlapping a freshly finalized item, so pushCharacterClearOfBox in PlacementServer only needs to act on the requesting/reverting player.

The platform it clamps into comes from PlacementSystem.LastBuildAreaPart, populated only by CalculatePlacement's raycast (the PlaceItem path). The revert path re-places at a stored CFrame and never calls CalculatePlacement, so LastBuildAreaPart is nil there; PlacementServer falls back to findBuildAreaBelow, a dedicated helper that raycasts straight down from the revert position (filtered to the BuildArea tag, the same idiom CalculatePlacement uses) to resolve the platform part.

Gotchas​

Anti-exploit — do not relax the server thresholds

MAX_ORIGIN_DISTANCE = 50, MAX_PLACE_DISTANCE = 60, and PLACE_COOLDOWN = 0.4 in PlacementServer are the primary defences against remote placement exploits. Raising these values substantially would allow clients to place items anywhere in the world or spam unlimited items.

  • Model structure is required. Every entry in ReplicatedStorage/PlaceableItems must have a CollisionBox (BasePart) child. Without it, PlacementSystem warns and falls back to bounding-box collision, which can cause floating or incorrect validity checks.
  • Obstruction is tag-driven, not folder-driven. Build placement only avoids a volume if it is tagged PlacementObstruction. Placed items are tagged automatically on their CollisionBox by finalizeModel. Any static world model that placement must respect (e.g. TrainShieldGeneratorPlaceholder, ResearchBenchPlaceholder) must have a CollisionBox BasePart tagged PlacementObstruction by hand. Tag the CollisionBox part only, never the whole model — sibling sub-models like TrajectoryPoints would otherwise become map-wide placement blockers.
  • CollisionBox must not be named RootPart or tagged PlacementIgnore. Those names cause the part to be treated as invisible/non-collidable in the ghost.
  • SetBuildMode must only be called on the client. Calling it on the server would create Texture instances in workspace and replicate them to all clients.
  • Ghost relay is observer-only. The GhostModels folder and its contents exist only on the client; the server's validity check correctly skips that folder for this reason.
  • Cutscene and combat gates (isInCutscene, isInCombat) in PlacementClient are not yet wired to any external system — they are TODO integration points.

Server-side security thresholds live in PlacementServer.server.luau as local constants (MAX_ORIGIN_DISTANCE, MAX_PLACE_DISTANCE, PLACE_COOLDOWN) — treat them as sensitive anti-exploit values.

Data flow​

sequenceDiagram
    participant P as Player
    participant C as PlacementClient
    participant S as PlacementServer
    participant O as Other clients

    P->>C: Equip tool
    C->>C: SetBuildMode(true), SetGhostModel(template)
    C->>S: ClientToggleGhost
    S->>S: Validate itemName exists
    S->>O: ServerToggleGhost (relay)
    loop Heartbeat @ GhostUpdateHz
        C->>C: CalculatePlacement (raycast) + CheckValidity
        C->>S: ClientUpdateGhost (CFrame)
        S->>S: Type-check CFrame
        S->>O: ServerUpdateGhost (relay)
    end
    P->>C: Click / confirm signal
    C->>S: PlaceItem (origin, dir, rotation, mode)
    S->>S: Cooldown + distance checks
    S->>S: Isolated PlacementSystem: CalculatePlacement + CheckValidity
    S->>S: Clone + finalizeModel -> workspace/PlacedObjects
    S->>C: Destroy tool
    S->>O: ServerToggleGhost(false)
