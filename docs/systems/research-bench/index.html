Research Bench

A cooperative, server-wide, session-only (no DataStore) research system. Players pay materials up front to enqueue a node; a single active job advances over real time, gated by a shared fuel reserve that only drains while a job is progressing. The catalog is 31 nodes across 6 branches, all MaxLevel = 1 — every node is researched exactly once. Each node places its own card in StarterGui.TechTreeGui through Branch, Tier and Column in config, and its lines come from Prereqs; a node's effects, if it has any, are a list (Effects) applied as buffs on completion, and prerequisites are a list (Prereqs) with AND semantics — a node can require more than one other node to be researched first.

Growing the catalog is a config change: a node is one Nodes entry (Branch/Tier/Column place it, Prereqs draws its lines) and a branch is one Branches entry. No Studio work and no new packets.

How it works​

Core loop​

  1. Enqueue — player spends materials immediately (pay-on-enqueue, not pay-on-complete) to queue an eligible node. If nothing is active, the job just enqueued starts immediately. The server also checks the node's Gamepass (if any) before accepting — see Gamepass gating.
  2. Advance — a server tick burns bench fuel and advances the active job's elapsed time. Progress pauses whenever fuel hits 0; it resumes the instant fuel is added back. Nothing burns or advances while a player holds REFUEL (state.frozen).
  3. Complete — when elapsed >= duration, the node's level is recorded, Signals.OnResearchLevelUp fires, and the next queued job (if any) becomes active.
  4. Refuel — a player holds the REFUEL button in the tech tree GUI. The press sends ReqResearchHold(true) and the server freezes the bench. While held, the client only previews the fuel (nothing is spent). On release, TechTreeGuiController sends ReqResearchHold(false) and one ReqResearchRefuel(points); the server spends pool Energy via MaterialPool.SpendUpTo (bench fuel has no cap). There is no refuel ProximityPrompt — see Studio setup.
  5. Cancel — a player cancels a node's job (queued or active); see Cascade-cancel.

Because there is one shared queue and one shared fuel pool for the whole server, this is explicitly a co-op system: any player at the bench can enqueue, cancel, or refuel, and progress benefits everyone.

Buff nodes vs. unlock-flag nodes​

Every entry in ResearchConfig.Nodes is a Node with MaxLevel = 1 and a single Levels[1] entry (Cost, Duration). The levelling machinery (MaxLevel, Levels keyed by number) is still generic — it costs nothing to keep and a future node could ship with MaxLevel > 1 — but every node shipped today researches once. Two shapes exist:

  • Buff nodes declare an Effects list (not a single Effect) — e.g. { { Type = "StatBuff", Key = "MaxHP", PerLevel = 50 } }. A list is required because two nodes need more than one key at once: Shield_Efficiency/Shield_EfficiencyPlus each grant ShieldEfficiency and ShieldStrength, and Shield_Delta grants MaxHP and ShieldAutoRegen. ResearchEffectsDispatcher sums every entry across every researched node sharing a Key into ReplicatedStorage/ResearchBuffs (see Buff/unlock folders).
  • Unlock-flag nodes have Effects = nil. Completing them writes only a ResearchUnlocked/<nodeId> BoolValue; there is no buff to compute. This is every node outside the Train Shield branch — Ranged/Armor weapon and armor nodes gate Workbench recipes, and Train Weapon/Train Utility/Special nodes gate systems that do not exist yet (see Honest status of Effects). The one recipe gate actually wired in WorkbenchConfig — CraftSMG's RequiresNode = "Ranged_SMG" — points at a Ranged branch node, confirming any node id can gate a recipe. See Workbench Crafting for the consumer side.

Prerequisites are AND-lists​

Prereqs: { string }? is a list, not a single id — every listed prereq must be at level ≥ 1 (ResearchState.isEligible loops the list) — there is no OR, and no separate minimum-level field now that every node is MaxLevel = 1. Two nodes actually need more than one prerequisite, which is the reason the field is a list at all:

  • Ranged_EnergyFirearms — Ranged_SniperRifle and Ranged_Explosives
  • Shield_Delta — Shield_Gamma and Shield_EfficiencyPlus

ResearchConfig.validate() walks every Prereqs edge at Studio-boot time and warns on an unknown prereq id or a prereq cycle — see Verification.

Cascade-cancel​

Cancelling is keyed by (nodeId, fromLevel). ResearchState.cancel removes every queued job of the same node with targetLevel >= fromLevel (full refund), and if the active job belongs to the same node and active.targetLevel >= fromLevel, cancels it too at ResearchConfig.ACTIVE_REFUND_FRACTION (0.5) — the same mechanism the old multi-level Tech Tree used.

With every node now MaxLevel = 1, a node can only ever have one job outstanding at a time (queued or active, never both, and never two queued levels stacked behind each other) — ResearchState.validateEnqueue rejects a second enqueue for the same node with AT_MAX_LEVEL. So in practice cascade-cancel today always resolves to cancelling that single job: fromLevel is always 1, and there is nothing behind it to cascade into. The generic multi-level mechanism is kept as-is (smaller diff than removing it) in case a future node ships with MaxLevel > 1.

If neither the queue nor the active job matches, ReqResearchCancel returns NOTHING_QUEUED and nothing is refunded. Refunds are credited to the server-wide Material Pool with the bench's TrajectoryPoints as the effect origin (pivot fallback); every client animates them into the Materials HUD.

Fuel and pause behavior​

  • Fuel is a single server-wide reserve with no cap.
  • While a job is active, fuel burns at ResearchConfig.FUEL_BURN_RATE (1.0/sec) — an idle bench (no active job) never burns fuel.
  • ResearchState.advance clamps effectiveDt = min(dt, fuel / burnRate) so a job's elapsed only ever grows in step with fuel actually spent — the moment fuel reaches 0, elapsed stops advancing (the job pauses, it does not fail or lose progress). Refueling resumes it on the next tick.
  • Refueling spends shared pool Energy: ReqResearchRefuel(points) calls MaterialPool.SpendUpTo("Energy", points × FUEL_PER_POINT, FUEL_PER_POINT) — the same path the Train Fuel, Train Shield, Jump Drive and Energy armor use — so a pool short of points pays what it has. An empty pool returns NO_FUEL_ITEM. One hold pays at most MAX_HOLD_POINTS (255) Energy, the NumberU8 limit; the client pays by itself at that point or after as long as that takes (25.5 s at the defaults, Rules.holdDone), even when a small pool stopped the charge first, so a real hold always ends before HOLD_TIMEOUT.
  • Freeze while held. ResearchService keeps holds: { [Player]: deadline }. ReqResearchHold(true) (live bench, isNearBench) adds the player with a deadline HOLD_TIMEOUT (30 s) away (a repeat press keeps the first deadline); false or leaving removes them. While the set is not empty, state.frozen = true and ResearchState.advance changes nothing, so the fuel and the job timer stop for every player (shared bench, shared freeze). Each tick ResearchState.pruneHolds drops expired holders, so a lost release freezes the bench for 30 s at most. The handler only records the hold; the next tick (TICK_INTERVAL, 0.1 s) applies it and broadcasts when frozen changes, so toggling the free packet cannot send more than one broadcast per tick. frozen is serialized. The trigger is the GUI's hold-to-refuel button (pay on release, one request per hold) rather than a second ProximityPrompt — see Studio setup.
Fuel and queue are shared, not per-player

There is exactly one fuel value and one queue for the entire server. Any player at the bench can enqueue against the shared queue, refuel the shared reserve, or cancel any job — including jobs another player paid for. This is intentional (co-op resource pooling) but means griefing-by-cancel is possible; there is no per-player ownership check.

Buff/unlock folders​

ResearchEffectsDispatcher.server.luau is the sole writer of two ReplicatedStorage folders, both recomputed from scratch (not delta-accumulated) on every Signals.OnResearchLevelUp, iterating every node's Effects list:

Every other branch's nodes are unlock-flag-only; the systems they gate (energy weapons, collectors, recycler, shared storage, train weapons) do not exist yet.

Card states & palette​

TechTreeGuiController paints every card into one of five states, sourced from ResearchConfig.NodeStateColors — the single source of truth for the palette (Background, Stroke, NameText, StatusText, StatusIcon, Line):

StateMeaning
LockedPrereqs not yet met
AvailableEligible, not queued/active/researched
QueuedWaiting behind the active job
InProgressThe active job — its stroke pulses between InProgress.Stroke and IN_PROGRESS_PULSE (a per-frame lerp in the controller's RenderStepped loop, never TweenService)
UnlockedResearched — mint (#94d2bd)

There is no Unaffordable state. A node you can reach but cannot pay for still renders Available — only the cost numbers (on the card and in the detail panel's UnlockCostContainer) turn red and the action button disables. One less state to build and to learn, and the affordance sits where the player is already looking when deciding to buy.

Connector lines are built from Prereqs by TechTreeGuiRules.connectors: for each prereq (left to right), three axis-aligned 4 px Frames — down from the prereq to a bus line halfway up the gap above the node, across to the entry point, and down into the node. Two prereqs enter 56 px apart. A segment takes the Line colour of the prereq that owns it (Locked dark, Available/Queued/InProgress grey, Unlocked green), so a path lights when its prereq completes. A line from a prereq more than one row up drops straight down that prereq's column; ResearchConfig.validate() warns if a card sits in that path.

Gamepass gating​

ResearchState stays pure and knows only about Prereqs — ownership is a separate gate layered on top by ResearchService:

  • Server checks MarketplaceService:UserOwnsGamePassAsync at enqueue time (ReqResearchEnqueue), caching the result per (player, passId); a PromptGamePassPurchaseFinished hook clears a cached denial so a mid-session purchase is picked up immediately. A gated node the player doesn't own is rejected with the new GAMEPASS_REQUIRED (11) result code.
  • Client (TechTreeGuiController) checks UserOwnsGamePassAsync once per pass at load (and marks it owned on PromptGamePassPurchaseFinished) to show the detail panel's "Game pass" or "Game pass owned" chip. Display only — the card is still Available and the server still decides. A pass card has a gold rail and a ticket before its name.
  • Owning the pass makes a node eligible; it is still queued with materials and duration like any other node.

Today exactly one node uses this: Special_BiomeSelector, gated on ResearchConfig.BIOME_SELECTOR_GAMEPASS_ID = 1982397425. Note that passesGamepassGate treats only a missing Gamepass field as "no gate" — a node carrying Gamepass = 0 is refused with GAMEPASS_REQUIRED, because 0 is not a pass anyone can own. So blanking the id locks the node rather than freeing it.

Client / Server / Shared responsibilities​

Shared — ResearchState.luau is a pure, stateless module with no Roblox service calls: newState, levelOf, pendingLevel, isEligible (loops Prereqs, AND semantics), validateEnqueue, enqueue, cancel (cascade logic), advance (tick), refuel, serialize. Both the server (authority) and the client GUI (asState() cast over the cached snapshot, for greying/afford checks) call the same pure helpers, so the rules can never drift between sides. validateEnqueue deliberately does not check materials or gamepass ownership — those checks are server-only and layered on top by ResearchService.

Server — ResearchService.luau is the authoritative owner of ResearchState.State. It is a ModuleScript, not a .server.luau Script — see ModuleScript + loader split below. Initialize() (idempotent, guarded by a boot flag) wires all four packet handlers plus the RunService.Heartbeat tick loop, the gamepass ownership cache, and its PromptGamePassPurchaseFinished/PlayerRemoving hooks. GetLevels() exposes the live levels table for ResearchEffectsDispatcher to read.

Server — ResearchSystemLoader.server.luau is a one-line boot script: require(...ResearchService) then ResearchService.Initialize(). Mirrors PerkManager.luau / PerkSystemLoader.server.luau.

Server — ResearchEffectsDispatcher.server.luau connects Signals.OnResearchLevelUp and republishes both buff/unlock folders from scratch, looping every node's Effects list. See Buff/unlock folders.

Client — TechTreeGuiController.client.luau drives StarterGui.TechTreeGui, which holds the panel plus a Templates folder (TabTemplate, CardTemplate, LineTemplate, TierTemplate, SelectionRing, EffectRowTemplate, ChipTemplate). It opens from the bench's TechPromptPart ProximityPrompt. Tabs are cloned once from ResearchConfig.Branches into the BranchTabs ScrollingFrame; a tab click rebuilds the tree for that branch only (one Janitor), and state updates only repaint. Selecting a card moves the SelectionRing and fills the detail panel: UNLOCKS rows (Unlocks) or EFFECT rows (Effects through EffectLabels), REQUIRES chips, the Metal/Wood/Time cost chips and the action button. When the node has a non-zero Gamepass the player does not own (and is not researched), the action button turns gold and shows BuyContent (ticket + BUY PASS + the Robux price from GetProductInfoAsync, … until it answers); a click opens PromptGamePassPurchase, and PromptGamePassPurchaseFinished marks the pass owned and repaints. The bottom row is the active job (click = cancel at 50%, or full with Lab Insurance), three queue slot cards (click = cancel, full refund) and the fuel stack: the BENCH FUEL header with the hint (m:ss OF RESEARCH, RESEARCH PAUSED in red, or PAUSED WHILE REFUELING in teal), the FuelRow (FuelAmount + FUEL, then EnergyLeft) and the REFUEL button. Pressing REFUEL sends ReqResearchHold(true) and stops the local clock; holding grows a client-only charge: FuelAmount counts up in pale teal, ← ⚡ n ENERGY LEFT and the header Energy count down. Release (anywhere), close or focus loss sends ReqResearchHold(false) and one ReqResearchRefuel(points); a hold pays by itself at MAX_HOLD_POINTS or after 25.5 s. A release within 0.3 s toasts Hold REFUEL to add more. With an empty pool the button greys out and reads NO ENERGY. While a hold freezes the bench the job box reads REFUELING; with no fuel and no hold the running card shows the Pause icon and PAUSED in red with a grey bar and no pulse, the detail pill reads PAUSED, and the job box reads PAUSED. Icon images come from ResearchConfig.Icons: every icon ImageLabel names its key in an Icon attribute. Icons, TabTemplate, CardTemplate, SelectionRing, TierTemplate and LineTemplate each hold a UIAspectRatioConstraint so they keep their shape; the controller sets each cloned line's ratio from its segment size. Move/Stash wiring is one call — PlaceableActions.bind(benchModel, screen), which finds the Move/Stash buttons of both layouts — see The bench is a placeable for when the buttons show. Between ResearchStateUpdate broadcasts, interpolated() fast-forwards the active job and the fuel locally with the known burn rate and the synced server clock.

Compact layout. TechTreeGui holds two panels built from the same templates: MainContainer (authored 1800×940, UIScale = min(W/1920, H/1022)) and CompactContainer (authored 1240×520). When the full scale drops below TechTreeGuiRules.COMPACT_BELOW (0.6, phones and 4:3 tablets), the controller shows CompactContainer instead, scaled by s = min(W/1240, H/520) and grown to min(W/s, 1400) × min(H/s, 860) (Rules.compactSize). The controller binds both panels into one View (bindView) and paints whichever fit() picks; crossing the threshold while REFUEL is held pays the hold first. The compact panel keeps the same names wherever the role is the same and drops: the TECH TREE title, the Metal/Wood header chips (the cost chips already read have/need), the RESEARCHED total, the detail icon, sub line, section labels and REQUIRES chips (a locked node's button reads NEEDS <PREREQ> / NEEDS <PREREQ> +n instead), the queue hint and slot times, and the BENCH FUEL header (FuelHint sits at the end of FuelRow and hides while ENERGY LEFT shows). Branch tabs are Templates.CompactTabTemplate clones in a horizontal BranchStrip.BranchTabs ScrollingFrame (AutomaticCanvasSize X, each tab Size = UDim2.new(0, 68, 1, 0) with a UIAspectRatioConstraint, DominantAxis = Height, inside it) beside the branch name and n / m RESEARCHED. AutomaticCanvasSize does not grow past items that hold an aspect-ratio constraint, so the controller also sets CanvasSize from the list's AbsoluteContentSize, and sizes the strip to its tabs while leaving the name 260 px. The tree sits in a vertical TechContainer ScrollingFrame with rows Rules.COMPACT_ROW_GAP (32 px) apart; its canvas height is Rules.treeHeight + 40.

ModuleScript + loader split (caution)​

ResearchService is a ModuleScript, booted by a separate loader

ResearchService.luau lives under ServerStorage/SharedModules/ as a ModuleScript, not ServerScriptService/ResearchService.server.luau. This is deliberate: Roblox's require() only accepts ModuleScript instances — a *.server.luau file compiles to a plain Script, which can never be required by another script. Because ResearchEffectsDispatcher.server.luau needs to call ResearchService.GetLevels(), ResearchService has to be a ModuleScript.

The split mirrors the existing PerkManager.luau (ModuleScript, state + Initialize()) / PerkSystemLoader.server.luau (thin boot Script) pattern:

  • ResearchService.luau defines state + an idempotent Initialize() that wires packets and the tick loop, but does nothing until Initialize() is called.
  • ResearchSystemLoader.server.luau is the only script that calls ResearchService.Initialize(), exactly once per server.

If you ever see require() fail on a *.server.luau/*.client.luau path in this codebase, this is the fix: split the requirable state into a ModuleScript and add a thin loader Script that calls its Initialize().

Studio setup​

Manual, one-time Studio work — none of this is created automatically by code:

  1. Bench Model. The ResearchBench tag on ReplicatedStorage.PlaceableItems.ResearchBench, with PrimaryPart set; placed clones live under workspace.PlacedObjects and inherit the tag. Lookup is by tag, never by name — see The bench is a placeable.
  2. Refund-arc trajectory. A child Model named TrajectoryPoints (tagged PlacementIgnore, per the Placement "tag the CollisionBox only" rule) holding two BasePart children: SpawnPoint (arc start, the bench's output mouth) and LandingPoint (arc end, the floor drop zone). If missing, MaterialPool.ArcPoints falls back to the bench pivot; the refund is still credited.
  3. Research prompt. A child BasePart named TechPromptPart holding a ProximityPrompt — opens the GUI. MaxActivationDistance is set to ResearchConfig.INTERACT_DISTANCE by the client controller at runtime.
  4. No refuel prompt. Refueling is the hold-to-refuel button inside the opened GUI (FuelStack.RefuelButton), one ReqResearchRefuel(points) per release, see Core loop. There is no second ProximityPrompt and no REFUEL_PROMPT_PART_NAME constant.
  5. Material templates. ReplicatedStorage/CraftingMaterials holds Wood and Metal Tool templates whose Handle the clients clone for the cosmetic refund effect — shared with the Shredder, no duplication needed.
  6. StarterGui.TechTreeGui. Built once through the Studio MCP (plan docs/_superpowers/plans/2026-10-14-tech-tree-gui.md, Task 3): the panel plus the Templates folder. Cards and lines are not authored by hand; they come from config. Icon ids go in ResearchConfig.Icons.

The bench is a placeable​

The bench is authored the same way as the Workbench: the ResearchBench tag lives on the template at ReplicatedStorage.PlaceableItems.ResearchBench, so every clone PlacementServer places inherits it. ReplicatedStorage.PlaceableTools.ResearchBench is the matching Tool (attribute PlaceableName = "ResearchBench", with a Handle).

The tag is not identity

CollectionService:GetTagged(BENCH_TAG) matches three different things, in no guaranteed order: the placed bench, the ReplicatedStorage template, and other players' build-mode ghosts — PlacementSystem strips tags from the local ghost but not from the other-player ghosts it parents under workspace.GhostModels, prompts included. This is the trap CannonConfig documents when it says placed cannons are found by attribute and "NOT a CollectionService tag — that would also match client build-mode ghosts."

Both lookups (ResearchService.findBench, the client's isLiveBench) therefore require Parent == workspace.PlacedObjects, the same condition PlaceableActionsServer enforces. A workspace-descendant check is not enough: ghosts live in workspace too, and an unfiltered lookup either measures isNearBench against a template in ReplicatedStorage — failing every enqueue with TOO_FAR — or hands out a working tech tree prompt on someone else's floating preview.

BenchInteractionContainer's MoveButton/StashButton go through PlaceableActions.bind, but PlaceableActionsServer.handleAction additionally requires a non-empty PlaceableName attribute on the placed Model. That attribute is never authored in Studio — PlacementServer stamps it at runtime on the line after it parents the clone (PlacementServer.server.luau, both the place and restore paths), which is why the PlaceableItems templates have no such attribute while the PlaceableTools Tools do (theirs is hand-authored and read at place-time). A bench dragged into workspace.PlacedObjects by hand therefore lacks it. open() checks it into stashable and hides the container when it fails, so the buttons are never visible-but-dead.

The ResearchBench Tool has no source today: it is not in StarterPack and CraftWorkbench is the only Kind = "Placeable" recipe. Stashing the world bench is currently the only way to hold it, so a player who stashes and then loses the Tool loses the bench. Add a Workbench recipe with Output = { Kind = "Placeable", PlaceableName = "ResearchBench" } if that matters.

Gotchas / anti-exploit​

Server re-checks proximity on every request

The client's ProximityPrompt distance is never trusted. ReqResearchEnqueue, ReqResearchCancel, ReqResearchRefuel and a ReqResearchHold(true) press all re-run isNearBench on the server using INTERACT_DISTANCE + INTERACT_DISTANCE_TOLERANCE. A player invoking from range receives TOO_FAR.

Validate-then-consume ordering on enqueue

ReqResearchEnqueue pays with one atomic MaterialPool.Spend(cost): it checks every cost entry against the server-wide pool before subtracting any. If the pool is short on any single material, nothing is consumed — there is no partial-payment state. The gamepass check runs after prereq/queue validation but before the materials check.

Cost is paid on enqueue, not on completion

Materials are deducted the instant a level is successfully enqueued — the queue holds already-paid-for jobs. Cancelling is therefore the only way to get materials back, and only at the refund fractions described in Cascade-cancel.

Gamepass ownership is cached per (player, passId), including denials

UserOwnsGamePassAsync is a yielding web call. ResearchService caches both grants and denials so it isn't re-queried on every enqueue attempt; a purchase completing mid-session clears the cached denial via PromptGamePassPurchaseFinished. A failed web call denies without caching, so the next attempt retries rather than sticking a player with a false negative.

Tuning​

Verification​

Two checks, split by what each can actually see at runtime — there is no automated test suite for this project.

ResearchConfig.validate() — pure data, no DataModel access, runs under RunService:IsStudio() at the bottom of the module so it warns on every Studio session. Asserts every Prereqs entry names a real node in the same branch and a higher row, the prereq graph is acyclic, every node has Levels[1], a known Branch, a whole-number Tier from 1 to MAX_TIER (5, the rows the tree canvas fits), a Column of 0/0.5/1, a free card slot, and Unlocks or Effects; a centred node is alone in its row; no line runs through a card; every Effects entry has a handler in the dispatcher and every StatBuff key has an EffectLabels entry; every branch icon is a key of Icons; and NodeStateColors defines all six fields for all five states. It also warns once while icon ids are blank.

TechTreeGuiRules is pure, so the layout maths and every number-driven string have a Studio self-check (plan docs/_superpowers/plans/2026-10-14-tech-tree-gui.md, Task 1 Step 4).

Everything else is Studio verification, per project convention.
