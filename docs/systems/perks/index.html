Perks

A level-driven permanent progression system, backed by ProfileStore, that lets players spend points and coins on persistent buffs. Two independent point pools — Personal (buffs the owner only) and Party (buffs resolved as the server-max across all players) — each grow by exactly 1 point per XP level; points are derived, never stored. Every perk must be unlocked — a level gate plus a one-time coin + point cost — before it can be upgraded — see Unlock gate. Each upgrade costs 1 point plus coins that rise per level. Respec refunds the exact coins paid (a per-perk ledger) and returns the points. Structured shared/server/client exactly like Quests and Battle Pass.

How it works​

Point and coin economy​

  • Each level-up grants 1 Personal point AND 1 Party point.
  • Available points = playerLevel - spent, computed by PerkState.available — points are never stored directly. spent = the pool's perk levels plus the UnlockPointCost of every unlocked perk in that pool.
  • Points cannot go negative; the pool is floored at 0.
  • Upgrade cost: level n of a perk costs 1 point + UpgradeCoinStep × n coins. PerkState.upgradeCost(perkId, n) is the single price source (server, PerkClient, GUI). UpgradeCoinStep is 100 for perks unlocked at level 0–9, 200 for 10–19, 350 for 20+. Starters pay upgrade coins too.
  • Respec costs nothing to start, returns all points in the chosen pool, re-locks non-starter perks, and refunds every coin paid on them (see Coin ledger).
  • Points carry across places because PerkManager uses the same DataStore key (PlayerPerks) everywhere in the universe.

PerkConfig.Perks is the single tuning surface. Each perk has Category, DisplayName, Description, MaxLevel, display Order, a Buffs list, the unlock fields, UpgradeCoinStep, and an optional Hidden flag. Each BuffSpec is { Key, PerLevel, Format? }: the dispatcher publishes PerLevel * level under Key.

PerkState.effectText(perkId, level) builds the GUI text: every {i} in Description becomes the formatted value of Buffs[i]. Format picks the formatting: "percent" (default, 0.025 → 2.5%), "count" (whole number), "total" (1 + value — Wide Net shows the whole net size), "seconds" (1.5 s). Example: Field Medic at level 5 reads +50% regen, −1.5 s regen delay.

Unlock gate​

Every perk declares an UnlockLevel (player level) gate plus a one-time cost: UnlockCost (coins) and UnlockPointCost (points from the perk's own pool). A perk with all three at 0 is a free starter, auto-unlocked: Iron Constitution (Personal) and Scavenger's Eye (Party).

Unlock is permanent: it persists on the PlayerPerks profile as an Unlocked map ({ [perkId]: boolean }).

function PerkManager.UnlockPerk(player: Player, perkId: string): (boolean, number)
function PerkManager.AllocatePoint(player: Player, perkId: string): (boolean, number)

UnlockPerk validates with PerkState.canUnlock (order: UNKNOWN_PERK → PERK_UNAVAILABLE → ALREADY_UNLOCKED → LEVEL_REQUIRED → NO_POINTS → NOT_ENOUGH_COINS), deducts UnlockCost via CoinManager.DeductCoins, records it in the ledger, marks the perk unlocked, and replicates. AllocatePoint validates with PerkState.canAllocate (order: UNKNOWN_PERK → PERK_UNAVAILABLE → PERK_LOCKED → AT_MAX_LEVEL → NO_POINTS → NOT_ENOUGH_COINS), deducts the upgrade coins before it raises the level (a failed deduct changes nothing), records them in the ledger, fires OnPerkStateChanged, and replicates. The frozen enum (PerkResultCodes):

Unlocking a perk changes no buffs (its level is still 0), so UnlockPerk does not fire Signals.OnPerkStateChanged.

Hidden perks. A perk whose mechanic is not built yet ships with Hidden = true. canUnlock/canAllocate return PERK_UNAVAILABLE, and PerkClient never lists or commands it. PerkState.spent still counts its levels (always 0), so un-hiding needs no migration. After Perk Rework part 5 Batch D no perk is hidden; the flag stays for future perks.

Coin ledger​

CoinsSpent: { [perkId]: number } on the profile records every coin paid per perk (unlock + each upgrade). Respec (PerkManager.Respec, a pool) and per-perk respec (PerkManager.RespecPerk) refund exactly CoinsSpent[perkId] through CoinManager.RefundCoins — un-inflated, not scaled by the Pocket Change CoinGainBonus — then clear the entry. Only the ledger decides a refund, never current prices, so a later re-tune of UnlockCost or UpgradeCoinStep never changes what a reset returns. If the coin profile is gone mid-respec, the perk is still reset and a warn names the lost amount.

Respec clears PerkLevels, re-locks non-starter perks, then re-seeds starters. Per-perk respec is validated by PerkState.canRespecPerk (UNKNOWN_PERK → NOTHING_TO_RESET). Both fire OnPerkStateChanged and replicate. The starter rule lives in one place, PerkState.isStarter.

Migration​

migrateAndSeed runs on every load; each step is version-guarded:

  • Schema 1 (PerkSchemaVersion < 1): one-time clean-slate wipe of PerkLevels/Unlocked.
  • Schema 2 (PerkSchemaVersion < 2, the Perk Rework): the 12 old perks are gone. The v1 unlock prices of every old unlocked perk (frozen in LEGACY_V1_UNLOCK_COSTS inside PerkManager; starters add 0) are added to the persisted PendingLegacyRefund, then PerkLevels, Unlocked and CoinsSpent are wiped and the version is set to 2.
  • Starters are re-seeded after the steps.

The wipe never waits. The payout waits for the coin profile: payLegacyRefund polls CoinManager.IsLoaded for up to 60 s, then refunds PendingLegacyRefund and sets it to 0. If the coin profile does not load in time (or the perk session ends first), the amount stays saved and is paid on a later join — never lost, never paid twice.

Where perk commands run​

PerkManager.Initialize() loads profiles, migrates, replicates and resends on level-up. The four request packets are bound only by PerkManager.WireCommandHandlers(), which only the Lobby's PerkLoadoutService calls: perk changes are Lobby-only. In the Game Instance the Perk menu's buttons get no answer (Studio logs OnServerInvoke not found) until Perk Rework part 4 makes that menu read-only.

PerkManager, CoinManager, XPManager and PerkInventoryManager each register a teleport hand-off with PersistenceRegistry: the Lobby ends their sessions without a kick right before a party teleport and reopens them if it fails. See Perk Inventory.

Shop perks (consumable and expiring, equipped in the Lobby) are a separate system: see Perk Inventory.

Party-max resolution​

Party perks apply to the entire server, but only the highest level held by any single player is active. If Player A has Fuel Saver 6 and Player B has Fuel Saver 3, the server resolves at 6. PerkEffectsDispatcher recomputes the max on every allocate, respec, player join, and player leave.

Shop perk layer​

Perk Rework part 3 adds shop perks on top of the permanent perks. PerkEffectsDispatcher stays the only writer; for every key:

  • Personal: permanent value + the sum of the player's live shop perks.
  • Party: permanent party max + each live party shop perk, counted once. Two players with the same party perk do not stack; different perks of one family do. <ShopPerkId>HolderId names the first holder (0 = not active).

A shop perk is live when it is in this run's ActiveRun (read only through PerkInventoryManager.GetActiveRun), visible, and (expiring) its clock has not ended. Every shop key is written each publish (0 when nothing is live), so an ended perk clears its key. The math lives in the pure ShopPerkEffects module (Studio self-check at boot). A shop key with no reader logs one warn at boot.

Expiry: the clock is real time. The dispatcher keeps one task.delay to the earliest upcoming expiry among present players and republishes when it fires, so a perk can end mid-run.

Junk bridges: JunkService overwrites its multipliers, so the dispatcher sends one value per tier — tier 1 1 − TierOneShift, tier 2 1 + TierOneShift · w1 / w2 (Golden Lure keeps the tier 1+2 total), tiers 3–5 1 + JunkTierRarityBonus — and ApplyTypeMultiplier("Energy", 1 + EnergySpawnBonus) (Energy Forecast).

Buff contract​

PerkEffectsDispatcher is the sole writer of the buff folders — every other system reads, never writes. It listens to Signals.OnPerkStateChanged, Signals.OnShopPerksChanged, PlayerAdded, PlayerRemoving and the next shop perk expiry, then calls publishPersonal and publishParty. Both write every BuffSpec.Key of every perk in the pool, and every shop key of the pool. It also bridges Scavenger's Eye / Lucky Streak / Golden Lure to Signals.ApplyTierMultiplier and Energy Forecast to Signals.ApplyTypeMultiplier, which JunkService consumes.

Armor damage mitigation​

Crafted armor (see Armor / ArmorConfig / ArmorManager) is the base of this mitigation, not the perk. HealthManager's damage sink calls ArmorManager.Absorb(player, amount, efficiency), passing the player's ArmorEfficiency perk bonus read fresh on every hit. The Plated perk does not reduce damage on its own; it's an efficiency multiplier on the equipped kind's BaseReduction, applied identically whether the worn kind is Ballistic or Energy:

reduction = clamp(kind.BaseReduction * (1 + ArmorEfficiency), 0, ArmorConfig.MaxReductionCap)

Absorb scales amount by (1 - reduction) as the final step before it reaches health, and drains the worn kind's pool by whatever was absorbed — mitigation and pool drain happen in the same call, because the two cannot be split without the pool going stale (see Armor — Mitigation). With nothing equipped, or an Energy kind at zero pool, the perk contributes nothing. Because the attacker's DamageBonus is already applied upstream in WeaponServer, attacker bonus and defender mitigation multiply independently: base * (1 + DamageBonus) * (1 - reduction). Coverage is every path routed through CombatService/HealthManager (Bullet/AOE and NPC hits); damage written directly to Humanoid.Health bypasses the sink and is not mitigated (see Health).

Client​

PerkClient.luau is the GUI-agnostic data layer (owns no GUI). It caches the authoritative PerkStateSync snapshot (perkLevels, unlocked, personalAvailable, partyAvailable, playerLevel, coinsSpent) and watches the replicated PartyPerkBuffs folder. A snapshot without coinsSpent (an older server during a live update) reads as {}. Queries return PerkView descriptors via GetPerks/GetActivePerks/GetAvailablePoints/GetPerk/GetPlayerLevel; hidden perks are skipped. Commands: optimistic-prediction Allocate/Respec/CanRespec, plus Unlock(perkId) (no optimistic coin prediction — the server owns the balance), and a Changed signal fired on every snapshot update.

"Active" is category-aware: a Personal perk is active at the player's Level > 0; a Party perk is active at its server-wide ActivePartyLevel > 0 (read from <PerkId>Level). PerkView carries Group, Summary, EffectText, NextEffectText (nil at max), UpgradeCost (coins for the next level, 0 at max), CoinsSpent (what a reset refunds), CanRespec, the unlock fields, and for Party perks ActiveEffectText and ActivePartyHolder: Player? (from <PerkId>HolderId). PerkController.client.luau is the one-line bootstrap that calls PerkClient.Init() once on join.

Active Perks menu. ActivePerksGuiController.client.luau binds the Studio-authored StarterGui.ActivePerksGui, a read-only view and the Game Instance's only perk GUI. It opens from a TopbarPlus "Active Perks" icon (toggle key O; CloseButton deselects it). The detail panel (BottomSection.InfoContainer) shows the name, Level N (Party: the active server level), one effect line, PerkOwner (Personal: you; Party: ActivePartyHolder, hidden when nil), and PerkConfig.CategoryBlurb. For a shop perk it shows This<br/>run (consumable) or Time<br/>h:mm:ss (expiring, your own clock, ticking once a second while open), Time<br/>— for a Party perk only another player holds (the client knows only its own clocks), the Description as the effect line, and the holder as PerkOwner. It repaints on PerkClient.Changed (also PartyPerkBuffs changes) and PerkInventoryClient.Changed; an own clock that ends drops its row. A tab with nothing active hides the detail panel. It has no reset button: perk changes are Lobby-only.

Locked: dimmed, Lv N / Unlock / Locked, and CostLabel (1 pt + 250 coins). Gotchas​

New readers must use PerkBuffRead

Read buff values through PerkBuffRead.Personal / PerkBuffRead.Party, and apply reductions with PerkBuffRead.Reduce / ReduceCost. Do not add new inline PerkBuffs folder lookups, and never let a reduction stack reach zero. PerkBuffRead and PerkState run Studio-only boot asserts on the shared math.

Points are derived, not stored

Available points are never stored directly. Available points = level - spent. Never add a separate stored point counter — it will desync.

Refunds come from the ledger only

A respec refunds CoinsSpent[perkId], never a price recomputed from the config. Any new coin charge on a perk must call recordPaid, or a reset will under-refund.

Party perk levels shown in the GUI are per-player, not the resolved active level

A Party card's LV n/max and the detail panel's CURRENT LEVEL show how many levels this player bought. The Active Perks menu shows the server-resolved max.

PerkEffectsDispatcher must run before PerkManager on join

PerkEffectsDispatcher seeds its folder at boot. PerkManager fires OnPerkStateChanged after profile load, which triggers a republish. The ordering is correct because both are ServerScriptService scripts and PerkManager.Initialize() is called from PerkSystemLoader, which yields on ProfileStore:StartSessionAsync before firing the signal.

HPBonus subscription attaches once at join

HealthManager subscribes to the HPBonus attribute change in PlayerAdded, not CharacterAdded. If PerkBuffs/<UserId> does not exist at join time (the dispatcher hasn't seeded yet), the subscription is skipped for that session. In practice the dispatcher seeds synchronously at boot, so the folder exists before any player's PlayerAdded fires normally.

    participant Manager as PerkManager (server)

    Note over Manager: JOIN
    Manager->>Manager: profile loaded (migrateAndSeed: schema steps + seedStarters)
    Manager->>Coins: payLegacyRefund (waits for IsLoaded, then RefundCoins)
    Manager->>Client: PerkStateSync(levels, unlocked, personalAvail, partyAvail, playerLevel, coinsSpent)
    Manager->>Dispatcher: publish personal buffs (0s); publishParty()

    Note over Client,Manager: UNLOCK
    Client->>Manager: ReqUnlockPerk(perkId)
    Manager->>Coins: DeductCoins(UnlockCost)
    Manager->>Manager: CoinsSpent[perkId] += UnlockCost; Unlocked[perkId] = true
    Manager->>Client: PerkStateSync (no OnPerkStateChanged — buffs unchanged)

    Note over Client,Manager: ALLOCATE (upgrade)
    Client->>Client: optimistic level++, avail--; repaint()
    Client->>Manager: ReqAllocatePerk(perkId)
    Manager->>Manager: canAllocate (points + coins)
    Manager->>Coins: DeductCoins(UpgradeCoinStep × nextLevel)
    Manager->>Manager: CoinsSpent[perkId] += cost; level++
    Manager->>Dispatcher: Signals.OnPerkStateChanged:Fire(player)
    Manager->>Client: PerkStateSync(...)
    Dispatcher->>Dispatcher: publishPersonal(player); publishParty()

    Note over Client,Manager: RESPEC
    Client->>Manager: ReqRespecPerk(perkId) / ReqRespecPerks(pool)
    Manager->>Coins: RefundCoins(CoinsSpent[perkId])
    Manager->>Manager: clear level + ledger; re-lock non-starters
    Manager->>Dispatcher: Signals.OnPerkStateChanged:Fire(player)
    Manager->>Client: PerkStateSync(...)

    Note over Manager: LEVEL UP
    Manager->>Client: PerkStateSync(levels, unlocked, personal+1, party+1, newLevel, coinsSpent)

FieldEffect
Perks[id].BuffsList of { Key, PerLevel, Format? }; each key publishes PerLevel * level.
Perks[id].MaxLevelCap on levels in this perk.
Perks[id].DisplayNameShown in the perk panel header.
Perks[id].DescriptionEffect text; {1}, {2} … become the formatted value of Buffs[1], Buffs[2] ….
Perks[id].UnlockCostOne-time coin cost to unlock (0 = free starter).
Perks[id].UnlockLevelMinimum player XP level required to unlock (0 = none).
Perks[id].UnlockPointCostOne-time point cost from the perk's own pool; counted as spent, returned by respec (0 = free).
Perks[id].UpgradeCoinStepLevel n costs UpgradeCoinStep × n coins. Re-tuning never changes refunds (ledger).
Perks[id].Hiddentrue = declared but not listed or unlockable (part 5 flips it).
MIN_REDUCTION_FACTORLowest fraction of a base value any reduction can leave (default 0.1).
NET_REEL_SLOWDOWN_PER_EXTRAWide Net: reel slows by this fraction per extra junk in one cast (default 0.10).
RESPEC_HOLD_TIMESeconds a reset-all (whole pool) button must be held before the respec fires (default 3).
RESPEC_PERK_HOLD_TIMESeconds a single-perk reset button must be held (default 0.75; shorter, as it undoes much less).
CategoryBlurbOne-line pool explanation shown in both perk menus' detail panels.
STORE_NAMEProfileStore key — change this only if you intentionally want to wipe all saved perk + unlock data.
