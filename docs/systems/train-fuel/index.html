Train Fuel

A single global fuel value (0–100) governs the train's Running/Braked/Stalled state for all players. The server computes fuel algebraically from the timestamp of the last event rather than polling every frame; every state transition snapshots the current fuel, switches the drain rate, and schedules the next deterministic transition via a nonce-guarded task.delay. Clients receive a snapshot and predict the bar locally between events — TrainFuelManager is the sole authority.

How it works​

Algebraic fuel model​

getFuel() is computed as fuelAtLastEvent - currentRate * elapsed rather than ticked every frame. commitEvent snapshots fuel under the old rate before switching to the new one, so every transition (brake, refuel, stall) is seamless. A scheduleNonce guards task.delay callbacks: any subsequent commitEvent increments the nonce, and a stale callback no-ops if its captured nonce no longer matches. Do not call reschedule directly — always go through commitEvent.

While hasStarted = false (before the first brake release), the drain rate is forced to 0 and no task.delay stall timer is scheduled — fuel is frozen pre-game.

Brake toggle​

Triggering a TrainBrakeLever-tagged prompt sends ReqToggleBrake(lever). The server flips isBraked; on the first-ever un-brake it also sets hasStarted = true and fires Signals.SetTrainStarted(true). Either way it calls commitEvent(), which reschedules the stall task.delay under the new rate and broadcasts TrainStateSync. The client updates the lever's ActionText ("Stop Train" / "Resume Train") from the returned isBraked.

Lever animation​

Purely cosmetic and entirely client-side — the server never knows the lever's physical pose. TrainClient swings the pivot by BRAKE_LEVER_SWING_DEG about the pivot's own Z axis between the two brake states, using MotionMaster (never TweenService), and plays BRAKE_LEVER_ANIM_ID once on the model's Animator as a button-press flourish plus the TrainBrakeLever SFX.

Which end means "braked" is a property of how the model was posed, not of the brake logic, so it lives in config: BRAKE_LEVER_REST_IS_BRAKED says whether the authored pose is the braked one. If the lever reads backwards in-game, flip that boolean — don't negate BRAKE_LEVER_SWING_DEG, which only changes which way it rotates.

Three rules keep it honest:

  • Only a flip animates. TrainStateSync also arrives on refuel and stall events, so the handler compares isBraked against the previous value — otherwise the lever would re-swing every time someone tops up the tank.
  • Joining snaps. The first snapshot after joining, and any lever that registers late (tag added at runtime, streaming), poses instantly with no swing.
  • Reversal is continuous. The in-flight tween lives in the lever's Janitor under the "leverTween" index; adding a new one there destroys the old, which pauses it in place rather than resetting it, so a mid-swing toggle starts from wherever the lever actually is.

Every client animates from the same replicated isBraked, so no extra network traffic is needed to keep the levers agreeing.

Refuel​

Triggering a TrainEngine-tagged prompt sends ReqRefuelTrain(engine). The server validates the tag, proximity, and that the tank isn't already full, gathers the player's Energy tools via EnergyToolHelper.GatherEnergyTools, consumes them smallest-tier-first up to MAX_FUEL, clears a stall if fuel becomes > 0, then calls commitEvent(newFuel). A boolean isRefueling mutex serializes concurrent requests — it is not a queue, so a second request while one is in flight returns NO_ENERGY even if the player holds tools; the player can retry immediately after.

Game-over reasons​

There are exactly two ways a round ends, both funneled through TrainGameOver.Trigger(reason) so the game-over sequence fires exactly once regardless of which path gets there first:

ReasonCodeTrigger pathGrace?
FUEL_DEPLETED1Natural fuel-out. Fuel algebraically reaches 0 → onStall() marks the train stalled and broadcasts the 0 → after GAME_OVER_DELAY (180s) elapses with no refuel, onGameOver() fires.Yes — GAME_OVER_DELAY seconds to refuel before it's final.
FUEL_DESTROYED_BY_ATTACK2Combat fuel-kill. TrainShieldManager.ApplyDamage routes hits to ApplyFuelDamage once the shield is at 0; if that hit drives fuel to exactly 0, the trigger fires immediately.No — immediate, no GAME_OVER_DELAY.

TrainGameOver.Trigger(reason: number?) stores the reason (GetReason() returns it) and fires Signals.OnTrainGameOver(reasonCode) exactly once per round; Reset() clears the flag for a future round restart (not yet wired). Both paths currently only log and fire the signal — the real game-over mechanic (round reset / respawn / UI) is a placeholder.

TrainFuelManager.ApplyFuelDamage(amount: number, source: any?) is the combat fuel-damage sink. amount is fuel units already converted by TrainConfig.FUEL_DAMAGE_FACTOR — the only caller today is TrainShieldManager.ApplyDamage, once the shield is at 0. Guards (all must pass or the call is a no-op): hasStarted must be true, TrainGameOver.HasFired() must be false, amount must be > 0 and not NaN. If the hit leaves fuel above 0 it just commits the lower level (the natural stall timer shortens). If it drives fuel to exactly 0, isStalled and gameOverFired are set before commitEvent(0) so no grace timer arms, then TrainGameOver.Trigger(FUEL_DESTROYED_BY_ATTACK) fires with no wait.

Client HUD prediction​

TrainFuelGuiController reads the authored StarterGui.TrainFuelGui (never creates UI). It holds no snapshot of its own — every RenderStepped frame it asks TrainStateCache.PredictedFuel() for the extrapolated fuel level (fuel - rate * (now - serverTime), clamped to [0, MAX_FUEL]) and smooths displayedFuel toward it with frame-rate-independent exponential smoothing (k = 8). It sets FuelBar.Size/FuelText.Text and colors the bar green (running) / amber (braked) / red (stalled) from the cached snapshot's isBraked/isStalled.

Before the server has sent a snapshot, PredictedFuel() returns nil — the controller never invents a starting value (it used to seed one from TrainConfig.INITIAL_FUEL/MAX_FUEL plus a client-read workspace:GetServerTimeNow(), which is what produced the reported 0% flash; see Join-Sync Snapshot Handshake). While nil, the HUD renders a placeholder ("—", a neutral grey, zero-width bar) instead. The first non-nil value is applied directly rather than eased into, so there is no visible sweep from a guessed number.

Studio setup​

Each TrainEngine-tagged and TrainBrakeLever-tagged root (a Model or BasePart) must contain a BasePart named TrainConfig.PROMPT_PART_NAME ("ProxPromptPart") with a child ProximityPrompt. Both client and server resolve the prompt part recursively via PromptResolver, so it may be nested at any depth. The prompt's MaxActivationDistance and the engine's ActionText are authored in Studio; only the lever's ActionText is set by script.

A brake lever model additionally needs, for the animation:

  • A PrimaryPart acting as the pivot, anchored, with all moving geometry WeldConstrainted (or Motor6Ded) to it. An assembly containing an anchored part is rigid, so writing PrimaryPart.CFrame carries the whole lever on every client with no physics ownership involved. Without a PrimaryPart the prompt still works and the animation is skipped with a warning.
  • The lever saved in a known pose, with TrainConfig.BRAKE_LEVER_REST_IS_BRAKED set to say which state that pose represents. The current rig follows the usual convention — lever pulled toward the player means braked — and is authored that way, hence BRAKE_LEVER_REST_IS_BRAKED = true.
  • Optionally an AnimationController/Animator for the button press. No Animator simply means no press flourish.

Do not leave a Script inside the model driving the lever itself — the pose is owned by TrainClient and a second writer will fight it.

Gotchas​

Game-over is a placeholder

Both onGameOver() (natural) and the immediate combat-kill path in ApplyFuelDamage funnel through TrainGameOver.Trigger, which only logs and fires Signals.OnTrainGameOver. No round reset, respawn, or UI is triggered. Do not ship without replacing the placeholder with a real mechanic.

Combat fuel-kill skips the grace delay

Unlike natural stall-out, a fuel-zeroing hit via ApplyFuelDamage ends the round immediately — GAME_OVER_DELAY is not consulted on that path. See Game-over reasons.

Algebraic drift note: commitEvent captures now() once and uses it for both lastEventTime and the serverTime field broadcast in TrainStateSync. Any task.wait or async work inserted between the snapshot and the broadcast would drift the client's extrapolation baseline — keep commitEvent synchronous.

Data flow​

sequenceDiagram
    participant Sv as TrainFuelManager
    participant Cl as TrainClient
    participant Cache as TrainStateCache
    participant Gui as TrainFuelGuiController

    Note over Sv,Cl: JOIN - via JoinSync on ClientReady, not PlayerAdded
    Sv->>Cl: TrainStateSync(fuel, rate, isBraked, isStalled, serverTime)
    Cl->>Cache: SetFuel(snapshot)
    Cl->>Cl: Signals.OnTrainStateChanged(snap) - MusicDirector, lever ActionText

    Note over Cl,Sv: BRAKE TOGGLE
    Cl->>Sv: ReqToggleBrake(lever)
    Sv->>Sv: validate lever tag + proximity, flip isBraked (first un-brake: hasStarted=true)
    Sv->>Sv: commitEvent() - snapshot fuel, switch rate, scheduleNonce++, reschedule()
    Sv-->>Cl: (success, isBraked, code)
    Sv->>Cl: TrainStateSync(...)

    Note over Cl,Sv: REFUEL
    Cl->>Sv: ReqRefuelTrain(engine)
    Sv->>Sv: validate proximity + not full, consume Energy tools smallest-tier-first
    Sv->>Sv: commitEvent(newFuel)
    Sv-->>Cl: (success, fuelAdded, code)

    Note over Sv: NATURAL STALL -> GAME OVER
    Sv->>Sv: task.delay(timeToEmpty) fires -> onStall(): isStalled=true, commitEvent(0)
    Sv->>Sv: task.delay(GAME_OVER_DELAY) fires -> onGameOver()
    Sv->>Sv: TrainGameOver.Trigger(FUEL_DEPLETED) - OnTrainGameOver(1), once per round

    Note over Sv: COMBAT FUEL-KILL (immediate, no grace)
    Sv->>Sv: TrainShieldManager.ApplyDamage while shield==0 -> ApplyFuelDamage(amount*FUEL_DAMAGE_FACTOR)
    Sv->>Sv: newFuel<=0: isStalled=true, gameOverFired=true, commitEvent(0)
    Sv->>Sv: TrainGameOver.Trigger(FUEL_DESTROYED_BY_ATTACK) - immediate, skips GAME_OVER_DELAY

    Note over Gui: CLIENT HUD LOOP (RenderStepped)
    Gui->>Cache: PredictedFuel() - nil until first snapshot -> render placeholder
    Gui->>Gui: predicted = snap.fuel - snap.rate*(now-snap.serverTime); smooth k=8
    Gui->>Gui: FuelBar.Size + color (green/amber/red)
