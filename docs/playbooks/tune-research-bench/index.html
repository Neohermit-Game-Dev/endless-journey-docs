Tune Research Bench

Goal: Adjust Research Bench node costs/durations, fuel/queue/refund constants, or add a new node.

Steps​

  1. Change a node's per-level cost or duration. Open src/ReplicatedStorage/SharedModules/Configs/ResearchConfig.luau and edit the Levels table on the node:

    Durability_T1 = {
        Category = "Train",
        DisplayName = "Scrap Plating",
        Description = "+%d shield capacity",
        Prereq = nil,
        MaxLevel = 3,
        Effect = { Type = "StatBuff", Key = "MaxHP", PerLevel = 50 },
        Levels = {
            [1] = { Cost = { Metal = 25 },  Duration = 20 },  -- ← per-level cost / time
            [2] = { Cost = { Metal = 60 },  Duration = 35 },
            [3] = { Cost = { Metal = 120 }, Duration = 55 },
        },
    },

    Cost is a { [materialItemType]: number } map — any ItemType that exists as a craft-material Tool template under ReplicatedStorage/CraftingMaterials is valid (not just Wood/Metal; unlike the Workbench GUI, the Research GUI renders however many cost rows a node has). Duration is in seconds and is the wall-clock time the level takes to complete while fuel is available — see step 2 below. Both values take effect immediately for any job enqueued after the change; jobs already queued or active keep the cost/duration they were enqueued with (no live re-pricing).

    Changing Effect.PerLevel (for StatBuff) or Effect.DrainPerLevel (for FuelEfficiency) changes the buff granted per level — see step 5 for the effect shapes. No code change is needed; ResearchEffectsDispatcher recomputes buffs from ResearchConfig.Nodes on every level-up.

  2. Review the fuel and pause behavior before retuning it.

    • FUEL_CAP (default 100) — the fuel reserve ceiling.
    • FUEL_BURN_RATE (default 1.0/sec) — how fast fuel burns while a job is active. Raising this makes fuel run out faster relative to node Duration, so jobs pause more often; consider raising EnergyFuelValue in tandem if you raise this.
    • EnergyFuelValue (default {20, 35, 55, 80, 110} for Energy tool tiers 1–5) — fuel granted per refuel. Tune this against FUEL_BURN_RATE * <typical node Duration> so a single refuel roughly covers the jobs you want it to.

    A job's elapsed only advances while fuel is available (ResearchState.advance clamps effectiveDt = min(dt, fuel / burnRate)), so at FUEL_BURN_RATE = 1.0 and FUEL_CAP = 100, a fully-fueled bench can sustain 100 seconds of active research before needing a refuel.

  3. Change the queue depth. QUEUE_MAX (default 8) caps how many jobs can wait behind the active one (ResearchState.validateEnqueue rejects with QUEUE_FULL beyond this). Raise it to let players stack more research ahead of time; lower it to force more frequent bench visits.

  4. Change the cancel refund fraction. ACTIVE_REFUND_FRACTION (default 0.5) is the fraction of the active job's cost refunded when it is cancelled — queued jobs always refund at 1.0 (full), since they haven't started consuming fuel/time yet. Set this to 1.0 to make cancelling an in-progress job free, or 0 to make active progress non-refundable. This does not affect the cascade behavior itself (see Research Bench — Cascade-cancel) — only the fraction applied to the active job's refund.

  5. Add a new node.

    • Declare it in ResearchConfig.Nodes. Pick a unique key (the nodeId), a Category ("Train", "Player", "Equipment", or "Recipes" — display grouping only, drives which header the node's row appears under in the GUI), DisplayName (the only descriptive text the shipped ResearchGuiController renders per row today — Description is authored in config but not currently displayed; add it to the row-building code if you want it shown), an optional Prereq (another node's id — nil means available from the start) and PrereqLevel (defaults to 1 if omitted — the level the prereq must reach before this node accepts enqueues), MaxLevel, and Levels (one {Cost, Duration} entry per level from 1 to MaxLevel).

      Example — a new two-level "Reinforced Hull" node gated behind Durability_T1 reaching level 2:

      ReinforcedHull = {
          Category = "Train",
          DisplayName = "Reinforced Hull",
          Description = "+%d shield capacity",
          Prereq = "Durability_T1",
          PrereqLevel = 2,
          MaxLevel = 2,
          Effect = { Type = "StatBuff", Key = "MaxHP", PerLevel = 75 },
          Levels = {
              [1] = { Cost = { Metal = 150, Wood = 20 }, Duration = 60 },
              [2] = { Cost = { Metal = 260, Wood = 40 }, Duration = 90 },
          },
      },

    • Choose an Effect shape (omit entirely — Effect = nil — for a pure recipe/gate node with no buff):

      • { Type = "StatBuff", Key = <attributeName>, PerLevel = <number> } — the effect handler in ResearchEffectsDispatcher sums PerLevel * level across every node sharing the same Key into that attribute on ReplicatedStorage/ResearchBuffs. Reuse an existing Key (e.g. "MaxHP") to stack with existing nodes, or introduce a new Key and wire a new consumer to read it.
      • { Type = "FuelEfficiency", DrainPerLevel = <number, 0 < n < 1> } — multiplies into ResearchBuffs.FuelEfficiency as DrainPerLevel ^ level (values below 1 reduce drain; e.g. 0.85 per level means 3 levels compound to 0.85^3 ≈ 0.614). TrainFuelManager already reads this attribute — no new consumer needed if you're adding another fuel-efficiency node.
      • Any other Type string logs a warn and no-ops in ResearchEffectsDispatcher — safe to author a node ahead of its gameplay wiring, but the buff will not apply until a handler exists.
      • nil — a recipe/gate node. Once it reaches level 1, ResearchUnlocked/<nodeId> is written; wire a Workbench recipe's RequiresNode to that same id (see Workbench Crafting), or read the folder from any other gate you want to add.

    • Test in Studio: join at the bench, confirm the new row appears under the right Category header (locked/greyed if Prereq isn't met yet), enqueue it, and confirm materials are deducted immediately. Let it complete (or refuel to speed through fuel pauses) and confirm the effect applies — check the ReplicatedStorage/ResearchBuffs attribute in Explorer for a StatBuff/FuelEfficiency node, or ReplicatedStorage/ResearchUnlocked/<nodeId> for a recipe node.

Verify​

  1. Join in Studio with API Services enabled, walk to the ResearchBench-tagged Model.
  2. Open the GUI (ResearchPromptPart prompt) and enqueue a cheap node's level 1.
  3. Confirm materials are deducted immediately (before the job completes) and the active panel shows the job progressing.
  4. Let fuel run to 0 (or start with an empty bench) and confirm the progress bar stops advancing and the "PAUSED" badge appears; trigger RefuelPromptPart with a held Energy tool and confirm progress resumes.
  5. Queue a second level of the same node behind the first, then cancel the first (lower) level from the active panel — confirm both the active job and the queued second level refund and clear (cascade-cancel), and that ReplicatedStorage/ResearchUnlocked/ResearchBuffs do not update for a job that never completed.
  6. Let a StatBuff node complete and confirm the target attribute in ReplicatedStorage/ResearchBuffs updates, or let a recipe node complete and confirm ReplicatedStorage/ResearchUnlocked/<nodeId> appears and the corresponding Workbench recipe ungreys.
