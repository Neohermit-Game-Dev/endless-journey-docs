Armor

Crafted armor mitigates incoming damage at the single HealthManager sink. Armor comes in two types that share one mechanic — a pool field that drains by the damage actually absorbed — and differ only in what happens at zero: a Ballistic kind's pool is durability, and the set is destroyed and unequipped when it runs out; an Energy kind's pool is a reserve that survives at zero, stays worn, and simply protects nothing until it is recharged at a workbench. ArmorManager owns ownership, pools and persistence; ArmorConfig is the only place any of it is tuned.

How it works​

The two types​

Every armor kind — Ballistic or Energy — is defined entirely by ArmorConfig.Kinds[kindId] (Type, Tier, BaseReduction, Pool, RequiresNode) plus one persisted number: pool remaining. ArmorManager.Absorb drains that number by whatever damage the hit actually absorbed, identically for both types. The only branch is what happens when the pool reaches zero:

  • Ballistic — the set is destroyed: owned[kindId] is cleared and, if it was worn, Equipped is cleared too. The player is unarmored until they craft another.
  • Energy — the kind stays in Owned and stays Equipped. Absorb returns the full incoming amount unmitigated (pool <= 0 short-circuits before any reduction), so a drained Energy set simply does nothing until ArmorManager.Recharge refills it.

The catalog​

ArmorConfig.Kinds is the entire catalog — five kinds, no separate tier ladder (Tiers no longer exists; Tier on a kind is a display badge only):

Kind idTypeTierReductionPoolResearch node
LightBallistic10.10250Armor_Light
MedBallisticBallistic20.20500Armor_MedBallistic
MedEnergyEnergy20.14700Armor_MedEnergy
HeavyBallisticBallistic30.30900Armor_HeavyBallistic
HeavyEnergyEnergy30.221200Armor_HeavyEnergy

By design, the Energy kind at a given tier always reduces less than its Ballistic counterpart (0.14 vs 0.20 at tier 2; 0.22 vs 0.30 at tier 3) — a refillable reserve trades raw mitigation for never being permanently destroyed. Light has no tier-1 Energy counterpart. Reduction, pool size, type and tier are all derived from this table at read time, so retuning a kind here applies retroactively to every player already holding it.

Crafting​

Each kind has a matching recipe in WorkbenchConfig.Recipes (CraftArmorLight, CraftArmorMedBallistic, CraftArmorMedEnergy, CraftArmorHeavyBallistic, CraftArmorHeavyEnergy), each with Output = { Kind = "Armor", ArmorKind = "<id>" } and its own RequiresNode gate matching the table above. WorkbenchService's craft handler checks CraftOutputDispatcher.isFeasible(player, output) before consuming materials; for an Armor output that calls ArmorManager.OwnsAtFullPool, so crafting a kind already at full pool is refused up front and costs nothing. Crafting a kind that is owned but damaged (or destroyed, for a Ballistic kind) instead calls ArmorManager.Grant, which refills it to full — recrafting is how a set is repaired. Grant also auto-equips the kind if the player has nothing worn, so a player's first craft is immediately useful without a separate equip step.

Mitigation​

HealthManager.ApplyDamage is the single damage sink for every attack category (Bullet/AOE/environment/NPC). Its internal applyDamageInternal reads the player's ArmorEfficiency perk bonus and calls ArmorManager.Absorb(player, amount, efficiency) on every hit — no caching, so crafting, equipping or recharging armor takes effect on the very next hit. Absorb computes reduction = clamp(kind.BaseReduction * (1 + efficiency), 0, ArmorConfig.MaxReductionCap) for whichever kind is equipped, exactly as the armor-efficiency perk (now Plated) already worked before this system existed (see Perks — Armor damage mitigation), then drains the pool by min(amount * reduction, pool). A hit never absorbs more than the pool has left, so the overflow of the hit that breaks a Ballistic set still reaches health in the same call. With nothing equipped, or an Energy kind at zero pool, Absorb returns the full amount and health takes it all.

Equipping and recharging​

Both Equip and Recharge are workbench actions — ReqEquipArmor and ReqRechargeArmor — handled by ArmorService, which validates the target with WorkbenchStation.IsValidStation and WorkbenchStation.IsPlayerNear (the same checks WorkbenchService uses for crafting) before delegating to ArmorManager. Client input is never trusted: both the bench and the distance are re-derived from server-owned state on every request.

ArmorManager.Recharge refills an owned Energy kind's reserve by spending shared pool Energy via MaterialPool.SpendUpTo("Energy", Pool − reserve, ArmorConfig.RESERVE_PER_POINT) — only the points needed, stopping at the Pool cap. It draws on the same material pool Energy the train burns for fuel (mirroring TrainFuelManager.handleRefuel), and needs no serialization: the path is synchronous with no yield point, so two in-flight requests can't interleave.

Client​

ArmorClient is a GUI-free read model, structured like PerkClient/QuestClient: it caches the ArmorStateSync snapshot, exposes IsReady/GetArmors/GetEquipped queries returning ArmorView descriptors, carries the Equip/Recharge request/response calls — both are declared with Packet:Response(...), so calling them on the client yields until the server answers and returns (ok, code) and (ok, energyAdded, code) respectively (no optimistic prediction — the server owns ownership and pools) — and fires Changed on every snapshot update. ArmorController.client.luau is the one-line bootstrap that calls ArmorClient.Init() once on join.

The player-facing surface is the Workbench GUI's armory page (ArmoryContainer, reached by the Recharge tab), driven by WorkbenchGuiController. The page is gated on owning at least one armor: with none, the tab, a swipe, gamepad or scroll wheel all bounce back to the workbench page with a "You must wear or craft an armor to access Recharge." toast. The gate checks owned, not worn, because this page is the only place to equip — an unworn owned set (e.g. after a worn Ballistic set broke) must stay reachable. If the last armor breaks while the page is showing, or a reopen lands on it, it silently returns to the workbench page.

  • Inventory (RightContainer…InventoryContainer.ScrollingFrame) — one item per owned kind, cloned from ExampleItem, in ArmorClient.GetArmors() order. Tapping one selects it; the selected item's UIStroke is opaque, the rest 0.7. With nothing selected (or the selected Ballistic set broke) the selection falls back to the worn kind, then the first owned.
  • Detail — name, EquipButton (worn kind: EQUIPPED, Interactable = false, bg #130f18; any other kind: EQUIP, interactable with AutoButtonColor, bg #383753, sends ReqEquipArmor), base reduction and RECHARGEABLE (TRUE for Energy kinds). Icons borrow the kind's CraftArmor* recipe icon, since ArmorConfig carries no art.
  • Recharge (LeftContainer.ArmorRechargeContainer) — FillBar and percent show the selected kind's PoolFraction; ENERGY RESERVE shows pool Energy. Holding ChargeButton for ArmorConfig.RECHARGE_HOLD_TIME eases the fill toward the level the pool Energy can reach, then sends one ReqRechargeArmor; releasing early (anywhere on screen) snaps it back. HintText always reads HOLD TO RECHARGE, except for a Ballistic kind: there the fill still shows durability, ChargeButton.Interactable is false, and the hint reads CANNOT RECHARGE THIS ARMOR in warning red (230,150,150, readable on the #1f1927 backing). A full Energy reserve also sets Interactable false. With no pool Energy the button stays enabled, and a press toasts "No energy to spare." (ArmorClient.CodeMessages[NO_ENERGY]) instead of starting the hold.

Gotchas​

Equipping a depleted Energy kind is allowed

ArmorManager.Equip does not check the pool — wearing an Energy kind at zero reserve succeeds and returns Codes.NONE. It is worn and worthless until recharged; this is the intended failure mode, not a bug.

A catalog rename or removal drops the profile's copy, not just the display

If a kind id is renamed or deleted from ArmorConfig.Kinds, ArmorManager drops it from Owned (and clears Equipped if it was worn) the next time that player's profile loads — silently, with no refund. Renaming a shipped kind id is effectively deleting it for every player who owns it.

Shop perk effects​

  • Armor Weave (ArmorRechargeBonus): ArmorManager.Recharge refills RESERVE_PER_POINT / Reduce(1, bonus) per Energy point; WorkbenchGuiController shortens the hold to Reduce(RECHARGE_HOLD_TIME, bonus) and previews the same reach.

Data flow​

sequenceDiagram
    participant H as HealthManager (Server)
    participant A as ArmorManager (Server)
    participant S as ArmorService (Server)
    participant C as ArmorClient (Client)

    Note over H: HealthManager.ApplyDamage(amount, type, ...)
    H->>A: ArmorManager.Absorb(player, amount, efficiency)
    A->>A: reduction = clamp(kind.BaseReduction * (1+efficiency), 0, MaxReductionCap)
    A->>A: absorbed = min(amount * reduction, pool); pool -= absorbed
    alt Ballistic pool reaches 0
        A->>A: owned[kindId] = nil; Equipped cleared if worn
    else Energy pool reaches 0
        A->>A: kind stays owned + equipped, protects nothing
    end
    A->>C: ArmorStateSync:FireClient(owned, equipped)
    A-->>H: return amount - absorbed
    H->>H: record.Health -= (amount - absorbed)

    Note over C,S: EQUIP / RECHARGE (at a Workbench)
    C->>S: ReqEquipArmor(bench, kindId) / ReqRechargeArmor(bench, kindId)
    S->>S: WorkbenchStation.IsValidStation + IsPlayerNear
    S->>A: ArmorManager.Equip / ArmorManager.Recharge
    A->>C: ArmorStateSync:FireClient(owned, equipped)
    A-->>S: (ok, code) / (ok, energyAdded, code)
    S-->>C: (ok, code) / (ok, energyAdded, code)
