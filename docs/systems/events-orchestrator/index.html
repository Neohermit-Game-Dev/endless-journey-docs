Events Orchestrator

A server-authoritative scheduler that decides when in-game events fire, which event fires, and enforces a configurable gap between events. It drives a virtual odometer (distance the train has traveled, accumulated only while running) and one independent state machine per channel. Each channel rolls a weighted table at a configurable distance cadence; the roll can come up empty (a Nothing entry), with a pity guard that forces a real event after enough empty rolls. Events plug in as handler modules implementing a shared EventHandler interface — the orchestrator never touches networking; each handler owns its own client communication.

See the design spec at docs/_superpowers/specs/2026-06-23-events-orchestrator-design.md for the full rationale and decision log (SDD artifacts under _superpowers/ are excluded from the published Moonwave site, so this is a repo path, not a doc link).

How it works​

Master switch​

EventConfig.Enabled gates the entire system — while false, EventOrchestrator.Init() registers nothing, builds no channels, and never starts the odometer loop; the orchestrator stays fully dormant. It defaults to false pending the Studio wiring tracked in TODO.md.

The virtual odometer​

The train has no physical speed/odometer of its own — TrainFuelManager only tracks Running/Braked/Stalled state. EventOrchestrator owns its own distance counter: a task.spawn loop ticks every EventConfig.TickInterval seconds (0.25s by default — ample precision for event cadence and cheaper than a per-frame Heartbeat). While running is true it accumulates EventConfig.CruiseSpeed * dt into the odometer, then ticks every channel. running is driven by Signals.SetTrainState (fired by TrainFuelManager on every brake/stall flip) — accumulation pauses on brake, stall, and the pre-game freeze. Signals.SetTrainStarted(true) (first un-brake of a round) calls EventOrchestrator.Reset(), zeroing the odometer and returning every channel to Idle, including force-finishing any handler that's currently Active via its finish().

Channel model​

Channels run fully independently, each with its own roll table, cadence, and state:

  • Encounter — PirateAttack and Outpost share this channel and are mutually exclusive (only one can be active at a time).

Each channel is a state machine: Idle → Active → Cooldown → Idle.

PhaseBehavior
IdleEvery RollInterval boundary crossed since the last tick rolls the weighted table once (a long pause/lag spike doesn't skip rolls). A real pick moves the channel to Active.
ActiveThe chosen handler's Start(ctx, finish) is running. A MaxActiveDistance watchdog (if > 0) force-finishes a handler that never calls finish(). Other channels keep rolling independently.
CooldownAfter finish(), the channel stays quiet until PostEventDelay odometer studs have passed, then returns to Idle with lastRollAt reset to the current odometer (the next roll is a full RollInterval away, not immediate).

Weighted roll + pity​

Each channel's Table is a list of RollEntrys — either a real event ({ Event = "PirateAttack", Weight = 50 }) or the no-op entry ({ Nothing = true, Weight = 20 }). On each roll:

  1. Build the eligible candidate set: real entries are excluded if their handler's optional CanTrigger(ctx) returns false (or no handler is registered for that Id); the Nothing entry is excluded outright when pity is forcing a real event.
  2. Pick one candidate by weight (Random:NextNumber(0, total) against cumulative weight).
  3. If the pick is Nothing (or nothing was eligible), emptyRollStreak increments and the channel stays Idle.
  4. If the pick is a real event, emptyRollStreak resets to 0 and the channel activates that event's handler.

Pity: once emptyRollStreak >= PityRolls, the next roll excludes the Nothing entry, forcing a real event. This bounds the maximum distance a channel can go without a real event to roughly (PityRolls + 1) * RollInterval studs.

EventHandler interface​

export type EventContext = {
    odometer: number,        -- current odometer value at roll/activation time
    rng: Random,              -- orchestrator-owned Random instance
    channel: string,          -- the channel name this activation belongs to
    janitor: Janitor.Janitor, -- per-activation Janitor; destroyed automatically on finish()
}

export type EventHandler = {
    Id: string,                                           -- unique; must match an EventConfig table entry
    Channel: string,                                      -- which channel this handler is registered under
    CanTrigger: ((ctx: EventContext) -> boolean)?,        -- optional eligibility guard, checked at roll time
    Start: (ctx: EventContext, finish: () -> ()) -> (),   -- begin the event; call finish() exactly once when done
}

Handlers register via EventOrchestrator.RegisterHandler(handler) (call before Init(), from the system loader). A duplicate Id is ignored with a warn. Start runs inside a pcall; a throwing handler is logged and the channel is force-finished into Cooldown so one bad event can't wedge the channel. finish is guarded by a per-activation nonce — late or duplicate calls (e.g. a watchdog firing after the handler already finished normally) are no-ops. ctx.janitor is destroyed automatically the moment finish() resolves, so handlers should hang connections/instances/cleanup off it rather than tearing down manually. A load-time validation pass (validate() in Init) warns if a config table references an Id with no registered handler, or a handler's Channel doesn't match the channel it's listed under (or targets an unknown channel) — these are warnings, not hard errors, matching the EnemySpawnerConfig missing-model convention.

Public API​

EventOrchestrator.RegisterHandler(handler: EventHandler)

Registers a handler module. Call before Init() (from the system loader).

EventOrchestrator.Init()

Builds channel state from EventConfig.Channels, runs the validation pass, subscribes to Signals.SetTrainState / Signals.SetTrainStarted, and starts the odometer loop. No-ops entirely while EventConfig.Enabled is false. Idempotent otherwise — a second call warns and is ignored.

EventOrchestrator.Reset()

Zeroes the odometer, force-finishes any Active channel (via its handler's finish), and returns every channel to Idle with lastRollAt reseeded from StartGrace. Called automatically on Signals.SetTrainStarted(true).

EventOrchestrator.GetState()

Returns a snapshot (odometer, running, per-channel phase/lastRollAt/emptyRollStreak/activeId/cooldownUntil) for debugging/inspection.

The two event handlers (stubs)​

src/ServerStorage/SharedModules/Events/ holds one module per event, each implementing EventHandler. Both are intentionally thin — full behavior is deferred to later, per-event specs:

  • PirateAttackEvent (Channel = "Encounter") — calls EnemySpawner.SpawnWave with the group/wave composition from EventConfig.Events.PirateAttack, hangs the returned WaveHandle off ctx.janitor (so a force-finish despawns survivors), and calls finish when WaveHandle.OnCleared fires. This is the one handler with "real" wiring; wave difficulty/rewards are a later spec.
  • OutpostEvent (Channel = "Encounter") — picks a side via ctx.rng, sets a workspace attribute (ActiveOutpostSide), and calls finish after a fixed distance window approximated as time at CruiseSpeed (a handler has no direct access to the live odometer tick). Approach telegraph, stop-by prompt, and outpost contents are a later spec.

Gotchas​

Master switch defaults off

EventConfig.Enabled = false. Until flipped, Init() returns immediately and the orchestrator never rolls, subscribes to signals, or starts its loop — check this first if events "aren't firing" in a playtest.

Reset force-finishes Active handlers, not Cooldown

EventOrchestrator.Reset() only calls activeFinish() for a channel currently in the Active phase. A channel in Cooldown is simply snapped back to Idle — there's no handler running to finish. A round reset mid-cooldown discards the cooldown window rather than honoring it.

OutpostEvent's window is time-based, not distance-based

Because a handler doesn't have direct access to the live odometer tick, OutpostEvent approximates its Window (studs) as Window / EventConfig.CruiseSpeed seconds and uses task.delay. If the train brakes or stalls during the window, the outpost still ends on the original wall-clock timer rather than pausing with the odometer. Called out as a stub limitation in the handler's own doc comment.

Channels are independent; "Encounter" exclusivity is per-channel, not global

PirateAttack and Outpost cannot overlap because they share the Encounter channel. A future event on its own channel could roll and activate while an Encounter event is Active; one needing true global exclusivity would need an explicit cross-channel guard (e.g. a CanTrigger that inspects another channel's state).

Biome change is now a player-initiated Jump Drive action, not a random orchestrator event — see Jump Drive.

Future directions​

See the design spec's "Out of scope" section: full Pirate-attack behavior (wave composition/difficulty/rewards), full Outpost behavior (approach telegraph, stop-by prompt, contents, departure), any client HUD/banner, and persistence of event history across sessions.

Data flow​

sequenceDiagram
    participant Fuel as TrainFuelManager
    participant Orc as EventOrchestrator
    participant H as EventHandler (e.g. PirateAttackEvent)

    Fuel->>Orc: Signals.SetTrainStarted(true)
    Orc->>Orc: Reset() - zero odometer, all channels Idle

    Fuel->>Orc: Signals.SetTrainState(isRunning)
    Orc->>Orc: running = isRunning

    loop every TickInterval while running
        Orc->>Orc: odometer += CruiseSpeed * dt
        Orc->>Orc: tickChannel() per channel
        alt Idle, RollInterval boundary crossed
            Orc->>Orc: weightedPick() - CanTrigger filter, pity check
            alt real event picked
                Orc->>Orc: activate() - phase=Active
                Orc->>H: Signals.OnGameEventStarted(eventId); Start(ctx, finish)
            else Nothing / no eligible candidate
                Orc->>Orc: emptyRollStreak += 1
            end
        else Active, MaxActiveDistance exceeded
            Orc->>H: force-call finish() (watchdog), warn
        end
    end

    H->>Orc: finish()
    Orc->>Orc: ctx.janitor:Destroy(); phase=Cooldown; cooldownUntil = odometer + PostEventDelay
    Orc->>Orc: Signals.OnGameEventEnded(eventId)

Tuning​

  • Config module: EventConfig — src/ReplicatedStorage/SharedModules/Configs/EventConfig.luau
FieldScopeEffect
EnabledglobalMaster on/off switch. false disables the orchestrator entirely (no registration, no loop).
CruiseSpeedglobalVirtual odometer rate in studs/sec, accumulated only while the train is running.
TickIntervalglobalSeconds between odometer-loop ticks (task.wait cadence).
Weightper roll-table entryRelative chance this entry (event or Nothing) is picked on a roll.
RollIntervalper channelOdometer studs between roll attempts on this channel.
PostEventDelayper channelQuiet studs after an event's finish() before the channel resumes rolling.
PityRollsper channelConsecutive empty rolls before the Nothing entry is excluded, forcing a real event.
StartGraceper channelOdometer offset before the channel's first roll (keeps players from being ambushed the instant the train starts moving).
MaxActiveDistanceper channelWatchdog: if an Active handler hasn't called finish() within this many odometer studs, the orchestrator force-finishes it with a warn. 0 disables the watchdog.

Current channel values for Encounter and the per-event parameter tables (EventConfig.Events.PirateAttack / .Outpost) live directly in the config module — see it for exact numbers, since those are expected to be tuned independently of this page.
